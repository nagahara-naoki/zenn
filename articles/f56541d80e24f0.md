DI。Dependency Injection。依存性の注入。依存関係の注入。DIコンテナ。

初めて調べたとき、この5つが同時に出てきました。全部同じものの話をしているのか、別々の話なのかすら分からなかったのを覚えています。

結論から書くと、DIの考え方自体は拍子抜けするほど単純です。

**必要なものを自分で作らず、外から渡してもらう。**

これだけです。難しく感じるのは、この一行に対して周辺の用語が多すぎるからでした。

「依存」という言葉をコードで確かめ、DIを使わない場合の問題から、依存を外から渡す形へ書き換えます。DIコンテナとの違いや、DIを使わない方が単純な場面も扱います。

## そもそも「依存」って何のこと

プログラムにおける依存とは、**あるクラスや関数が動くために、別のクラスやオブジェクトを必要としている状態**のことです。

ユーザー情報を取得する `UserService` を例にします。

```ts
class UserRepository {
  findById(id: number) {
    return {
      id,
      name: "Taro",
    };
  }
}

class UserService {
  private repository = new UserRepository();

  getUser(id: number) {
    return this.repository.findById(id);
  }
}
```

`UserService` は `UserRepository` を使っています。これが依存です。

```text
UserService
    ↓ 必要としている
UserRepository
```

ここで先に言っておきたいことがあります。依存すること自体は、悪いことではありません。

クラスが他のクラスを使うのは当たり前です。それを全部なくそうとしたら、何も作れなくなります。

引っかかるのは、依存していること自体ではありませんでした。**依存するオブジェクトを、クラスの中で自分で作っていること**のほうです。

## この1行が、何を引き起こすか

```ts
class UserService {
  private repository = new UserRepository();

  getUser(id: number) {
    return this.repository.findById(id);
  }
}
```

このコードは普通に動きます。動くので、しばらく誰も困りません。

ただ `new UserRepository()` と書いた時点で、`UserService` は `UserRepository` の**作り方**まで知ってしまいました。つまりこのクラスは、2つの仕事を抱えています。

1. ユーザー情報を取得する処理を行う
2. `UserRepository` を作成する

本当はユーザーのビジネスロジックに集中したいクラスなのに、生成の面倒まで見ている。ここから3つの問題が生えてきます。

### 差し替えられない

テストでは、本物の代わりに `MockUserRepository` を使いたい。

```ts
class MockUserRepository {
  findById(id: number) {
    return {
      id,
      name: "Mock User",
    };
  }
}
```

用意はできました。でも渡せません。

```ts
class UserService {
  private repository = new UserRepository();
}
```

こう書かれている限り、`UserService` は何があっても `UserRepository` を使います。モックに切り替えたければ、`UserService` のコードそのものを書き換えるしかない。

テストのために本番のコードを書き換える。だいぶ嫌な形です。

### テストが重くなる

実務のRepositoryは、DBや外部APIを触ります。

```ts
class UserRepository {
  async findById(id: number) {
    // 実際にはDBやAPIにアクセスする
  }
}
```

これを `UserService` の中で直接作っていると、`UserService` のロジックを確認したいだけなのに、DBへの接続まで付いてきます。

結果、テストはこうなります。

- 実行が遅い
- 外部環境に依存する
- DBの状態によって結果が変わる
- APIの障害でテストが落ちる
- テストデータの準備が面倒になる

確認したいのは自分のロジックだけなのに、依存先の都合に振り回されている状態です。

### 生成の複雑さが伝染する

Repositoryの生成に設定値が要るようになったとします。

```ts
class UserRepository {
  constructor(private endpoint: string) {}
}
```

すると、その設定が `UserService` にまで顔を出します。

```ts
class UserService {
  private repository = new UserRepository("https://api.example.com");

  getUser(id: number) {
    return this.repository.findById(id);
  }
}
```

なぜユーザー処理のクラスが、APIのエンドポイントを知っているのか。依存先の生成が複雑になるほど、使う側も一緒に複雑になっていきます。

## DIは、たった1行の書き換え

ここでDIの出番です。

> DIとは、クラスや関数が必要とする依存オブジェクトを、自分で作るのではなく、外部から渡してもらう設計方法です。

さっきのコードを、その形にします。

```ts
class UserRepository {
  findById(id: number) {
    return {
      id,
      name: "Taro",
    };
  }
}

class UserService {
  constructor(private repository: UserRepository) {}

  getUser(id: number) {
    return this.repository.findById(id);
  }
}

const repository = new UserRepository();
const service = new UserService(repository);

console.log(service.getUser(1));
```

変わったのは、ここだけです。

```ts
constructor(private repository: UserRepository) {}
```

`new UserRepository()` が消えて、外から受け取る形になりました。

```ts
const repository = new UserRepository();
const service = new UserService(repository);
```

これでDIです。フレームワークもライブラリも使っていません。

### 流れで見ると

```text
1. 利用する側のクラスが、必要な依存を定義する
2. 外部で依存オブジェクトを作成する
3. 作成した依存オブジェクトを利用する側に渡す
4. 利用する側は、受け取った依存オブジェクトを使う
5. 必要に応じて、依存オブジェクトを別実装に差し替える
```

```text
外部
  ↓ UserRepositoryを作る
UserRepository
  ↓ 渡す
UserService
  ↓ 利用する
getUser()
```

見るべきところは1つです。利用する側が、依存オブジェクトを作らない。受け取ったものを使うだけ。

## 何が嬉しいのか

### 差し替えられる

本番用とテスト用を、外から選べるようになります。

```ts
class UserRepository {
  findById(id: number) {
    return {
      id,
      name: "Real User",
    };
  }
}

class MockUserRepository {
  findById(id: number) {
    return {
      id,
      name: "Mock User",
    };
  }
}

class UserService {
  constructor(private repository: UserRepository) {}

  getUser(id: number) {
    return this.repository.findById(id);
  }
}
```

本番。

```ts
const repository = new UserRepository();
const service = new UserService(repository);
```

テスト。

```ts
const mockRepository = new MockUserRepository();
const service = new UserService(mockRepository);
```

`UserService` は1文字も変わっていません。

### 抽象に依存させると、もっと効く

いまのコードには、まだ引っかかる点があります。コンストラクタが具体クラスの `UserRepository` を名指ししていることです。

```ts
constructor(private repository: UserRepository) {}
```

これでもDIではあります。ただ、インターフェースにするともう一段柔らかくなります。

```ts
interface IUserRepository {
  findById(id: number): {
    id: number;
    name: string;
  };
}

class UserRepository implements IUserRepository {
  findById(id: number) {
    return {
      id,
      name: "Real User",
    };
  }
}

class MockUserRepository implements IUserRepository {
  findById(id: number) {
    return {
      id,
      name: "Mock User",
    };
  }
}

class UserService {
  constructor(private repository: IUserRepository) {}

  getUser(id: number) {
    return this.repository.findById(id);
  }
}
```

これで `UserService` が見ている相手が、具体的な実装から契約に変わりました。

```text
UserService
    ↓ 具体クラスではなく抽象に依存
IUserRepository
    ↑
UserRepository / MockUserRepository
```

`findById` を持っているものなら、中身が何であろうと構わない。この考え方が、設計原則でいう**依存関係逆転の原則**につながります。

### テストが軽くなる

```ts
class MockUserRepository {
  findById(id: number) {
    return {
      id,
      name: "Test User",
    };
  }
}

const mockRepository = new MockUserRepository();
const service = new UserService(mockRepository);

const user = service.getUser(1);

console.log(user.name); // Test User
```

DBにも外部APIにも触っていません。渡すものを変えただけです。

- 速い
- 安定する
- 外部環境に依存しない
- テストデータを用意しやすい
- ロジックだけを確認しやすい

DIは設計をきれいに見せるための作法ではありません。テストできるコードにするための、実務的な手段です。

### 実装を入れ替えても、使う側は無傷

最初はメモリ上のデータで作ったとします。

```ts
class InMemoryUserRepository implements IUserRepository {
  findById(id: number) {
    return {
      id,
      name: "Memory User",
    };
  }
}
```

あとからAPI経由に変えたくなりました。

```ts
class ApiUserRepository implements IUserRepository {
  findById(id: number) {
    return {
      id,
      name: "API User",
    };
  }
}
```

直すのは、渡す場所の1行だけです。

```ts
const repository = new ApiUserRepository();
const service = new UserService(repository);
```

`UserService` は `IUserRepository` しか知らないので、データがどこから来ているかを気にする必要がありません。

### 責務の線が引ける

```text
UserService
  → ユーザー処理に集中する

外側のコード
  → どのRepositoryを使うか決める
```

「作る責務」を外へ追い出した結果、クラスの中身がやりたいことだけになりました。

## 渡し方は3つある

実務ではコンストラクタインジェクションがほとんどですが、他の形も知っておくと選べます。

### コンストラクタインジェクション

```ts
class UserService {
  constructor(private repository: IUserRepository) {}

  getUser(id: number) {
    return this.repository.findById(id);
  }
}
```

いちばんの利点は、依存関係が隠せないことです。コンストラクタを見れば、このクラスが何を必要としているか一目で分かります。

しかも、渡さないとインスタンスが作れません。渡し忘れが構造的に起きない。基本はこれで足ります。

### セッターインジェクション

```ts
class UserService {
  private repository?: IUserRepository;

  setRepository(repository: IUserRepository) {
    this.repository = repository;
  }

  getUser(id: number) {
    if (!this.repository) {
      throw new Error("repository is not set");
    }

    return this.repository.findById(id);
  }
}
```

インスタンスを作ったあとで設定できます。

```ts
const service = new UserService();
service.setRepository(new UserRepository());
```

柔軟です。ただ、設定を忘れた状態のインスタンスが存在できてしまう。必須の依存には向きません。

### メソッドインジェクション

```ts
class UserService {
  getUser(id: number, repository: IUserRepository) {
    return repository.findById(id);
  }
}
```

そのメソッドでだけ必要な依存を渡す形です。毎回引数に書くことになるので、何度も使う依存には向きません。

## DIとDIコンテナは、別物です

ここが最初にいちばん混乱したところでした。

```text
DI
  → 依存オブジェクトを外から渡す設計方法

DIコンテナ
  → 依存オブジェクトの生成や注入を自動で管理する仕組み
```

DIは考え方。DIコンテナは、それを楽にするための道具。

### コンテナがなくても、DIはできる

ここまで書いてきたコードには、コンテナが1つも出てきていません。

```ts
const repository = new UserRepository();
const service = new UserService(repository);
```

でも、依存を外から渡しています。これは立派にDIです。

### Angularの場合

```ts
@Injectable({
  providedIn: "root",
})
export class UserService {
  getUser(id: number) {
    return {
      id,
      name: "Taro",
    };
  }
}
```

```ts
@Component({
  selector: "app-user",
  template: `<p>{{ user.name }}</p>`,
})
export class UserComponent {
  user = this.userService.getUser(1);

  constructor(private userService: UserService) {}
}
```

`new UserService()` はどこにもありません。AngularのDIコンテナが作って、渡しています。

### NestJSの場合

```ts
@Injectable()
export class UserService {
  findUser(id: number) {
    return {
      id,
      name: "Taro",
    };
  }
}
```

```ts
@Controller("users")
export class UserController {
  constructor(private readonly userService: UserService) {}

  @Get(":id")
  getUser(@Param("id") id: string) {
    return this.userService.findUser(Number(id));
  }
}
```

やっていることは同じです。生成と注入をNestJSが引き受けています。

### Reactには？

標準のDIコンテナはありません。でも、考え方は普通に使われています。

```tsx
type UserListProps = {
  fetchUsers: () => Promise<string[]>;
};

function UserList({ fetchUsers }: UserListProps) {
  // fetchUsersを使ってユーザー一覧を取得する
}
```

`UserList` は `fetchUsers` を自分で作っていません。外から受け取っています。propsによるDIです。

Contextを使う形もあります。

```tsx
const ApiClientContext = createContext<ApiClient | null>(null);

function UserPage() {
  const apiClient = useContext(ApiClientContext);

  if (!apiClient) {
    throw new Error("ApiClient is not provided");
  }

  // apiClientを使う
}
```

コンテナという形をとっていないだけで、DIそのものは日常的に書いています。

## 並べて見る

**DIなし**

```ts
class UserService {
  private repository = new UserRepository();

  getUser(id: number) {
    return this.repository.findById(id);
  }
}
```

```text
UserService
  ├─ UserRepositoryを作る
  └─ UserRepositoryを使う
```

**DIあり**

```ts
class UserService {
  constructor(private repository: IUserRepository) {}

  getUser(id: number) {
    return this.repository.findById(id);
  }
}
```

```text
外部
  └─ Repositoryを作る

UserService
  └─ Repositoryを使う
```

箱の中から仕事が1つ消えた。それだけの違いです。

## 使いすぎるとどうなるか

DIを覚えた直後がいちばん危ないです。何にでも適用したくなります。

### 小さい処理にまで持ち込まない

```ts
function double(value: number) {
  return value * 2;
}
```

これをDIにする理由はありません。

効くのは、こういう相手です。

- DBアクセス
- 外部APIアクセス
- ファイル操作
- ログ出力
- メール送信
- 認証処理
- 設定値に依存する処理
- テスト時に差し替えたい処理

差し替えたいもの。テストで切り離したいもの。判断基準はこれで足ります。

### 引数が5個並んだら、疑う

```ts
class UserService {
  constructor(
    private userRepository: UserRepository,
    private mailService: MailService,
    private logger: Logger,
    private paymentService: PaymentService,
    private notificationService: NotificationService,
  ) {}
}
```

依存が多いこと自体は、必ずしも悪ではありません。

ただ、これだけ並んでいるなら、そのクラスが色々やりすぎているサインである可能性は高い。直すべきはDIの書き方ではなく、クラスの分け方のほうです。

### コンテナは、便利すぎて見えなくなる

自動で注入してくれるのは楽です。楽なぶん、どこで何が作られているのかが見えなくなります。

規模が大きくなってきたら、この5点は説明できる状態を保ってください。

- どのクラスがどの依存を必要としているか
- どの実装が注入されているか
- スコープはどうなっているか
- シングルトンなのか、リクエストごとなのか
- テスト時にどう差し替えるか

## DIは手段です

最後にこれだけ。

DIを使うこと自体はゴールではありません。目指しているのは、その先です。

- テストしやすくする
- 変更に強くする
- 差し替えしやすくする
- 責務を分けやすくする
- クラス同士の結合を弱くする

コードが読みやすく、変えやすくなっていないなら、DIを入れた意味はありません。

---

冒頭の5つの用語に戻ります。

DI、Dependency Injection、依存性の注入、依存関係の注入。この4つは全部同じものの言い換えでした。**必要なものを自分で作らず、外から渡してもらう設計**です。

そして5つめのDIコンテナだけが別物で、それを自動でやってくれる道具のことでした。

```text
DI
  → 依存を外から渡す設計方法

DIコンテナ
  → 依存の生成や注入を自動管理する仕組み
```

この一行さえ持っておけば、Angularも、NestJSも、Springも、同じ話をしているのが分かります。

> DIとは、必要なものを自分で作らず、外から渡してもらう設計である。
