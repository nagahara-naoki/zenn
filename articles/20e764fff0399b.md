# はじめに

Node.js やフロントエンド開発をしていると、ほぼ必ず `package.json` を触ります。

React、Vue、Angular、Next.js、Vite、React Native、Expo、Node.js の API サーバーなど、どのプロジェクトでもだいたい出てきます。

ただ、普段よく見るのはこのあたりではないでしょうか。

```json
{
  "scripts": {},
  "dependencies": {},
  "devDependencies": {}
}
```

一方で、実務のプロジェクトでは次のような項目もよく見かけます。

```json
{
  "private": true,
  "type": "module",
  "main": "./dist/index.js",
  "exports": {
    ".": "./dist/index.js"
  },
  "peerDependencies": {},
  "overrides": {},
  "engines": {},
  "packageManager": "pnpm@10.0.0"
}
```

最初は「なんとなく書いてあるけど、正直よく分からない」となりがちです。

この記事では、`package.json` の中でも **実務でよく見る項目** を中心に整理します。

全項目を百科事典のように網羅するというより、次のような状態を目指します。

- `package.json` を見たときに、プロジェクトの構成が少し読める
- `dependencies` / `devDependencies` / `peerDependencies` の違いが分かる
- `scripts` に何が書かれているか分かる
- `type` / `main` / `exports` の役割が分かる
- `overrides` をなぜ使うのか分かる
- `engines` / `packageManager` で環境を固定する意味が分かる

# package.json とは

`package.json` は、Node.js / npm プロジェクトの設定ファイルです。

npm 公式ドキュメントでは、`package.json` は実際の JSON ファイルであり、パッケージに関する情報や npm の挙動に関わる設定を書く場所として説明されています。

ざっくり言うと、`package.json` には次のような情報を書きます。

| 種類 | 例 |
| --- | --- |
| プロジェクト情報 | `name`, `version`, `description` |
| 実行コマンド | `scripts` |
| 依存パッケージ | `dependencies`, `devDependencies`, `peerDependencies` |
| 依存関係の調整 | `overrides` |
| 実行環境 | `engines`, `packageManager` |
| モジュール形式 | `type`, `main`, `exports`, `imports` |
| npm 公開設定 | `files`, `private`, `publishConfig` |
| モノレポ設定 | `workspaces` |

最初に大事なのは、`package.json` は **npm install のためだけのファイルではない** ということです。

開発コマンド、依存関係、Node.js のバージョン、ライブラリとして公開するときの入口など、プロジェクトの重要な情報が集まっています。

# まずは全体像を見る

例として、フロントエンドアプリの `package.json` を見てみます。

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "tsc && vite build",
    "preview": "vite preview",
    "test": "vitest",
    "lint": "eslint .",
    "format": "prettier --write ."
  },
  "dependencies": {
    "@vitejs/plugin-react": "latest",
    "react": "^19.0.0",
    "react-dom": "^19.0.0"
  },
  "devDependencies": {
    "typescript": "^5.8.0",
    "vite": "^6.0.0",
    "vitest": "^3.0.0",
    "eslint": "^9.0.0",
    "prettier": "^3.0.0"
  },
  "engines": {
    "node": ">=22"
  },
  "packageManager": "pnpm@10.0.0"
}
```

この `package.json` を見るだけで、次のようなことが分かります。

- Vite を使っている
- React を使っている
- TypeScript を使っている
- テストは Vitest
- Lint は ESLint
- Format は Prettier
- Node.js は 22 以上を想定している
- パッケージマネージャは pnpm を想定している
- npm に公開する予定はなさそう

つまり、`package.json` は **プロジェクトの自己紹介ファイル** のようなものです。

# name

```json
{
  "name": "my-app"
}
```

`name` はプロジェクト名、または npm に公開するパッケージ名です。

アプリ開発では単純にプロジェクト名として使われることが多いです。

ライブラリとして npm に公開する場合は、他のパッケージと名前が重複しないようにする必要があります。

スコープ付きパッケージの場合は、次のような形になります。

```json
{
  "name": "@my-org/ui-button"
}
```

`@my-org/ui-button` のように、`@スコープ名/パッケージ名` の形式です。

## name で見るポイント

- アプリなのかライブラリなのか
- スコープ付きパッケージか
- monorepo の package 名として使われているか
- import 時に参照される名前か

ライブラリの場合、`name` は利用者が `import` するときの名前にも関係します。

```ts
import { Button } from "@my-org/ui-button";
```

この `@my-org/ui-button` が `package.json` の `name` と対応します。

# version

```json
{
  "version": "1.0.0"
}
```

`version` はパッケージのバージョンです。

npm に公開するパッケージでは特に重要です。`name` と `version` の組み合わせで、そのパッケージの特定バージョンを識別します。

よく見る形式は次のようなものです。

```txt
1.0.0
```

これは SemVer と呼ばれる形式です。

```txt
MAJOR.MINOR.PATCH
```

それぞれざっくり説明すると、次のようになります。

| 位置 | 例 | 意味 |
| --- | --- | --- |
| MAJOR | `1` | 破壊的変更があるときに上げる |
| MINOR | `0` | 後方互換性のある機能追加で上げる |
| PATCH | `0` | 後方互換性のあるバグ修正で上げる |

アプリ開発では、npm に公開しないなら `version` をそこまで意識しないこともあります。

一方で、ライブラリ開発や社内パッケージではかなり重要です。

# private

```json
{
  "private": true
}
```

`private` は、誤って npm に公開しないための設定です。

`"private": true` にしておくと、npm はそのパッケージの公開を拒否します。

アプリ開発では、基本的に `private: true` が付いていることが多いです。

```json
{
  "name": "my-app",
  "private": true
}
```

これは「このプロジェクトは npm パッケージとして公開するものではない」という意思表示にもなります。

## private があるときの見方

`private: true` がある場合は、だいたい次のように考えられます。

- Web アプリ本体
- 管理画面
- 社内ツール
- npm に公開しない個人開発アプリ
- monorepo のルート package

monorepo のルートでは、誤公開防止のために `private: true` が付いていることが多いです。

# scripts

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "test": "vitest"
  }
}
```

`scripts` は、よく使うコマンドに名前を付けるための項目です。

上の例なら、次のように実行できます。

```bash
npm run dev
npm run build
npm run test
```

npm では `npm run <script名>` で実行します。

ただし、`start` や `test` など一部は短縮できます。

```bash
npm start
npm test
```

## scripts を見るとプロジェクトの開発フローが分かる

`scripts` を見ると、そのプロジェクトで何を使っているかがかなり分かります。

```json
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start",
    "lint": "next lint",
    "test": "jest",
    "e2e": "playwright test",
    "format": "prettier --write .",
    "typecheck": "tsc --noEmit"
  }
}
```

この場合、次のように読めます。

- Next.js を使っている
- Unit Test は Jest
- E2E は Playwright
- Format は Prettier
- 型チェックは `tsc --noEmit`

プロジェクトに入ったら、まず `scripts` を見ると開発の入口が分かりやすいです。

## よくある scripts

| script | 役割 |
| --- | --- |
| `dev` | 開発サーバー起動 |
| `start` | 本番起動、またはサーバー起動 |
| `build` | ビルド |
| `test` | テスト実行 |
| `lint` | ESLint などで静的解析 |
| `format` | Prettier などで整形 |
| `typecheck` | TypeScript の型チェック |
| `e2e` | E2E テスト |
| `storybook` | Storybook 起動 |

## pre / post scripts

npm scripts には、`pre` / `post` という仕組みもあります。

```json
{
  "scripts": {
    "prebuild": "npm run lint",
    "build": "vite build",
    "postbuild": "node scripts/after-build.js"
  }
}
```

この状態で次を実行すると、

```bash
npm run build
```

実行順は次のようになります。

```txt
prebuild → build → postbuild
```

便利ですが、暗黙的に処理が走るので、知らないと「なぜ build の前に lint が走るのか」が分かりづらくなります。

チーム開発では、分かりやすさを優先して明示的に書くことも多いです。

```json
{
  "scripts": {
    "build": "npm run lint && vite build"
  }
}
```

# dependencies

```json
{
  "dependencies": {
    "react": "^19.0.0",
    "react-dom": "^19.0.0"
  }
}
```

`dependencies` は、アプリやライブラリが **実行時に必要とする依存関係** を書く場所です。

例えば React アプリなら、`react` や `react-dom` は実行時に必要なので `dependencies` に入ります。

```json
{
  "dependencies": {
    "react": "^19.0.0",
    "react-dom": "^19.0.0"
  }
}
```

サーバーサイドなら、次のようなものが `dependencies` に入ることが多いです。

```json
{
  "dependencies": {
    "express": "^5.0.0",
    "zod": "^3.0.0",
    "pg": "^8.0.0"
  }
}
```

## dependencies に入れる基準

ざっくり言うと、次のようなものは `dependencies` です。

- アプリの実行に必要
- 本番環境でも必要
- ビルド後の成果物が依存している
- ライブラリ利用者が実行時に必要とする

逆に、次のようなものは基本的に `dependencies` ではありません。

- テストツール
- Lint ツール
- Formatter
- TypeScript
- Storybook
- 開発用のコード生成ツール

これらは次の `devDependencies` に入れることが多いです。

# devDependencies

```json
{
  "devDependencies": {
    "typescript": "^5.8.0",
    "vitest": "^3.0.0",
    "eslint": "^9.0.0",
    "prettier": "^3.0.0"
  }
}
```

`devDependencies` は、**開発時に必要な依存関係** を書く場所です。

例えば次のようなものです。

- TypeScript
- ESLint
- Prettier
- Jest
- Vitest
- Playwright
- Storybook
- build tool
- test utility

アプリの実行そのものには不要だけど、開発・ビルド・テストには必要なものです。

## dependencies と devDependencies の違い

よくある説明は次です。

| 項目 | 役割 |
| --- | --- |
| `dependencies` | 本番実行に必要 |
| `devDependencies` | 開発時に必要 |

ただし、フロントエンドアプリでは少し注意が必要です。

例えば Vite や TypeScript は本番ブラウザ上では動きません。しかし、アプリをビルドするためには必要です。

そのため、アプリ開発では `devDependencies` にビルドツールが入っていても問題ありません。

```json
{
  "devDependencies": {
    "vite": "^6.0.0",
    "typescript": "^5.8.0"
  }
}
```

本番サーバー上で `npm install --omit=dev` してからビルドするような構成だと、ビルドに必要なツールがなくて失敗することがあります。

CI/CD の構成によって、どこまでを本番環境に含めるかは変わります。

# peerDependencies

```json
{
  "peerDependencies": {
    "react": "^18.0.0 || ^19.0.0"
  }
}
```

`peerDependencies` は、ざっくり言うと **利用側のプロジェクトに入っていてほしい依存関係** です。

特にライブラリやプラグインでよく使います。

例えば React 用の UI ライブラリを作る場合、そのライブラリ自身が React と一緒に動く必要があります。

しかし、UI ライブラリ側が勝手に別の React を持ってしまうと、利用側の React と二重になって問題が起きることがあります。

そこで、次のように書きます。

```json
{
  "name": "my-ui-library",
  "peerDependencies": {
    "react": "^18.0.0 || ^19.0.0",
    "react-dom": "^18.0.0 || ^19.0.0"
  }
}
```

これは、利用側に対して次のように伝えています。

> このライブラリは React 18 または 19 と一緒に使ってください。

## peerDependencies が出てくる場面

よく見るのは次のような場面です。

- React の UI ライブラリ
- Angular のプラグイン
- ESLint plugin
- Storybook addon
- Vite plugin
- webpack plugin

例えば、ある Angular 関連ライブラリが次のような `peerDependencies` を持っているとします。

```json
{
  "peerDependencies": {
    "@angular/core": ">=18.0.0 <22.0.0"
  }
}
```

この場合、利用側の Angular が 22 だと、依存関係の解決でエラーや警告が出る可能性があります。

Angular のアップデート時に Storybook や周辺ライブラリで詰まりやすいのは、この `peerDependencies` の制約が原因であることが多いです。

## peerDependencies は「同居条件」

`dependencies` は「自分が使うもの」です。

`peerDependencies` は「利用側に一緒に用意してほしいもの」です。

イメージとしては、次のように考えると分かりやすいです。

| 項目 | イメージ |
| --- | --- |
| `dependencies` | 自分の荷物 |
| `devDependencies` | 開発中だけ使う道具 |
| `peerDependencies` | 相手の環境にいてほしいもの |

# peerDependenciesMeta

```json
{
  "peerDependencies": {
    "react": "^19.0.0",
    "@types/react": "^19.0.0"
  },
  "peerDependenciesMeta": {
    "@types/react": {
      "optional": true
    }
  }
}
```

`peerDependenciesMeta` は、`peerDependencies` に対する追加情報を書く項目です。

よく見る使い方は、peer dependency を optional にすることです。

```json
{
  "peerDependenciesMeta": {
    "@types/react": {
      "optional": true
    }
  }
}
```

「対応しているけど、必須ではない」という依存関係を表現したいときに使います。

アプリ開発だけだとあまり書く機会はないかもしれませんが、ライブラリ開発では見かけることがあります。

# optionalDependencies

```json
{
  "optionalDependencies": {
    "fsevents": "^2.0.0"
  }
}
```

`optionalDependencies` は、インストールに失敗しても処理を続行できる依存関係です。

例えば、特定 OS でだけ使うパッケージなどで見かけます。

ただし、optional だからといって、コード側で何もしなくてよいわけではありません。

使えない環境がある前提で、コード側でも存在チェックが必要です。

```ts
let optionalPackage: unknown;

try {
  optionalPackage = await import("some-optional-package");
} catch {
  optionalPackage = null;
}
```

アプリ開発で自分から書く機会は少なめですが、依存パッケージの中ではよく見かけます。

# overrides

```json
{
  "overrides": {
    "lodash": "^4.17.21"
  }
}
```

`overrides` は、依存関係ツリーの中にあるパッケージのバージョンを上書きするための項目です。

かなり実務寄りの項目です。

例えば、自分のプロジェクトが直接 `lodash` を使っていなくても、依存しているライブラリのさらに奥で古い `lodash` が使われていることがあります。

```txt
my-app
└─ some-library
   └─ lodash@古いバージョン
```

このようなときに、脆弱性対応などで特定バージョンへ寄せたい場合があります。

```json
{
  "overrides": {
    "lodash": "^4.17.21"
  }
}
```

これにより、依存関係ツリー上の `lodash` を指定バージョンに上書きできます。

## overrides の使いどころ

主な使いどころは次です。

| 場面 | 説明 |
| --- | --- |
| 脆弱性対応 | 依存の奥にある vulnerable package を一時的に更新したい |
| バグ回避 | 特定バージョンのバグを避けたい |
| バージョン統一 | 同じパッケージの複数バージョン混在を避けたい |
| fork 利用 | 修正版 fork に差し替えたい |

## 特定の親パッケージ配下だけ上書きする

`overrides` は、単純に全体へ効かせるだけでなく、特定の依存配下だけに効かせることもできます。

```json
{
  "overrides": {
    "some-library": {
      "lodash": "^4.17.21"
    }
  }
}
```

これは、`some-library` の配下にある `lodash` を上書きするイメージです。

## overrides の注意点

`overrides` は便利ですが、かなり強い操作です。

依存パッケージが想定していないバージョンを使わせることになるため、次の点に注意した方がよいです。

- テストを必ず通す
- lock file の差分を見る
- 一時対応として使う
- なぜ `overrides` したのか PR やコメントに残す
- 可能なら本来の依存パッケージ自体を更新する

`overrides` は「とりあえず何でも直せる魔法」ではありません。

依存関係の問題を一時的に回避するための強力な道具、と考えるのがよいです。

## npm / pnpm / yarn で書き方が違う

注意点として、パッケージマネージャによって似た仕組みの名前が違うことがあります。

| パッケージマネージャ | 項目 |
| --- | --- |
| npm | `overrides` |
| pnpm | `pnpm.overrides` など |
| Yarn Classic | `resolutions` |

プロジェクトが npm なのか pnpm なのか yarn なのかによって確認するドキュメントが変わります。

# engines

```json
{
  "engines": {
    "node": ">=22",
    "npm": ">=10"
  }
}
```

`engines` は、このパッケージが想定している Node.js や npm のバージョンを書く項目です。

例えば次のように書きます。

```json
{
  "engines": {
    "node": ">=22"
  }
}
```

これは「Node.js 22 以上を想定しています」という意味です。

## engines は完全な固定ではない

注意点として、npm の `engines` はデフォルトでは警告に近い扱いです。

つまり、`engines` に合わない Node.js を使っていたとしても、設定によってはインストールが止まらず、警告だけで進むことがあります。

厳密に止めたい場合は、npm の `engine-strict` なども関係します。

とはいえ、チーム開発では `engines` を書いておくことで、想定環境が分かりやすくなります。

```json
{
  "engines": {
    "node": "22.x"
  }
}
```

また、Volta を使っている場合は次のような設定と併用されることもあります。

```json
{
  "volta": {
    "node": "22.17.0",
    "pnpm": "10.0.0"
  }
}
```

`engines` は「このプロジェクトが想定している環境」を読むための重要なヒントです。

# packageManager

```json
{
  "packageManager": "pnpm@10.0.0"
}
```

`packageManager` は、プロジェクトで使うパッケージマネージャとバージョンを書く項目です。

例えば次のように書きます。

```json
{
  "packageManager": "pnpm@10.0.0"
}
```

これは「このプロジェクトでは pnpm 10.0.0 を使う想定です」という意味です。

他にも次のような形があります。

```json
{
  "packageManager": "npm@11.0.0"
}
```

```json
{
  "packageManager": "yarn@4.0.0"
}
```

## なぜ packageManager が必要なのか

同じプロジェクトで、ある人は npm、ある人は yarn、ある人は pnpm を使うと、lock file が混ざったり、依存解決の結果が変わったりすることがあります。

例えば、次のような状態です。

```txt
package-lock.json
pnpm-lock.yaml
yarn.lock
```

これらが同時に存在すると、どれを正とするのか分かりづらくなります。

`packageManager` を書いておくと、プロジェクトが想定しているパッケージマネージャが分かります。

## packageManager と Corepack

Corepack は、プロジェクトの `package.json` にある `packageManager` を見て、指定されたパッケージマネージャを使うための仕組みです。

ただし、Node.js や Corepack のバージョン、環境によって扱いが変わることがあるため、プロジェクトの README やセットアップ手順にも明記しておくと安全です。

# type

```json
{
  "type": "module"
}
```

`type` は、Node.js が `.js` ファイルをどのモジュール形式として扱うかを決める項目です。

よく見る値は次の2つです。

| 値 | 意味 |
| --- | --- |
| `module` | `.js` を ES Modules として扱う |
| `commonjs` | `.js` を CommonJS として扱う |

例えば次のように書くと、同じディレクトリ配下の `.js` は ES Modules として扱われます。

```json
{
  "type": "module"
}
```

この場合、次のような書き方を使います。

```js
import fs from "node:fs";

export function hello() {
  console.log("hello");
}
```

一方で、`type` が未指定、または `commonjs` の場合は CommonJS として扱われます。

```json
{
  "type": "commonjs"
}
```

```js
const fs = require("node:fs");

module.exports = {
  hello() {
    console.log("hello");
  }
};
```

## type で詰まりやすいポイント

`type` は、次のようなエラーの原因になることがあります。

- `require is not defined`
- `Cannot use import statement outside a module`
- `ERR_REQUIRE_ESM`
- `module.exports` が期待通りに動かない

つまり、`type` は単なる飾りではありません。

Node.js がファイルをどう解釈するかに関わる、かなり重要な項目です。

## .mjs / .cjs との関係

`type` に関係なく、拡張子で明示することもできます。

| 拡張子 | 扱い |
| --- | --- |
| `.mjs` | ES Modules |
| `.cjs` | CommonJS |
| `.js` | `package.json` の `type` に従う |

混在させたい場合は `.mjs` や `.cjs` を使うことがあります。

# main

```json
{
  "main": "./dist/index.js"
}
```

`main` は、そのパッケージの入口となるファイルを指定する項目です。

例えば、あるパッケージが次のような `package.json` を持っているとします。

```json
{
  "name": "my-library",
  "main": "./dist/index.js"
}
```

利用側で次のように import したとき、

```ts
import { hello } from "my-library";
```

`my-library` の入口として `./dist/index.js` が使われます。

## main はアプリよりライブラリで重要

Web アプリ本体では、`main` をあまり意識しないこともあります。

一方で、npm に公開するライブラリでは重要です。

```json
{
  "name": "my-library",
  "version": "1.0.0",
  "main": "./dist/index.cjs"
}
```

ただし、最近のパッケージでは次の `exports` を使うことが増えています。

# exports

```json
{
  "exports": {
    ".": "./dist/index.js"
  }
}
```

`exports` は、パッケージの外部に公開する入口を定義する項目です。

Node.js 公式ドキュメントでは、`exports` は `main` の現代的な代替として説明されています。

`exports` を使うと、次のように「どのファイルを外部から import できるか」を明示できます。

```json
{
  "name": "my-library",
  "exports": {
    ".": "./dist/index.js",
    "./button": "./dist/button.js",
    "./card": "./dist/card.js"
  }
}
```

利用側は次のように import できます。

```ts
import { hello } from "my-library";
import { Button } from "my-library/button";
import { Card } from "my-library/card";
```

## exports は公開範囲を絞れる

`exports` の重要なポイントは、公開していないパスへのアクセスを制限できることです。

例えば、次のような内部ファイルがあったとします。

```txt
src/internal/secret.ts
```

`exports` で公開していなければ、利用者が勝手に内部ファイルへアクセスしづらくなります。

```json
{
  "exports": {
    ".": "./dist/index.js"
  }
}
```

これはライブラリの API を安定させるために重要です。

内部構造を変更しても、公開 API を守っていれば利用側への影響を減らせます。

## import / require で出し分ける

ES Modules と CommonJS の両方に対応するため、条件付き exports を書くこともあります。

```json
{
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  }
}
```

このようにすると、ES Modules から import された場合と、CommonJS から require された場合で入口を変えられます。

ただし、ここは複雑になりやすいので、アプリ開発だけなら最初から深追いしすぎなくてもよいです。

# imports

```json
{
  "imports": {
    "#utils/*": "./src/utils/*"
  }
}
```

`imports` は、パッケージ内部で使う import alias のようなものです。

`exports` が外部向けの公開口だとすると、`imports` は内部向けの参照設定です。

例えば次のように書けます。

```json
{
  "imports": {
    "#utils/*": "./src/utils/*"
  }
}
```

コード側では次のように import できます。

```ts
import { formatDate } from "#utils/date";
```

`#` から始まる指定を使うのが特徴です。

TypeScript の `paths` と似た用途で見かけることがありますが、完全に同じものではありません。

Node.js の解決、TypeScript の型解決、bundler の解決が絡むため、実務では設定を揃える必要があります。

# files

```json
{
  "files": [
    "dist",
    "README.md",
    "LICENSE"
  ]
}
```

`files` は、npm にパッケージを公開するとき、どのファイルを含めるかを指定する項目です。

ライブラリ開発でよく使います。

例えば、TypeScript のソースコードではなく、ビルド後の `dist` だけを公開したい場合があります。

```json
{
  "files": ["dist"]
}
```

こうすると、npm publish 時に含めるファイルを絞れます。

## files がない場合

`files` を省略すると、基本的には多くのファイルが含まれます。

不要なファイルを公開しないためにも、ライブラリでは `files` を指定しておくと分かりやすいです。

```json
{
  "files": [
    "dist",
    "README.md",
    "LICENSE"
  ]
}
```

アプリ開発だけなら、`files` を意識する機会は少なめです。

# bin

```json
{
  "bin": {
    "my-cli": "./bin/cli.js"
  }
}
```

`bin` は、CLI コマンドを提供するパッケージで使います。

例えば、次のように書くと、パッケージをインストールしたときに `my-cli` というコマンドを使えるようになります。

```json
{
  "name": "my-cli-package",
  "bin": {
    "my-cli": "./bin/cli.js"
  }
}
```

CLI ファイル側には、通常 shebang を書きます。

```js
#!/usr/bin/env node

console.log("hello cli");
```

アプリ開発ではあまり書きませんが、npm パッケージとして CLI ツールを作る場合は重要です。

# browser

```json
{
  "browser": "./dist/browser.js"
}
```

`browser` は、ブラウザ向けの入口や置き換えを示すために使われる項目です。

Node.js 向けとブラウザ向けで実装を分けたい場合に見かけます。

例えば、Node.js では `fs` を使うけど、ブラウザでは使えないため別実装にしたい、というようなケースです。

ただし、`browser` の扱いは bundler によって差が出ることがあります。

最近は `exports` の conditional exports で環境ごとの入口を制御するケースもあります。

# repository

```json
{
  "repository": {
    "type": "git",
    "url": "git+https://github.com/example/my-library.git"
  }
}
```

`repository` は、ソースコードの置き場所を示す項目です。

npm に公開するパッケージでは、利用者がリポジトリを見つけやすくなります。

```json
{
  "repository": {
    "type": "git",
    "url": "git+https://github.com/example/my-library.git"
  }
}
```

GitHub の場合は、README や issue への導線にもなります。

アプリ本体では必須ではありませんが、OSS や社内パッケージではあると便利です。

# license

```json
{
  "license": "MIT"
}
```

`license` は、パッケージのライセンスを示す項目です。

npm に公開するパッケージでは重要です。

例えば MIT ライセンスなら次のように書きます。

```json
{
  "license": "MIT"
}
```

複数ライセンスの場合は、SPDX の表記を使うことがあります。

```json
{
  "license": "(MIT OR Apache-2.0)"
}
```

非公開プロジェクトで外部に利用を許可しない場合は、次のようにすることもあります。

```json
{
  "license": "UNLICENSED",
  "private": true
}
```

# workspaces

```json
{
  "workspaces": ["packages/*"]
}
```

`workspaces` は、monorepo で複数パッケージを管理するための項目です。

例えば次のような構成があるとします。

```txt
my-repo/
├─ package.json
└─ packages/
   ├─ ui/
   │  └─ package.json
   └─ utils/
      └─ package.json
```

ルートの `package.json` に次のように書きます。

```json
{
  "private": true,
  "workspaces": ["packages/*"]
}
```

これにより、`packages/ui` や `packages/utils` を同じリポジトリ内の workspace として扱えます。

monorepo では、ルートの `package.json` と各パッケージの `package.json` の役割が分かれます。

## ルート package.json

```json
{
  "name": "my-monorepo",
  "private": true,
  "workspaces": ["packages/*"],
  "scripts": {
    "build": "npm run build --workspaces"
  }
}
```

## packages/ui/package.json

```json
{
  "name": "@my-org/ui",
  "version": "1.0.0",
  "main": "./dist/index.js"
}
```

monorepo では、どの `package.json` を見ているのかを意識することが大事です。

# package.json と lock file の違い

`package.json` と一緒によく出てくるのが lock file です。

代表的なものは次です。

| パッケージマネージャ | lock file |
| --- | --- |
| npm | `package-lock.json` |
| pnpm | `pnpm-lock.yaml` |
| yarn | `yarn.lock` |

`package.json` は、依存関係の希望や設定を書きます。

```json
{
  "dependencies": {
    "react": "^19.0.0"
  }
}
```

一方で lock file は、実際に解決された依存関係の結果を固定します。

例えば `^19.0.0` と書いた場合、将来的に `19.1.0` や `19.2.0` が入る可能性があります。

lock file があることで、チーム内や CI で同じ依存関係を再現しやすくなります。

## lock file は基本的にコミットする

アプリ開発では、lock file は基本的にコミットします。

理由は、チームメンバーや CI で同じ依存関係を使うためです。

```txt
package.json       依存関係の希望を書く
package-lock.json  実際に解決された結果を固定する
```

もし `package-lock.json` と `pnpm-lock.yaml` と `yarn.lock` が同時にある場合は、プロジェクトで使うパッケージマネージャを整理した方がよいです。

# 実務で package.json を読むときのチェックリスト

プロジェクトに入ったときは、次の順番で見ると分かりやすいです。

## 1. scripts を見る

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "test": "vitest"
  }
}
```

まずは、どう起動するのか、どうビルドするのか、どうテストするのかを確認します。

## 2. dependencies を見る

```json
{
  "dependencies": {
    "react": "^19.0.0",
    "react-router": "^7.0.0"
  }
}
```

主要ライブラリを見ると、プロジェクトの技術スタックが分かります。

## 3. devDependencies を見る

```json
{
  "devDependencies": {
    "typescript": "^5.8.0",
    "vitest": "^3.0.0",
    "playwright": "^1.0.0"
  }
}
```

テスト、Lint、Format、ビルドツールが分かります。

## 4. engines / packageManager を見る

```json
{
  "engines": {
    "node": ">=22"
  },
  "packageManager": "pnpm@10.0.0"
}
```

Node.js のバージョンやパッケージマネージャを確認します。

環境差分によるエラーを避けるために重要です。

## 5. type / main / exports を見る

```json
{
  "type": "module",
  "main": "./dist/index.js",
  "exports": {
    ".": "./dist/index.js"
  }
}
```

ライブラリ開発や Node.js 実行環境では特に重要です。

ES Modules なのか CommonJS なのか、どこが入口なのかを確認します。

## 6. overrides を見る

```json
{
  "overrides": {
    "some-package": "1.2.3"
  }
}
```

`overrides` がある場合は、なぜ上書きしているのかを確認した方がよいです。

脆弱性対応なのか、バグ回避なのか、古い一時対応が残っているのかで、扱いが変わります。

# よくある疑問

## dependencies と devDependencies は間違えるとどうなる？

すぐに壊れないこともあります。

ただし、環境によっては問題になります。

例えば、本番環境で `npm install --omit=dev` している場合、`devDependencies` はインストールされません。

その状態で本番起動に必要なパッケージが `devDependencies` に入っていると、起動時にエラーになります。

逆に、開発時にしか使わないものを `dependencies` に入れると、本番側の依存が増える可能性があります。

## ^ と ~ は何が違う？

かなりざっくり言うと、許可する更新範囲が違います。

```json
{
  "dependencies": {
    "foo": "^1.2.3",
    "bar": "~1.2.3"
  }
}
```

一般的には次のようなイメージです。

| 指定 | ざっくりした意味 |
| --- | --- |
| `^1.2.3` | 互換性がある範囲で minor / patch 更新を許可 |
| `~1.2.3` | patch 更新を中心に許可 |
| `1.2.3` | 完全固定 |

ただし、`0.x` 系では挙動の感覚が変わるため注意が必要です。

厳密には semver のルールを確認するのが安全です。

## overrides は積極的に使ってよい？

基本的には、必要なときだけ使うのがよいです。

特に脆弱性対応では便利ですが、根本対応ではない場合もあります。

理想は、依存しているライブラリ自体をアップデートして、自然に安全なバージョンへ上がることです。

ただ、実務ではすぐに上げられないこともあります。

そのときの一時対応として `overrides` は有効です。

# まとめ

`package.json` は、単なる依存関係の一覧ではありません。

プロジェクトの構成、開発コマンド、依存関係、実行環境、公開設定、モジュール形式などが集まった重要な設定ファイルです。

特に実務では、次の項目を読めるようになるとかなり楽になります。

| 項目 | 見るポイント |
| --- | --- |
| `scripts` | 起動、ビルド、テスト、Lint の方法 |
| `dependencies` | 実行時に必要な依存関係 |
| `devDependencies` | 開発時に必要な依存関係 |
| `peerDependencies` | 利用側に求める依存関係 |
| `overrides` | 依存関係ツリーの上書き |
| `engines` | 想定 Node.js / npm バージョン |
| `packageManager` | 想定パッケージマネージャ |
| `type` | `.js` を ESM / CJS のどちらで扱うか |
| `main` | パッケージの入口 |
| `exports` | 外部に公開する入口 |
| `files` | npm 公開時に含めるファイル |
| `workspaces` | monorepo のパッケージ管理 |

最初は全部を完璧に覚える必要はありません。

ただ、`package.json` を見たときに「このプロジェクトは何を使っていて、どう動かすのか」が読めるようになると、エラー調査や環境構築がかなり楽になります。

特に `peerDependencies` と `overrides` は、依存関係のエラーや脆弱性対応で実務上よく出てきます。

`package.json` は、なんとなく眺めるファイルではなく、プロジェクトを理解するための入口として読むとかなり役に立ちます。
