`constructor` は、`new` でインスタンスを作るときに呼ばれる特別なメソッドです。

主な役割は、引数を受け取り、インスタンスが利用可能な状態になるよう初期化することです。

## 基本形

```ts
class User {
  readonly name: string;
  private active = true;

  constructor(name: string) {
    const normalizedName = name.trim();

    if (normalizedName === "") {
      throw new Error("name is required");
    }

    this.name = normalizedName;
  }

  deactivate(): void {
    this.active = false;
  }
}

const user = new User(" Taro ");
console.log(user.name); // Taro
```

`constructor` の中の `this` は、生成中のインスタンスを指します。

constructorの実行が正常に終わった時点で、そのインスタンスがクラスの前提条件を満たすようにします。

## constructorを省略した場合

基底クラスでconstructorを省略すると、引数を取らない空のconstructorがあるように動作します。

```js
class User {}

const user = new User();
```

派生クラスで省略した場合は、引数を基底クラスへ渡すデフォルトconstructorが使われます。

```js
class Admin extends User {
  // constructor(...args) {
  //   super(...args);
  // }
}
```

## TypeScriptのparameter properties

TypeScriptでは、constructor引数にアクセス修飾子などを付けると、プロパティ宣言と代入をまとめられます。

```ts
class User {
  constructor(
    public readonly name: string,
    private age: number,
  ) {}

  isAdult(): boolean {
    return this.age >= 18;
  }
}
```

これは簡潔ですが、引数の変換や検証が必要なら、明示的にプロパティへ代入する方が読みやすいことがあります。

## class fieldとの実行順序

基底クラスでは、インスタンスフィールドの初期化後にconstructor本体が実行されます。

```js
class Counter {
  count = 0;

  constructor(initialCount) {
    this.count = initialCount;
  }
}
```

派生クラスのフィールドは `super()` が戻った後に初期化されます。継承とフィールド初期化の順序へ依存する設計は追いにくいため、基底constructorからオーバーライド可能なメソッドを呼ぶことは避けるのが安全です。

## 継承時のconstructor

```ts
class User {
  constructor(public readonly name: string) {}
}

class Admin extends User {
  constructor(
    name: string,
    public readonly permissions: readonly string[],
  ) {
    super(name);
  }
}
```

派生クラスでは、`this` を使う前に `super()` を呼びます。

`super(name)` は基底クラスのconstructorを実行し、基底クラス側の初期化を担当します。

## constructorで避けたい処理

### 非同期初期化

constructorは `async` にできません。通信やファイル読み込みが必要なら、static factory methodへ分離します。

```ts
type UserData = {
  id: number;
  name: string;
};

class User {
  private constructor(
    readonly id: number,
    readonly name: string,
  ) {}

  static async load(id: number): Promise<User> {
    const response = await fetch(`/api/users/${id}`);

    if (!response.ok) {
      throw new Error(`failed to load user: ${response.status}`);
    }

    const data: UserData = await response.json();
    return new User(data.id, data.name);
  }
}
```

### 大きな副作用

constructor内でDOM操作、イベント登録、ログイン、複数の外部通信などを始めると、`new` しただけで何が起きるか予測しにくくなります。

必要なら、次のように責務を分けます。

- constructor：値の検証と代入
- factory：依存の取得と生成手順
- `start` / `dispose`：明示的なライフサイクル

### 多すぎる依存

```ts
class ReportService {
  constructor(
    private readonly repository: ReportRepository,
    private readonly logger: Logger,
  ) {}
}
```

依存をconstructorで明示すること自体は有用です。ただし引数が増え続ける場合は、そのクラスが複数の責務を持っていないかを見直します。

## 戻り値を書かない

JavaScriptのconstructorには特殊な戻り値規則がありますが、通常は別オブジェクトを `return` しません。

生成結果を条件によって変えたい場合は、factory functionやstatic factory methodの方が意図を伝えやすくなります。

## 良いconstructorの判断基準

- 完了後のインスタンスが常に利用可能か
- 必須値が引数から分かるか
- 不正な値を早い段階で拒否できるか
- 外部I/Oや大きな副作用を始めていないか
- 初期化以外の責務を抱えていないか

## まとめ

constructorは「最初に何でも行う場所」ではありません。

- 必須値を受け取る
- 値を検証・正規化する
- インスタンスの前提条件を成立させる

非同期処理や複雑な生成手順はfactoryへ、開始と終了がある処理は明示的なメソッドへ分けると、クラスの使い方が予測しやすくなります。
