`constructor` は、クラスから作られるオブジェクトを「使い始めてもよい状態」にするための入口です。引数をプロパティへコピーするだけの場所ではありません。必要な値を受け取り、検証と正規化を行い、そのクラスが約束する不変条件を成立させるのが中心的な責務です。

先に設計上の結論をまとめます。

- 正常に生成できたインスタンスは、追加設定なしですぐ使える状態にする
- 必須の依存や値は引数で明示し、不正な入力は生成時点で拒否する
- ネットワークやファイルなどの非同期処理は、`constructor` ではなくファクトリへ分ける
- ログ送信やイベント登録のような、生成以外の副作用を詰め込まない
- 継承する場合は `super()` とフィールド初期化の順序を理解し、オーバーライド可能なメソッドを呼ばない

この記事は、こうした「初期化責務の設計」に焦点を当てます。`new` 演算子が内部で何をするか、prototype chainがどう構成されるか、エンジンがオブジェクトをどう配置するかは、それぞれ別の論点です。

## 最小例から初期化の責務を考える

まず、名前とメールアドレスを持つユーザーをTypeScriptで表します。

```ts
class User {
  readonly name: string;
  readonly email: string;

  constructor(name: string, email: string) {
    this.name = name;
    this.email = email;
  }
}

const user = new User("Taro", "taro@example.com");
console.log(user.name); // Taro
```

このコードは動きますが、空白だけの名前や大文字を含むメールアドレスも受け入れます。利用側が毎回チェックしなければならず、`User` がどの状態なら正しいのか分かりません。

そこで、生成時に不変条件を成立させます。不変条件とは、「そのオブジェクトが存在している間、常に守られるべきルール」です。ここでは、名前が空ではないことと、メールアドレスが正規化済みであることを約束します。

```ts
class User {
  readonly name: string;
  readonly email: string;

  constructor(name: string, email: string) {
    const normalizedName = name.trim();
    const normalizedEmail = email.trim().toLowerCase();

    if (normalizedName.length === 0) {
      throw new Error("name must not be empty");
    }
    if (!normalizedEmail.includes("@")) {
      throw new Error("email must contain @");
    }

    this.name = normalizedName;
    this.email = normalizedEmail;
  }
}

const user = new User("  Taro  ", " TARO@EXAMPLE.COM ");
console.log(user); // User { name: 'Taro', email: 'taro@example.com' }
```

これで、生成後のコードは「名前が空かもしれない」と疑う必要がありません。ただし、例のメール検証は仕組みを示すための最小実装です。実務では要件に応じた検証ライブラリや、確認メールを含む業務フローを使います。複雑な正規表現をconstructorへ埋め込むことが目的ではありません。

## 正常終了した時点で利用可能にする

良いconstructorは、正常に終了したか、例外を投げてインスタンスを外へ出さないかのどちらかです。「生成には成功したが、まだ使えない」という中間状態をできるだけ作りません。

次の設計では、`setRepository` を呼び忘れると実行時に失敗します。

```ts
interface TaskRepository {
  save(title: string): Promise<void>;
}

class TaskService {
  private repository?: TaskRepository;

  setRepository(repository: TaskRepository): void {
    this.repository = repository;
  }

  async create(title: string): Promise<void> {
    if (!this.repository) {
      throw new Error("repository is not configured");
    }
    await this.repository.save(title);
  }
}
```

repositoryが必須なら、constructorで要求した方が安全です。型からも必須であることが読み取れ、未設定状態そのものを表現しなくて済みます。

```ts
class TaskService {
  constructor(private readonly repository: TaskRepository) {}

  async create(title: string): Promise<void> {
    await this.repository.save(title.trim());
  }
}
```

一方、本当に後から任意設定できる機能なら、optionalな状態にも意味があります。たとえば監査ログを無効にできる場合は、既定実装を渡す、オプション引数にする、別メソッドに分ける、といった選択肢があります。「setterは悪い」と暗記するのではなく、未設定状態がドメイン上有効かで判断します。

## フィールド初期化とconstructor本体の順序

public class fieldは、constructor本体と無関係に見えても初期化順序があります。基底クラスでは、インスタンスフィールドを初期化してからconstructor本体を実行します。

```js
class Counter {
  count = 0;

  constructor(initialCount) {
    console.log(this.count); // 0
    this.count = initialCount;
  }
}

console.log(new Counter(5).count); // 5
```

そのため、フィールド初期値へ代入した値をconstructorで上書きできます。逆に、constructorで先に代入してからfield initializerが上書きする、と考えるのは誤りです。

初期化式は上から評価され、先に宣言されたフィールドを参照できます。

```js
class Rectangle {
  width = 2;
  height = 3;
  area = this.width * this.height;
}

console.log(new Rectangle().area); // 6
```

ただし、後に宣言したフィールドへ依存すると、その時点では未初期化です。宣言順に意味を持たせすぎると保守しづらいため、複数値から導出できる値はgetterにする判断も有効です。

```ts
class Rectangle {
  constructor(
    readonly width: number,
    readonly height: number,
  ) {}

  get area(): number {
    return this.width * this.height;
  }
}
```

getterなら元の値と食い違うキャッシュを持ちません。計算が高価でなく、毎回最新値を求めたい場合に向いています。

## TypeScriptのparameter propertiesを使い分ける

TypeScriptでは、constructor引数へ `public`、`protected`、`private`、`readonly` のいずれかを付けると、プロパティ宣言と代入を短く書けます。

```ts
class Point {
  constructor(
    public readonly x: number,
    public readonly y: number,
  ) {}

  distanceFromOrigin(): number {
    return Math.hypot(this.x, this.y);
  }
}
```

これは簡潔ですが、constructorの引数とインスタンスの公開APIが同じ行に現れます。引数の正規化、複数値からの導出、コメントの付与が必要なら、明示的なプロパティ宣言の方が読みやすくなります。

また、TypeScriptの `private` と `readonly` は、通常は型検査上の制約です。コンパイル後のJavaScriptで完全な秘匿や凍結を保証するものではありません。実行時にも外部アクセスを拒否したいなら `#privateField`、オブジェクトの変更まで防ぎたいなら `Object.freeze` など、目的に合う仕組みを選びます。

```ts
class ApiKey {
  #value: string;

  constructor(value: string) {
    if (value.length < 16) {
      throw new Error("API key is too short");
    }
    this.#value = value;
  }

  matches(candidate: string): boolean {
    return this.#value === candidate;
  }
}
```

短い記法を使うかどうかより、公開したい状態と隠したい状態を先に決めることが重要です。

## 引数が増えたらオプションオブジェクトを検討する

同じ型の引数が並ぶconstructorは、呼び出し側で意味を取り違えやすくなります。

```ts
class RetryPolicy {
  constructor(
    readonly maxAttempts: number,
    readonly initialDelayMs: number,
    readonly maxDelayMs: number,
  ) {}
}

const policy = new RetryPolicy(3, 100, 5_000);
```

引数が今後増える、任意項目がある、同じプリミティブ型が並ぶ、といった場合はオプションオブジェクトが有効です。

```ts
type RetryPolicyOptions = {
  maxAttempts: number;
  initialDelayMs?: number;
  maxDelayMs?: number;
};

class RetryPolicy {
  readonly maxAttempts: number;
  readonly initialDelayMs: number;
  readonly maxDelayMs: number;

  constructor(options: RetryPolicyOptions) {
    if (!Number.isInteger(options.maxAttempts) || options.maxAttempts < 1) {
      throw new RangeError("maxAttempts must be a positive integer");
    }

    this.maxAttempts = options.maxAttempts;
    this.initialDelayMs = options.initialDelayMs ?? 100;
    this.maxDelayMs = options.maxDelayMs ?? 10_000;

    if (this.initialDelayMs > this.maxDelayMs) {
      throw new RangeError("initialDelayMs must not exceed maxDelayMs");
    }
  }
}

const policy = new RetryPolicy({
  maxAttempts: 3,
  maxDelayMs: 5_000,
});
```

呼び出しが自己説明的になり、既定値も一か所に集まります。ただし、必須引数が一つだけの小さな値オブジェクトまで一律にオブジェクト化すると冗長です。引数の数ではなく、読み違いと変更の可能性で選びます。

既定値を扱うときは、未指定と不正値を混同しません。`options.timeoutMs || 1000` は `0`、`NaN`、空文字まで未指定として扱います。`0` に「待たない」という意味があるなら、`options.timeoutMs ?? 1000` で `null` と `undefined` だけを既定値へ置き換え、その後に許容範囲を検証します。constructorの既定値は入力エラーを隠すためではなく、省略可能な契約を明示するために使います。

## mutableな入力の所有権を決める

配列、Map、Date、通常オブジェクトは参照として渡されます。constructorでそのまま保持すると、呼び出し側が後から変更した内容がインスタンスへ反映されます。

```ts
class Team {
  constructor(readonly members: string[]) {}
}

const members = ["Taro"];
const team = new Team(members);

members.push("Hanako");
console.log(team.members); // ["Taro", "Hanako"]
```

`readonly members` が禁止するのは、TypeScript上で `team.members` へ別の配列を再代入することです。配列の中身を不変にする保証ではありません。Teamが独立したsnapshotを所有すべきなら、constructor境界でcopyし、公開型もreadonlyにします。

```ts
class Team {
  readonly members: readonly string[];

  constructor(members: Iterable<string>) {
    this.members = [...members];
  }
}

const source = ["Taro"];
const team = new Team(source);
source.push("Hanako");

console.log(team.members); // ["Taro"]
```

これで配列自体は分離されますが、要素がmutable objectならshallow copyにすぎません。すべてを無条件にdeep copyすると、class instance、循環参照、大きなデータで別の問題が生じます。入力をimmutable valueとして契約する、必要なprimitiveだけを取り出す、所有権を移すことをdocument化する、という方法から選びます。

```ts
type MemberInput = {
  id: string;
  displayName: string;
};

type Member = Readonly<{
  id: string;
  displayName: string;
}>;

class Team {
  readonly members: readonly Member[];

  constructor(inputs: readonly MemberInput[]) {
    this.members = inputs.map((input) => ({
      id: input.id,
      displayName: input.displayName.trim(),
    }));
  }
}
```

外部オブジェクトを丸ごと保持せず、classが必要な値だけを新しいオブジェクトへ写しています。constructorは値の検証だけでなく、「生成後の状態を誰が変更できるか」を決める境界でもあります。

Dateにも同じ注意が必要です。`Readonly<Date>` と型付けしても、`setTime` などDate自身のmethodによる変更を実行時に止めません。時刻を不変値として保持したいなら、epoch millisecondsをnumberで保存し、外へ返すときに新しいDateを作る方法が明確です。

```ts
class ScheduledEvent {
  readonly #startsAtMs: number;

  constructor(startsAt: Date) {
    const time = startsAt.getTime();
    if (Number.isNaN(time)) {
      throw new RangeError("startsAt must be a valid date");
    }
    this.#startsAtMs = time;
  }

  get startsAt(): Date {
    return new Date(this.#startsAtMs);
  }
}
```

この設計なら、引数のDateを後から変更してもScheduledEventは変わらず、getterの戻り値を変更しても内部状態へ影響しません。copy costと必要な不変性のバランスを、データの大きさと利用範囲に応じて決めます。

## 継承ではsuperより先にthisを使えない

派生クラスに明示的なconstructorを書く場合、`this` を参照する前に `super()` を呼びます。基底クラスの初期化によって、派生インスタンスで使う `this` が得られるためです。

```ts
class User {
  constructor(public readonly name: string) {
    if (name.trim() === "") {
      throw new Error("name must not be empty");
    }
  }
}

class Admin extends User {
  readonly permissions: ReadonlySet<string>;

  constructor(name: string, permissions: Iterable<string>) {
    super(name);
    this.permissions = new Set(permissions);
  }
}

const admin = new Admin("Taro", ["user:read"]);
console.log(admin.permissions.has("user:read")); // true
```

派生クラスでは、`super()` が戻った後に派生側のインスタンスフィールドが初期化され、その後にconstructor本体の残りが進みます。フィールド初期値とconstructor代入が競合しないよう、どちらで値を決めるか統一すると安全です。

もう一つ重要なのは、基底constructorからオーバーライド可能なメソッドを呼ばないことです。

```ts
class BaseReport {
  constructor() {
    this.initialize();
  }

  protected initialize(): void {}
}

class SalesReport extends BaseReport {
  private rows: string[] = [];

  protected initialize(): void {
    this.rows.push("header");
  }
}
```

`super()` の実行中に派生側の `initialize` が呼ばれますが、その時点では `rows` のフィールド初期化がまだ終わっていません。結果は `TypeError` です。初期化順序に依存するフックではなく、生成後に明示的なメソッドを呼ぶか、必要な値を基底constructorへ渡します。

## 非同期処理はstatic factoryへ分離する

JavaScriptのconstructorを `async` にすることはできません。さらに、生成時にHTTP通信やファイル読込を隠すと、失敗条件や待ち時間が呼び出し側から見えにくくなります。

非同期に取得した値が必要なら、同期的な初期化と非同期な取得を分けます。

```ts
type UserResponse = {
  id: number;
  name: string;
};

class RemoteUser {
  private constructor(
    readonly id: number,
    readonly name: string,
  ) {}

  static async load(id: number): Promise<RemoteUser> {
    const response = await fetch(`https://example.com/users/${id}`);
    if (!response.ok) {
      throw new Error(`failed to load user: ${response.status}`);
    }

    const data = (await response.json()) as UserResponse;
    return new RemoteUser(data.id, data.name.trim());
  }
}
```

`RemoteUser.load` はPromiseを返すため、非同期であることが型と呼び出し方に現れます。なお、レスポンスの型アサーションは実行時検証ではありません。信頼できないJSONならスキーマライブラリなどで検証してからconstructorへ渡します。

生成方法が複数ある場合にもnamed factoryは役立ちます。`Duration.fromSeconds(5)` と `Duration.fromMilliseconds(5000)` のように、引数の単位や意図を名前で表せます。ただし、単一の明白な生成方法しかないなら、公開constructorの方が単純です。

## constructorへ副作用を詰め込まない

constructor内で次の処理を始めると、生成と同時に外部状態が変わります。

- DOMイベントやメッセージブローカーへの購読
- タイマーやバックグラウンド処理の開始
- データベース更新やHTTP送信
- ファイル作成やグローバルな登録

この設計ではテストが難しく、途中で失敗した場合の後始末も曖昧です。constructorは依存と初期状態の保持にとどめ、開始と終了を対にしたメソッドへ分けるとライフサイクルが見えます。

```ts
interface Subscription {
  unsubscribe(): void;
}

interface EventSource {
  subscribe(listener: (message: string) => void): Subscription;
}

class MessageWatcher {
  #subscription?: Subscription;

  constructor(private readonly source: EventSource) {}

  start(): void {
    if (this.#subscription) return;
    this.#subscription = this.source.subscribe((message) => {
      console.log(message);
    });
  }

  stop(): void {
    this.#subscription?.unsubscribe();
    this.#subscription = undefined;
  }
}
```

二重開始をどう扱うか、停止後に再開できるか、といった状態遷移もAPIとして設計できます。生成しただけでは副作用が起きないため、テストの準備も容易です。

## 例外とResultをどう選ぶか

constructorで不正な値を検出したとき、例外を投げる方法は簡潔です。設定ミスやプログラミングエラーのように、本来起きるべきでない失敗に適しています。

一方、フォーム入力の不備のように頻繁に起こり、呼び出し側で分岐したい失敗なら、factoryからResult型を返す方が扱いやすいことがあります。

```ts
type Result<T> =
  | { ok: true; value: T }
  | { ok: false; message: string };

class Percentage {
  private constructor(readonly value: number) {}

  static create(value: number): Result<Percentage> {
    if (!Number.isFinite(value) || value < 0 || value > 100) {
      return { ok: false, message: "value must be between 0 and 100" };
    }
    return { ok: true, value: new Percentage(value) };
  }
}
```

例外とResultのどちらが常に優れているわけではありません。失敗が想定内か、呼び出し側が回復できるか、既存コードのエラーモデルと一貫しているかで選びます。

## 初期化契約をテストで確認する

constructorのテストは内部実装ではなく、生成後に守られる約束を確認します。Node.js標準のassertなら追加ライブラリなしで検証できます。

```ts
import assert from "node:assert/strict";

const user = new User("  Taro  ", " TARO@EXAMPLE.COM ");
assert.equal(user.name, "Taro");
assert.equal(user.email, "taro@example.com");

assert.throws(
  () => new User("   ", "taro@example.com"),
  /name must not be empty/,
);
```

境界値、既定値、正規化、失敗時の例外またはResultを確認します。private fieldへ直接アクセスして代入された値を検査するより、公開メソッドが正しく振る舞うことをテストした方が、リファクタリングに強くなります。

## constructorを使わない選択もある

状態と振る舞いをまとめ、複数の操作を通じて不変条件を守りたいならclassは有効です。しかし、値を一度整形するだけなら通常の関数で十分です。

```ts
type UserName = string & { readonly __brand: "UserName" };

function createUserName(value: string): UserName {
  const normalized = value.trim();
  if (normalized === "") {
    throw new Error("name must not be empty");
  }
  return normalized as UserName;
}
```

classを採用すると、constructor、インスタンス、メソッドという概念が増えます。識別子付きの値、クロージャ、オブジェクトリテラルで目的を満たせるなら、それらの方が軽量です。constructorの書き方を工夫する前に、そのクラスが状態と振る舞いをまとめる価値を持つか確認します。

## まとめ

`constructor` の品質は、行数の短さではなく、生成後の状態をどこまで明確に保証できるかで決まります。

- 必須値と必須依存を引数へ出し、正常終了時には利用可能な状態にする
- 入力を検証・正規化し、不変条件を生成境界で成立させる
- field initializer、基底constructor、派生field、派生constructor本体の順序を意識する
- 非同期処理はfactory、副作用を伴う開始と終了は明示的なメソッドへ分ける
- 想定外の失敗は例外、想定内で回復可能な失敗はResultも検討する
- 単純な値変換なら、classではなく関数やオブジェクトリテラルも比較する

constructorを「代入する場所」ではなく「有効なオブジェクトだけを外へ出す境界」と捉えると、利用側の条件分岐が減り、型と実行時の振る舞いが揃ったAPIになります。
