ターミナルで `node` や `git` を入力すると、ファイルの場所を書いていないのにプログラムが起動します。シェルが、実行ファイルを探すディレクトリの一覧を持っているためです。その一覧を保存する環境変数が `PATH` です。

「`PATH` を通す」とは、コマンドの実体があるディレクトリを、その検索先へ追加することです。この仕組みが分かれば、`command not found` を設定のコピペに頼らず切り分けられます。

## コマンド名だけを入力すると、シェルが検索する

たとえば、`node app.js` と実行したとします。

シェルは `node` という名前の実行ファイルを、`PATH` に登録されたディレクトリから左順に探します。最初に見つけたものを実行し、見つからなければ `command not found` を表示します。

```mermaid
flowchart LR
    A[nodeと入力] --> B[/usr/local/binを探す]
    B -- ない --> C[/usr/binを探す]
    C -- 見つけた --> D[/usr/bin/nodeを実行]
    C -- ない --> E[次のディレクトリ]
    E -- 最後までない --> F[command not found]
```

現在の `PATH` は `echo "$PATH"` で確認できます。macOSやLinuxでは、`/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin` のようにディレクトリがコロン `:` で区切られています。

左にあるディレクトリほど優先されます。同名の実行ファイルが複数ある場合、この順序が「どのバージョンが動くか」を決めます。

## `PATH` へ入れるのは実行ファイルではなく、親ディレクトリ

ここが最もよく混同される点です。`/opt/tools/bin/mytool` という実行ファイルをコマンド名 `mytool` で呼びたいなら、`PATH` へ追加するのは `/opt/tools/bin` です。

| 対象 | 例 | `PATH` へ追加するか |
| --- | --- | --- |
| 実行ファイル | `/opt/tools/bin/mytool` | 追加しない |
| 実行ファイルの親ディレクトリ | `/opt/tools/bin` | 追加する |
| コマンド名 | `mytool` | シェルで入力する |

シェルは、各 `PATH` 要素の後ろへコマンド名を付けて候補を作る、と考えると分かりやすくなります。`/opt/tools/bin` と `mytool` から、候補 `/opt/tools/bin/mytool` を組み立てます。

## 実行されるファイルは `command -v` で確認する

コマンドが見つかるか、どの実体を使うかは `command -v` で確認できます。

```sh
command -v node
command -v git
command -v mytool
ls -l "$(command -v node)"
type -a node
```

何も表示されなければ、現在のシェルからそのコマンドは見つかっていません。パスが表示されたら、`ls -l` でそのファイルを確認します。

`which` もよく使われます。ただし、別のコマンド名を置き換えるalias（別名）や、シェル自身が実装する組み込みコマンドまで含めて解決方法を確認するには、POSIXシェルで利用できる `command -v` が扱いやすい選択です。zshの `type -a node` なら、同名候補をまとめて確認できます。

複数バージョンを入れたのに古い方が動く場合は、候補の順序を見てください。

## 一時的な設定と永続設定は目的が違う

現在のターミナルだけで試すなら、`export` します。

```sh
# 現在のシェルだけで試す
export PATH="/opt/tools/bin:$PATH"

# ~/.zshrcへ保存した後に読み直す
source ~/.zshrc

# 現在動いているシェルも確認する
echo "$SHELL"
ps -p $$ -o command=
```

`PATH` の変更は、現在のシェルと、そこから起動した子プロセスにだけ伝わります。ターミナルを閉じれば消えるため、設定が正しいかを安全に試す用途に向いています。

毎回使いたい場合は、利用中のシェルが読み込む設定ファイルへ同じ `export` を追加します。macOSでzshを使っているなら、対話的なターミナルでは一般に `~/.zshrc` が候補です。保存後、新しいターミナルを開くか、上の例のように設定を読み直します。

ただし、どの設定ファイルが読み込まれるかは、シェルの種類と起動方法で変わります。利用者がログインしたときの環境を準備するログインシェルと、ターミナルで入力を受け付ける対話シェルでは、読む設定ファイルが異なる場合があります。GUIアプリから起動した処理も同じ条件とは限りません。まず現在のシェルと起動方法を確認します。

`$SHELL` はログインシェルの設定を示し、現在動いているシェルと一致しない場合があります。実際のプロセスも合わせて見ると確実です。

## `PATH` の追加位置で優先順位が変わる

新しいディレクトリを前へ置くか、後ろへ置くかで意味が変わります。

```sh
# 既存の同名コマンドより優先する
export PATH="/opt/tools/bin:$PATH"

# 既存のコマンドが見つからないときだけ使う
export PATH="$PATH:/opt/tools/bin"
```

バージョン管理ツールやHomebrewのように、特定のバージョンを優先したい場合は前へ置くことがあります。一方、意図せずシステムコマンドを上書きすると、スクリプトや開発環境が別の挙動になる可能性があります。

`PATH` へ追加するときは、「見つかるようにする」だけでなく、「既存の何より優先するか」まで確認してください。

## `command not found` は5段階で切り分ける

確認に使うコマンドを先に並べます。上から順に実行するのではなく、以下の各段階で必要なものを使います。

```sh
ls -l /opt/tools/bin/mytool       # 実体と権限
printf '%s' "$PATH" | tr ':' '\n'  # PATHを1行ずつ表示
source ~/.zshrc                   # 設定を読み直す
chmod +x /opt/tools/bin/mytool    # 必要な場合だけ実行権限を付ける
hash -r                           # シェルの検索cacheを更新
```

### 1. インストールされているか

まず、ツールの実行ファイルが存在するかを確認します。インストール先が分からない場合は、パッケージマネージャーや公式のインストール手順を確認します。`PATH` は、存在しないファイルを作る設定ではありません。

### 2. 実行ファイルの場所を確認する

既知のインストール先を `ls -l /opt/tools/bin/mytool` で見ます。

シンボリックリンクなら、リンク先が存在するかも確認します。

### 3. 親ディレクトリが `PATH` に入っているか

見やすいように1行ずつ表示します。上のコマンドは、コロンを改行へ置き換えて検索先を縦に並べます。zshだけで確認するなら `print -l $path` も使えます。

実行ファイルが `/opt/tools/bin/mytool` なら、一覧で確認する対象は親の `/opt/tools/bin` です。

### 4. 設定が現在のシェルへ読み込まれたか

設定ファイルを編集しても、すでに開いているシェルの環境は自動で変わりません。新しいターミナルを開くか、適切な設定ファイルを読み直します。

設定行を複数ファイルへ重複して書くと、順序を追いにくくなります。どのファイルが責任を持つかを1つに決めます。

### 5. 実行権限とシェルのキャッシュを確認する

ファイルがあっても実行権限がなければ起動できません。`ls -l` で権限を読み、必要な場合だけ `chmod +x` を実行します。シェルが過去の検索結果をキャッシュしている場合は、`hash -r` で再検索させます。

この順で確認すれば、「未インストール」「`PATH` の設定不足」「読み込み忘れ」「権限不足」を混ぜずに切り分けられます。

## `PATH` を壊さないための3つの注意

### 既存の `PATH` を消さない

次の2行は似ていますが、最初の行は既存の検索先をすべて失います。通常は `$PATH` を残します。

```sh
# 避ける
export PATH="/opt/tools/bin"

# 既存の検索先を残す
export PATH="/opt/tools/bin:$PATH"
```

### 信頼できないディレクトリを先頭へ置かない

カレントディレクトリを表す `.` や、誰でも書き込めるディレクトリを `PATH` の先頭へ置くと、正規のコマンドと同名の悪意あるファイルを実行する危険があります。

`PATH` は実行するプログラムを選ぶ信頼境界でもあります。追加するディレクトリの所有者と書き込み権限を確認します。便利さだけで検索先を増やすと、意図しないファイルを優先する危険があります。

### 同じ設定を何度も追加しない

`.zshrc` の複数箇所や、複数の設定ファイルで同じディレクトリを追加すると、`PATH` が長くなり、優先順位を追いにくくなります。バージョン管理ツールが自動設定している場合、手動の追加と競合することもあります。

## Windowsの `Path` も基本の考え方は同じ

Windowsでも、実行ファイルを探すディレクトリ一覧という役割は同じです。主な違いは、区切り文字がセミコロン `;` であることと、設定方法です。

```powershell
$env:Path -split ';'
Get-Command node
```

PowerShellで現在のセッションだけ変更する場合は `$env:Path` を編集します。永続化はWindowsの環境変数設定や適切な管理コマンドを使います。ユーザーの `Path` とシステムの `Path` のどちらへ入れるかも、必要な利用者範囲で決めます。

## 実体・検索先・選択結果の3点を確認する

`PATH` は、シェルがコマンド名から実行ファイルを探すためのディレクトリ一覧です。実行ファイルの親ディレクトリを追加し、一覧の順序でどのバージョンを優先するかを決めます。

問題が起きたら、次の3つを別々に確認してください。

1. 実行ファイルは存在するか。
2. 親ディレクトリが `PATH` に含まれるか。
3. シェルはどの候補を選んでいるか。

この3点が分かれば、`command not found` だけでなく、「インストールしたのに古いバージョンが動く」という問題も同じ仕組みで説明できます。
