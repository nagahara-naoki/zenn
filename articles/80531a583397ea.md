```
zsh: command not found: mytool
```

この一行を見たとき、私が長いことやっていたのは検索でした。「mytool command not found」で調べて、出てきた `export PATH=...` を `.zshrc` に貼る。動くこともあるし、動かないこともある。動いた理由は、結局わからないままでした。

仕組み自体は、たぶん想像より単純です。

ターミナルで `node` と打つと、ファイルの場所を書いていないのにプログラムが起動します。シェルが、実行ファイルを探すディレクトリの一覧を持っているからです。その一覧を入れている環境変数が `PATH` です。

つまり「`PATH` を通す」とは、コマンドの実体があるディレクトリを、その検索先に足すこと。それだけ。ここが分かると、`command not found` をコピペに頼らず切り分けられるようになります。

## シェルは、左から順に探している

`node app.js` と実行したとします。

シェルは `node` という名前の実行ファイルを、`PATH` に登録されたディレクトリから**左順に**探します。最初に見つけたものを実行して、最後まで無ければ `command not found` を出します。

いまの中身は `echo "$PATH"` で見られます。macOSやLinuxなら、`/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin` のようにコロン `:` 区切りで並んでいるはずです。

左が強い。同名の実行ファイルが複数あるとき、この順序が「どのバージョンが動くか」を決めています。

## 追加するのはファイルじゃない、フォルダのほう

ここ、いちばん間違えます。私も間違えました。

`/opt/tools/bin/mytool` を `mytool` で呼びたいとき、`PATH` に足すのは `/opt/tools/bin` です。

| 対象 | 例 | `PATH` へ追加するか |
| --- | --- | --- |
| 実行ファイル | `/opt/tools/bin/mytool` | 追加しない |
| 実行ファイルの親ディレクトリ | `/opt/tools/bin` | 追加する |
| コマンド名 | `mytool` | シェルで入力する |

シェルは、`PATH` の各要素の後ろに打ち込まれたコマンド名をくっつけて候補を作っている。そう考えると腑に落ちます。`/opt/tools/bin` と `mytool` をつないで `/opt/tools/bin/mytool` を組み立てているわけです。

## いま何が動いているか、を見る

見つかっているのか、どの実体が使われているのか。これは推測せず、`command -v` に聞きます。

```sh
command -v node
command -v git
command -v mytool
ls -l "$(command -v node)"
type -a node
```

何も出てこなければ、いまのシェルからそのコマンドは見えていません。パスが出たら `ls -l` で実体を確認します。

`which` もよく使われますね。ただ、別名を張るaliasやシェル自身の組み込みコマンドまで含めて解決方法を知りたいなら、POSIXシェルで使える `command -v` のほうが素直です。zshなら `type -a node` で同名候補をまとめて出せます。

複数バージョンを入れたのに古いほうが動く。そういうときは、候補の順序を見てください。

## その場かぎりか、ずっとか

いまのターミナルだけで試すなら `export` です。

```sh
# 現在のシェルだけで試す
export PATH="/opt/tools/bin:$PATH"

# ~/.zshrcへ保存した後に読み直す
source ~/.zshrc

# 現在動いているシェルも確認する
echo "$SHELL"
ps -p $$ -o command=
```

`PATH` の変更が届く範囲は、いまのシェルと、そこから起動した子プロセスまで。ターミナルを閉じれば消えます。だからこそ、設定が合っているかを安全に試すのに向いています。

毎回使いたくなったら、同じ `export` を設定ファイルへ移します。macOSでzshなら、対話的なターミナルでは `~/.zshrc` が第一候補です。保存したら新しいターミナルを開くか、上のように読み直します。

ただ、ここに落とし穴があります。**どの設定ファイルが読まれるかは、シェルの種類と起動方法で変わります。** ログイン時に環境を用意するログインシェルと、ターミナルで入力を受け付ける対話シェルでは、読むファイルが違うことがある。GUIアプリから起動した処理も、同じ条件とは限りません。

だからまず、いまのシェルと起動方法を確認します。`$SHELL` はログインシェルの設定を指していて、実際に動いているシェルと一致しないことがあるので、プロセスも一緒に見ておくと確実です。

## 前に置くか、後ろに置くか

これは好みではなく、意味が変わります。

```sh
# 既存の同名コマンドより優先する
export PATH="/opt/tools/bin:$PATH"

# 既存のコマンドが見つからないときだけ使う
export PATH="$PATH:/opt/tools/bin"
```

バージョン管理ツールやHomebrewのように、特定のバージョンを優先したいときは前に置きます。ただし、うっかりシステムコマンドを上書きすると、スクリプトや開発環境がまるごと別の挙動になることがあります。

追加するときは「見つかるようにする」だけでなく、**既存の何より優先するのか**まで決めてください。

## 5段階で切り分ける

使うコマンドを先に並べます。上から順に全部叩くのではなく、各段階で必要なものだけ使ってください。

```sh
ls -l /opt/tools/bin/mytool       # 実体と権限
printf '%s' "$PATH" | tr ':' '\n'  # PATHを1行ずつ表示
source ~/.zshrc                   # 設定を読み直す
chmod +x /opt/tools/bin/mytool    # 必要な場合だけ実行権限を付ける
hash -r                           # シェルの検索cacheを更新
```

### 1. そもそも入っているか

まず実行ファイルが存在するか。インストール先が分からなければ、パッケージマネージャーや公式手順を確認します。

`PATH` は、無いファイルを生み出す魔法ではありません。

### 2. 場所を押さえる

`ls -l /opt/tools/bin/mytool` で見ます。シンボリックリンクだったら、リンク先が生きているかも確認してください。

### 3. 親ディレクトリが一覧にあるか

コロンを改行に置き換えて、縦に並べると読みやすくなります。zshだけなら `print -l $path` でも見られます。

実行ファイルが `/opt/tools/bin/mytool` なら、探すのは親の `/opt/tools/bin` のほうです。

### 4. その設定、いまのシェルに届いているか

設定ファイルを編集しても、すでに開いているシェルの環境は勝手に変わりません。新しいターミナルを開くか、設定を読み直します。

あと、同じ設定行をあちこちのファイルに書かないこと。責任を持つファイルを1つに決めます。

### 5. 権限とキャッシュ

ファイルがあっても、実行権限がなければ起動しません。`ls -l` で権限を読んで、必要なときだけ `chmod +x` します。シェルが過去の検索結果を覚えている場合は、`hash -r` で探し直させます。

この順に見れば、「未インストール」「`PATH` 不足」「読み込み忘れ」「権限不足」をごちゃ混ぜにせずに済みます。

## `PATH` を壊さないために

### 既存の `PATH` を消さない

次の2行、見た目は似ています。でも上の行は、既存の検索先を全部捨てています。

```sh
# 避ける
export PATH="/opt/tools/bin"

# 既存の検索先を残す
export PATH="/opt/tools/bin:$PATH"
```

`$PATH` を残す。基本はこれです。

### 信頼できない場所を先頭に置かない

カレントディレクトリを表す `.` や、誰でも書き込めるディレクトリを先頭に置くと、正規のコマンドと同じ名前の悪意あるファイルを実行してしまう危険があります。

`PATH` は、実行するプログラムを選ぶ信頼境界でもあります。追加するディレクトリの所有者と書き込み権限は確認してください。便利さだけで検索先を増やすのは、けっこう危ない行為です。

### 同じ設定を何度も足さない

`.zshrc` の複数箇所や、複数の設定ファイルで同じディレクトリを追加すると、`PATH` がどんどん長くなって優先順位が読めなくなります。バージョン管理ツールが自動で設定していると、手動の追加とぶつかることもあります。

## Windowsも、考え方は同じ

実行ファイルを探すディレクトリ一覧、という役割は変わりません。違うのは区切り文字がセミコロン `;` であることと、設定方法くらいです。

```powershell
$env:Path -split ';'
Get-Command node
```

PowerShellでそのセッションだけ変えるなら `$env:Path` を編集します。永続化はWindowsの環境変数設定や管理コマンドを使います。ユーザーの `Path` とシステムの `Path`、どちらに入れるかは必要な利用者の範囲で決めてください。

---

冒頭のコピペに戻ります。あれで直ることがあったのは、たまたま自分の状況と記事の状況が一致していたからでした。

見るべきは3つだけです。

1. 実行ファイルは存在するか。
2. 親ディレクトリが `PATH` に含まれるか。
3. シェルはどの候補を選んでいるか。

この3点を別々に確認できるようになると、`command not found` だけでなく、「インストールしたのに古いバージョンが動く」という気持ち悪い現象まで、同じ仕組みで説明がつきます。
