`console.log` は便利ですが、値を無秩序に出すだけでは原因調査が難しくなります。

重要なのはメソッドを暗記することではなく、次の順序で観測することです。

1. どの処理を通ったか
2. 入力は何だったか
3. どの時点で期待値とずれたか
4. エラーや処理時間に特徴があるか

## 調査できるログにする

次のログは、対象が増えると見分けづらくなります。

```js
console.log(user);
console.log(result);
```

処理名と識別子を含めます。

```js
console.log("[checkout] start", {
  userId: user.id,
  itemCount: cart.items.length,
});
```

オブジェクト形式にすると、DevTools上でプロパティを確認しやすくなります。

本番の構造化ログでは文字列化されることもあるため、ブラウザーconsoleの見え方とサーバーロガーの出力仕様は区別します。

## 主なconsoleメソッド

| メソッド | 向いている用途 |
| --- | --- |
| `console.log` / `info` | 通常の観測情報 |
| `console.warn` | 継続できるが確認が必要な状態 |
| `console.error` | 失敗や例外 |
| `console.table` | 同じ形の配列・オブジェクト |
| `console.group` | 関連ログのまとまり |
| `console.time` | 区間の簡易計測 |
| `console.count` | 呼び出し回数 |
| `console.trace` | 呼び出し経路 |
| `console.assert` | 条件を満たさないときだけ出力 |

ブラウザーや実行環境によって、表示方法や対応状況は異なります。console APIはJavaScript言語仕様ではなく、実行環境が提供するAPIです。

## console.tableで一覧を比較する

```js
const users = [
  { id: 1, name: "Taro", active: true },
  { id: 2, name: "Hanako", active: false },
];

console.table(users, ["id", "name", "active"]);
```

配列要素を1件ずつ `console.log` するより、欠損や値の違いを確認しやすくなります。

大量データをそのまま出すとDevToolsが重くなるため、必要な件数・列へ絞ります。

## groupで1回の処理をまとめる

```js
function logRequest(requestId, request, response) {
  console.groupCollapsed(`[request] ${requestId}`);
  console.log("input", request);
  console.log("output", response);
  console.groupEnd();
}
```

並行する複数処理では、groupだけでなくrequest IDなどの相関IDを全ログへ含めることが重要です。

## timeで遅い区間を絞る

```js
console.time("load-dashboard");

const [user, notifications] = await Promise.all([
  fetchUser(),
  fetchNotifications(),
]);

console.timeEnd("load-dashboard");
```

`console.time` は調査の入口には便利ですが、厳密なベンチマークではありません。

- DevToolsを開いている影響
- ネットワークやキャッシュのばらつき
- JavaScriptエンジンのウォームアップ
- 他処理の影響

性能判断ではPerformance API、DevTools Performance panel、複数回の計測を使います。

## countで予想外の再実行を見つける

```js
function renderList(items) {
  console.count("renderList");
  // render
}
```

`console.countReset("renderList")` で同じlabelのcountをリセットできます。

UIの再レンダーやevent handlerの多重登録を調べるときに役立ちます。ただし回数が多いこと自体が問題とは限らないため、期待する回数と比較します。

## traceで呼び出し元を調べる

```js
function updateState(nextState) {
  console.trace("updateState called", nextState);
}
```

同じ関数が複数経路から呼ばれ、どこから予想外の更新が来たか分からない場合に使えます。

通常はdebuggerのcall stackの方が、変数も含めて詳しく調べられます。

## assertで前提条件を観測する

```js
console.assert(
  cart.items.length > 0,
  "[checkout] cart must not be empty",
  { cartId: cart.id },
);
```

`console.assert` は通常、処理を停止しません。入力検証や不変条件を保証したい場合は、例外や型、validationを使います。

## エラーオブジェクトを保つ

```js
try {
  await saveOrder(order);
} catch (error) {
  console.error("[order] save failed", {
    orderId: order.id,
    error,
  });
  throw error;
}
```

`error.message` だけにするとstackやcauseを失うことがあります。使用するロガーがErrorをどうserializeするか確認します。

回復できないエラーをログだけ出して握りつぶすと、呼び出し側は成功したと誤認します。ログ出力とエラー処理は別の責務です。

## オブジェクト表示の注意

ブラウザーDevToolsは、オブジェクトを展開した時点の状態を遅延表示することがあります。

```js
const state = { count: 0 };
console.log(state);
state.count = 1;
```

「ログを呼んだ瞬間のスナップショット」が必要なら、必要なプリミティブ値だけ出すか、対象に応じてコピーします。

```js
console.log({ count: state.count });
```

`JSON.stringify` は循環参照、BigInt、`undefined`、関数などをそのまま表せず、クラス情報も失うため、万能なスナップショット方法ではありません。

## consoleだけで調べない

ログを増やす前に、目的に合うDevTools機能も使います。

- Sources：breakpoint、step実行、watch、call stack
- Network：リクエスト、status、payload、timing
- Performance：長いtask、rendering、CPU使用
- Memory：heap snapshot、保持参照
- Elements：DOM、computed style、event listener

「値が違う」ならbreakpoint、「通信結果が違う」ならNetwork、「遅い」ならPerformanceというように、観測手段を選びます。

## 本番ログの注意

- token、password、cookie、個人情報を出さない
- 大きなresponse全体を出さない
- 同じエラーを多重に記録しない
- `console.log` が残っているだけで機械的に障害と考えない
- 必要な本番ログは専用ロガーへ集約し、levelと送信先を管理する

ログ削除をビルドツールに任せる場合、`console.error` など必要な観測まで消えないかを確認します。

## まとめ

良いデバッグログには、次の情報があります。

- 処理名
- 対象を識別するID
- 観測した入力・状態
- 失敗した段階
- 必要ならErrorと処理時間

consoleメソッドを増やすことより、「仮説を立て、最小限の観測でずれた地点を特定する」ことが重要です。
