JavaScriptのprototypeは、オブジェクトが別のオブジェクトへ処理を委譲する仕組みです。あるプロパティが自身に存在しなければ、内部リンク `[[Prototype]]` の先を調べ、最終的に `null` へ到達するまで探索します。この連鎖がprototype chainです。

先に実務上の結論をまとめます。

- 継承プロパティを含む参照には `in`、自分自身のプロパティ確認には `Object.hasOwn` を使う
- `Constructor.prototype` と、インスタンスの `[[Prototype]]` は別の概念として区別する
- classの通常メソッドはprototype上に一つ置かれ、インスタンス間で共有される
- 代入、getter、setterでは「見つかった場所」と「処理対象のthis」が異なることがある
- 実行中の `Object.setPrototypeOf` や共有prototypeへの変更は、予測しづらさと最適化上の不利を招くため避ける
- 外部入力をキーとして持つ辞書には、`Map` やnull prototype objectも検討する

この記事はプロパティ探索と共有の仕組みに集中します。`new` の戻り値規則、constructorの設計、V8のメモリ表現は別の層です。

## Object.createで最小構造を見る

classを使わず、prototype chainだけを作ると仕組みが見えやすくなります。

```js
const animal = {
  eat() {
    return `${this.name} eats`;
  },
};

const dog = Object.create(animal);
dog.name = "Pochi";

console.log(dog.name);  // Pochi
console.log(dog.eat()); // Pochi eats
```

`dog` 自身が持つのは `name` だけです。`eat` を読むとき、エンジンは `dog` で見つけられないため `animal` を調べます。

```text
dog
├─ name: "Pochi"
└─ [[Prototype]] ──> animal
                      ├─ eat: function
                      └─ [[Prototype]] ──> Object.prototype ──> null
```

内部リンクは `Object.getPrototypeOf` で観測できます。

```js
console.log(Object.getPrototypeOf(dog) === animal); // true
console.log(Object.getPrototypeOf(animal) === Object.prototype); // true
```

ここで `dog.eat()` の `this` は、メソッドが保存されている `animal` ではなく、呼び出しの基点になった `dog` です。そのため `eat` 内の `this.name` は `dog.name` を読めます。この「処理をprototypeへ委譲し、対象は元のオブジェクトのまま」という性質がJavaScriptのオブジェクトモデルの中心です。

## .prototypeと[[Prototype]]を区別する

名前が似ている二つを混同すると、classや `new` の説明が難しくなります。

- `[[Prototype]]` は、ほぼすべての通常オブジェクトが内部に持つ別オブジェクトまたは `null` へのリンク
- `.prototype` は、constructorとして使われる関数が通常持つ、名前が `prototype` の通常プロパティ

```js
function User(name) {
  this.name = name;
}

User.prototype.greet = function () {
  return `Hello, ${this.name}`;
};

const user = new User("Taro");

console.log(Object.getPrototypeOf(user) === User.prototype); // true
console.log(Object.getPrototypeOf(User) === Function.prototype); // true
```

一行目はインスタンスとメソッド共有用オブジェクトの関係です。二行目は、`User` という関数オブジェクト自身のprototype chainです。同じ `User` に関係していても、別のリンクを観測しています。

歴史的な `__proto__` accessorでも `[[Prototype]]` を読み書きできますが、新しいコードでは `Object.getPrototypeOf`、`Object.setPrototypeOf`、`Object.create` を使います。オブジェクトリテラル内の `__proto__: value` には特別な構文上の意味もあり、通常プロパティとの混同を増やすためです。

## classメソッドもprototypeで共有される

`class` はprototypeを廃止した仕組みではありません。通常メソッドは `ClassName.prototype` に定義され、各インスタンスから探索されます。

```js
class User {
  constructor(name) {
    this.name = name;
  }

  greet() {
    return `Hello, ${this.name}`;
  }
}

const taro = new User("Taro");
const hanako = new User("Hanako");

console.log(taro.greet === hanako.greet); // true
console.log(taro.greet === User.prototype.greet); // true
console.log(Object.hasOwn(taro, "greet")); // false
```

`name` は個体ごとのown property、`greet` は共有されるprototype propertyです。メソッドをインスタンスごとに作らないため、同じ関数オブジェクトを再利用できます。

class構文で定義したprototype methodは、単純な代入で追加したメソッドとproperty descriptorが異なります。class methodはenumerableではありません。

```js
const descriptor = Object.getOwnPropertyDescriptor(
  User.prototype,
  "greet",
);

console.log(descriptor);
// { value: [Function: greet], writable: true,
//   enumerable: false, configurable: true }
```

そのため、通常の `for...in` でclass methodは列挙されません。関数コンストラクターのprototypeへ代入したプロパティは既定でenumerableになるため、同じ性質にしたい場合は `Object.defineProperty` を使います。

```js
function Item() {}

Object.defineProperty(Item.prototype, "describe", {
  value() {
    return "item";
  },
  writable: true,
  enumerable: false,
  configurable: true,
});
```

## class fieldのアロー関数は共有されない

見た目がメソッドに似ていても、public fieldへアロー関数を代入すると、各インスタンスのown propertyになります。

```js
class Button {
  handleClick = () => {
    console.log(this);
  };
}

const a = new Button();
const b = new Button();

console.log(a.handleClick === b.handleClick); // false
console.log(Object.hasOwn(a, "handleClick")); // true
```

この書き方は、コールバックとして関数だけを渡してもlexical `this` を保持できる利点があります。一方、インスタンスごとに関数を生成し、サブクラスがprototype methodとして通常の `super.handleClick()` を呼ぶ形とも噛み合いません。

標準のmethodとfield arrowのどちらを使うかは、共有そのものより、関数を切り離して渡す必要があるか、継承で上書きしたいか、インスタンス数が多いかで判断します。Reactなど特定のフレームワーク習慣を、すべてのclassへ自動適用する必要はありません。

## プロパティ探索は最初に見つかった場所で止まる

同名のown propertyがあると、prototype側のプロパティは隠れます。これをshadowingと呼びます。

```js
const base = { role: "member" };
const user = Object.create(base);

console.log(user.role); // member

user.role = "admin";
console.log(user.role); // admin
console.log(base.role); // member

delete user.role;
console.log(user.role); // member
```

通常の代入はprototypeのデータプロパティを上書きするのではなく、receiverである `user` にown propertyを作ります。`delete user.role` も `user` 自身だけを対象にし、prototype上の `base.role` は削除しません。

ただし、prototype側のproperty descriptorによって代入結果は変わります。継承したプロパティがwritableではない場合、own propertyは作られません。strict modeでは例外になります。

```js
"use strict";

const base = {};
Object.defineProperty(base, "id", {
  value: 1,
  writable: false,
});

const child = Object.create(base);

try {
  child.id = 2;
} catch (error) {
  console.log(error instanceof TypeError); // true
}

console.log(Object.hasOwn(child, "id")); // false
console.log(child.id); // 1
```

「代入すれば必ずown propertyになる」は近似にすぎません。内部的には `[[Set]]` がprototype chainとdescriptorを調べます。

## getterとsetterではreceiverが重要になる

継承したgetterが実行されるときも、`this` はgetterを保持するprototypeではなく、最初にアクセスしたreceiverです。

```js
const personPrototype = {
  get label() {
    return `${this.firstName} ${this.lastName}`;
  },
};

const person = Object.create(personPrototype);
person.firstName = "Taro";
person.lastName = "Yamada";

console.log(person.label); // Taro Yamada
```

setterがprototype上に見つかると、通常はそのsetterがreceiverを `this` として呼ばれます。

```js
const temperaturePrototype = {
  set celsius(value) {
    this.kelvin = value + 273.15;
  },
};

const temperature = Object.create(temperaturePrototype);
temperature.celsius = 20;

console.log(temperature.kelvin); // 293.15
console.log(Object.hasOwn(temperature, "celsius")); // false
console.log(Object.hasOwn(temperature, "kelvin")); // true
```

setter自体はprototypeに残り、その処理が `temperature.kelvin` を作っています。この仕組みにより、一つのaccessorを複数インスタンスで共有しながら、状態は各インスタンスへ保存できます。

Proxyや `Reflect.get(target, key, receiver)` の第三引数でもreceiverが明示されます。ライブラリ内部でgetterの `this` が予想外になる問題を調べるときは、「どこでプロパティが見つかったか」と「receiverは誰か」を分けると理解しやすくなります。

## 所有、存在、列挙を使い分ける

プロパティを調べるAPIは、似ていても問いが違います。

```js
const settings = Object.create({ theme: "light" });
settings.language = "ja";

console.log("theme" in settings); // true
console.log(Object.hasOwn(settings, "theme")); // false
console.log(Object.hasOwn(settings, "language")); // true
console.log(Object.keys(settings)); // ["language"]
```

使い分けは次のとおりです。

| API | 答える問い |
| --- | --- |
| `key in object` | prototype chainを含め、アクセス可能なプロパティが存在するか |
| `Object.hasOwn(object, key)` | object自身がそのプロパティを持つか |
| `Object.keys(object)` | ownかつenumerableな文字列キーは何か |
| `Object.getOwnPropertyNames(object)` | enumerableでないものも含むown文字列キーは何か |
| `Reflect.ownKeys(object)` | Symbolも含むすべてのown keyは何か |

`object.hasOwnProperty(key)` は、対象が同名メソッドを持つ場合やnull prototype objectの場合に使えません。`Object.hasOwn` なら対象からメソッドを取得しないため安全です。

`for...in` はenumerableな文字列キーをprototype chainまで列挙します。JSONのような入力のown propertyだけを処理したい場面で使うと、意図しない継承プロパティが混ざります。`Object.keys` と `for...of` の組み合わせの方が問いを明示できます。

## null prototype objectとMap

`Object.create(null)` は `[[Prototype]]` がnullのオブジェクトを作ります。`toString` や `constructor` などを継承しないため、純粋な文字列キー辞書として使えます。

```js
const counts = Object.create(null);

counts.apple = 2;
counts.constructor = 1;

console.log(counts.apple); // 2
console.log(counts.constructor); // 1
console.log(Object.getPrototypeOf(counts)); // null
console.log(Object.hasOwn(counts, "toString")); // false
```

ただし、通常のオブジェクト用メソッドを直接呼べず、TypeScriptの型付けやデバッグ表示が扱いにくい場合があります。キーと値の集合を操作したいだけなら `Map` がより明示的です。

```js
const counts = new Map();

counts.set("apple", 2);
counts.set("constructor", 1);

console.log(counts.get("apple")); // 2
console.log(counts.has("toString")); // false
```

JSONへそのまま変換したい、固定形状のレコードとして扱いたいならobject、任意キーの追加削除、サイズ取得、オブジェクトキーが必要ならMap、と役割で選びます。

外部入力のキーを既存オブジェクトへ無制限にマージすると、prototype pollutionの原因になる場合があります。null prototype objectだけであらゆる攻撃を防げるわけではありません。許可するキーの検証、安全なマージ方法、依存ライブラリの更新を組み合わせます。

## 継承は二つのprototype chainを作る

classの `extends` は、インスタンス側とconstructor側の両方に関係を作ります。

```js
class Animal {
  static category = "animal";

  eat() {
    return "eat";
  }
}

class Dog extends Animal {
  bark() {
    return "bow";
  }
}

const dog = new Dog();

console.log(Object.getPrototypeOf(Dog.prototype) === Animal.prototype); // true
console.log(Object.getPrototypeOf(Dog) === Animal); // true
console.log(dog.eat()); // eat
console.log(Dog.category); // animal
```

一つ目のchainによって、`dog` は `Dog.prototype` から `Animal.prototype` へ進み、instance methodを見つけます。二つ目のchainによって、`Dog` というconstructor objectは `Animal` のstatic memberを継承します。

継承を一つの矢印だけで描くと、static側の挙動を説明できません。インスタンスから始まるchainと、class objectから始まるchainを別々に追います。

## instanceofが確認しているもの

通常の `value instanceof Constructor` は、`Constructor.prototype` がvalueのprototype chainに現れるかを調べます。

```js
class User {}

const user = new User();

console.log(user instanceof User); // true
console.log(User.prototype.isPrototypeOf(user)); // true
```

ただし、これは「そのconstructorが確実にvalueを生成した」という履歴の証明ではありません。`Object.create(User.prototype)` でもtrueになり、prototypeを書き換えると結果も変わります。また、iframeなど別realmで作った配列は、現在realmの `Array` に対する `instanceof` がfalseになることがあります。配列の判定には `Array.isArray` が適しています。

classは `Symbol.hasInstance` を定義して判定をカスタマイズできますが、一般的な読者の期待から離れます。ドメインオブジェクトの判定なら、明示的なtag、schema validation、必要な振る舞いを確認する型ガードも比較します。

`user.constructor === User` も確実な判定ではありません。`constructor` は通常prototypeから継承される書き換え可能なプロパティであり、own propertyで隠せるからです。

## 実行中のprototype変更を避ける理由

`Object.setPrototypeOf` で既存オブジェクトの `[[Prototype]]` を変更できますが、通常の設計では避けます。

```js
const object = { name: "Taro" };
const behavior = {
  greet() {
    return `Hello, ${this.name}`;
  },
};

Object.setPrototypeOf(object, behavior);
console.log(object.greet()); // Hello, Taro
```

動作自体は標準ですが、オブジェクトの能力が実行途中で変わり、コードを局所的に読めなくなります。JavaScriptエンジンも、安定した形状とprototypeを前提にプロパティアクセスを最適化するため、変更は既存の最適化を無効化し得ます。

関係が必要なら生成時に `Object.create` またはclassで決めます。既存オブジェクトへ能力を足したいだけなら、委譲先を明示するcompositionも選べます。

```js
function createGreeter(person) {
  return {
    greet() {
      return `Hello, ${person.name}`;
    },
  };
}
```

共有prototypeへのメソッド追加も、すべての既存インスタンスへ即座に見える変更です。polyfillやフレームワーク基盤など目的が明確な場合を除き、組み込みprototypeや他ライブラリのprototypeを拡張しません。

## 動作を検証する

Node.js標準のassertを使うと、所有と継承の違いを小さなテストで確認できます。

```js
import assert from "node:assert/strict";

const base = { enabled: true };
const feature = Object.create(base);
feature.name = "search";

assert.equal(feature.enabled, true);
assert.equal("enabled" in feature, true);
assert.equal(Object.hasOwn(feature, "enabled"), false);
assert.equal(Object.hasOwn(feature, "name"), true);
assert.equal(Object.getPrototypeOf(feature), base);

feature.enabled = false;
assert.equal(feature.enabled, false);
assert.equal(base.enabled, true);

delete feature.enabled;
assert.equal(feature.enabled, true);
```

DevToolsでは `console.dir(object)` からprototypeを展開できます。ただし、コンソールが後からオブジェクトの最新状態を表示する場合もあるため、再現可能な確認にはassertと明示的な標準APIを使います。

## まとめ

prototypeは「古いclass構文」ではなく、JavaScriptのプロパティ参照を支える現在の仕組みです。

- 各オブジェクトの `[[Prototype]]` をたどり、最初に見つかったプロパティを使う
- `Constructor.prototype` は通常プロパティであり、インスタンスの内部リンクとは別物である
- class methodはprototypeで共有され、field arrow functionは各インスタンスのown propertyになる
- 参照・代入・getter・setterでは、プロパティの保管場所とreceiverを区別する
- `in`、`Object.hasOwn`、列挙APIは、それぞれ異なる問いに答える
- null prototype object、Map、compositionは、継承以外の目的に応じた代替になる
- `instanceof` や `constructor` は履歴の絶対的な証明ではない
- prototype関係は生成時に決め、実行途中の変更や組み込みprototypeの拡張を避ける

迷ったときは、対象オブジェクトのown propertyを確認し、`Object.getPrototypeOf` で一段ずつ進み、どのdescriptorが最初に見つかるかを追います。この手順だけで、class、継承、getter、shadowingに関する多くの挙動を説明できます。
