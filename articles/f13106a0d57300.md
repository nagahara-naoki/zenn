`package.json` を開くと、依存パッケージのバージョンに `^` や `~` が付いています。`^1.2.3` を見て「1系の最新版が入る」とだけ覚えると、`0.x`、プレリリース、lockfileが絡んだときに判断を誤ります。

```json
{
  "dependencies": {
    "sample-package": "^1.2.3"
  }
}
```

先に結論を述べると、SemVerとnpmの範囲指定は別の役割です。

- **SemVer**：公開者が変更の互換性を `MAJOR.MINOR.PATCH` で伝える契約。
- **npmのバージョン範囲**：利用者がインストールを許可するバージョン集合。
- **package-lock.json**：あるインストールで実際に解決した依存ツリーの記録。

`^1.2.3` はnpmでは `>=1.2.3 <2.0.0` を意味します。しかし、範囲内なら絶対に安全という保証ではありません。公開者がSemVerを正しく運用していること、利用側のテストが通ること、Node.jsなどの実行条件が合うことまで確認して、初めて更新を採用できます。

この記事では、SemVerの読み方、caretとtilde、`0.x`、プレリリース、lockfile、更新手順、公開者側の判断を一つの流れで整理します。

## SemVerは変更の意味を伝える

Semantic Versioning 2.0.0では、通常バージョンを `MAJOR.MINOR.PATCH` の三つの非負整数で表します。

```text
2.7.4
│ │ └─ PATCH: 4
│ └─── MINOR: 7
└───── MAJOR: 2
```

各番号を上げる基準は、変更量や開発期間ではなく、宣言した公開APIとの互換性です。

| 上げる番号 | 変更の意味 | 例 |
| --- | --- | --- |
| PATCH | 後方互換な不具合修正 | 同じ入力で誤っていた結果を仕様どおりに直す |
| MINOR | 後方互換な機能追加 | 新しい関数や任意オプションを追加する |
| MAJOR | 後方互換でない変更 | APIを削除する、引数の意味を変える |

MINORを上げるとPATCHは0へ、MAJORを上げるとMINORとPATCHは0へ戻します。`1.4.7` へ後方互換な機能を追加するなら `1.5.0`、互換性を壊すなら `2.0.0` です。

SemVerを使うには、何を公開APIとするかを先に宣言する必要があります。JavaScriptライブラリならexportした関数だけとは限りません。型定義、CLIのオプション、設定ファイルの形式、イベント名、エラーの種類、サポートするNode.jsバージョンなども、利用者が依存する契約になり得ます。

```js
// 1.xで公開しているAPI
export function formatPrice(amount, options = {}) {
  const { currency = "JPY", locale = "ja-JP" } = options;
  return new Intl.NumberFormat(locale, {
    style: "currency",
    currency,
  }).format(amount);
}
```

任意オプションの追加はMINOR、引数の型や既定動作の非互換変更、関数の削除はMAJORの候補です。内部を全面的に書き換えても公開契約を保てるならPATCHにできます。SemVerは互換性の機械的な証明ではなく、公開者が変更を分類して利用者へ伝える約束です。

## 0.xは安定版と同じ規則で読まない

SemVer仕様では、メジャーバージョン0は初期開発用で、公開APIは安定しているとみなすべきではなく、いつでも変更され得るとされています。`0.2.0` から `0.3.0` が、`1.2.0` から `1.3.0` と同じ安全性を持つわけではありません。

```text
0.2.3 → 0.2.4  パッケージの運用方針次第では修正扱い
0.2.3 → 0.3.0  破壊的変更を含む可能性が高い
0.9.0 → 1.0.0  公開APIを安定版として宣言する節目
```

「0.xでもPATCHは互換、MINORは破壊的変更を許す」という慣例もありますが、SemVerが保証する規則ではありません。READMEと変更履歴を確認します。公開者も破壊的変更と移行方法を説明し、公開APIが定まったら `1.0.0` を検討します。

## プレリリースとビルドメタデータ

通常バージョンの後ろへハイフンと識別子を付けるとプレリリースになります。プレリリースは、同じ `MAJOR.MINOR.PATCH` の通常版より優先順位が低くなります。

```text
2.0.0-alpha.1
2.0.0-beta.1
2.0.0-rc.1
2.0.0
```

`alpha`、`beta`、`rc` は一般的な命名ですが、品質や本番利用可否は公開者が説明します。

プラス記号以降はビルドメタデータです。バージョンの優先順位比較では無視されます。

```text
1.4.2+build.105
1.4.2+linux.x64
```

ビルドメタデータだけが異なる二つは、SemVer上の優先順位が同じです。配布物の識別には使えても、互換性の段階は表しません。

## npmの範囲は「許可する集合」

SemVerが一つのリリースへ意味を付けるのに対し、npmのrangeはインストールしてよいバージョンの集合を表します。node-semverの規則で、比較演算子の組み合わせへ展開して考えると正確です。

```text
"1.2.3"   = 1.2.3だけ
"~1.2.3"  = >=1.2.3 <1.3.0
"^1.2.3"  = >=1.2.3 <2.0.0
"1.2.x"   = >=1.2.0 <1.3.0
"1.x"     = >=1.0.0 <2.0.0
"*"       = 0.0.0以上（通常はプレリリースを除く）
```

範囲は「次回必ずその最新版へ上げる」という命令ではありません。npmが依存解決を行うときの候補です。すでにlockfileがあり、その内容が `package.json` の範囲を満たしていれば、同じバージョンが使われる場合があります。

範囲を複数の比較で直接書くことも、論理ORで分けることもできます。

```json
{
  "dependencies": {
    "sample-a": ">=1.4.0 <2.0.0",
    "sample-b": "^1.8.0 || ^2.2.0",
    "sample-c": "1.4.0 - 1.9.5"
  }
}
```

複雑な範囲は対応方針を正確に表せますが、許可した境界とテスト対象を説明できる形に留めます。

## tildeは指定したMINOR系列を保つ

三要素を指定した `~1.2.3` は、PATCH更新を許可し、次のMINORは許可しません。

```text
~1.2.3
├─ 1.2.3  利用可能
├─ 1.2.9  利用可能
└─ 1.3.0  範囲外

展開: >=1.2.3 <1.3.0
```

要素を省略すると上限も広がります。`~1.2` は `>=1.2.0 <1.3.0`、`~1` は `>=1.0.0 <2.0.0` です。「tildeは常にPATCHだけ」と覚えるのではなく、指定した要素数を確認します。

```text
~1.2   = >=1.2.0 <1.3.0
~1     = >=1.0.0 <2.0.0
```

通常は三要素を明記すると下限と意図が明確です。tildeは更新を同じMINOR内で小刻みにレビューしたい場合に向きます。

## caretは左端の0でない要素を保つ

caretは「先頭の数字を固定」と説明されがちですが、正確には左から見て最初の0ではない要素を変更しない範囲です。安定版の `^1.2.3` ではMAJORを固定し、MINORとPATCHを許可します。

```text
^1.2.3 = >=1.2.3 <2.0.0
^0.2.3 = >=0.2.3 <0.3.0
^0.0.3 = >=0.0.3 <0.0.4
```

この規則により、0.xでは範囲が狭くなります。

| 指定 | 許可される例 | 許可されない最初の境界 |
| --- | --- | --- |
| `^1.2.3` | `1.9.9` | `2.0.0` |
| `^0.2.3` | `0.2.9` | `0.3.0` |
| `^0.0.3` | 実質 `0.0.3` | `0.0.4` |

`^0.2.3` は `0.9.0` まで許可しません。新しい0.x MINORを採用するなら範囲自体を変更します。caretは、安定版の同じMAJORにある機能追加と修正を候補へ入れたい場合に向きます。

## プレリリースは通常の範囲へ自動で入らない

npmのrange判定では、通常、範囲内の数値に見えてもプレリリースは候補から除外されます。プレリリースを採用するには、その系統を明示した比較を含めます。

```text
^1.2.3       は 1.3.0-beta.1 を通常は選ばない
^2.0.0-rc.1  は 2.0.0-rc.2 を候補にできる
```

プレリリースを含むrangeには細かな条件があります。node-semverの仕様か `semver` パッケージで候補を検証し、安定版だけを使うなら通常のrangeへ混ぜません。

npmのdist-tagも別の概念です。`latest`、`next`、`beta` などのタグは、レジストリ上で名前を特定バージョンへ結び付けます。プレリリース文字列が付いているだけで、自動的に `next` タグで公開されるわけではありません。

## package.jsonとpackage-lock.jsonの責任

`package.json` は許容範囲という方針を表します。`package-lock.json` は、直接依存と推移的依存を含め、実際に解決されたツリーを記録します。

```json
{
  "name": "shop-app",
  "lockfileVersion": 3,
  "requires": true,
  "packages": {
    "": {
      "dependencies": {
        "sample-package": "^1.2.3"
      }
    },
    "node_modules/sample-package": {
      "version": "1.8.4"
    }
  }
}
```

この例では方針が `^1.2.3`、解決結果が `1.8.4` です。実際のlockfileは取得元、integrity、推移的依存も記録するため、npmに生成させます。アプリでは両ファイルをコミットし、更新差分をレビューします。

公開ライブラリのlockfileは開発・CIには役立ちますが、consumerは自分のルートで解決します。利用者へ伝える互換範囲は `dependencies` や `peerDependencies` に正しく記述します。

## npm installとnpm ciを使い分ける

`npm install` は必要に応じて依存解決とlockfile更新を行います。`npm ci` は既存lockfileからクリーンにインストールし、`package.json` と一致しなければ失敗します。ファイルを書き換えず、既存の `node_modules` は先に削除します。

```bash
# 開発中: 依存追加やlockfile更新を伴い得る
npm install
npm install sample-package@^1.4.0

# CI: コミット済みlockfileを変更せず再現する
npm ci
```

`npm ci` は互換性を保証する機能ではありません。Node.jsやOSなどの実行条件は別に管理します。チームとCIでNode.js・npmの方針を揃えると、lockfileの不要な差分も減らせます。

## npm outdatedで現在・範囲内・最新を分ける

`npm outdated` は、インストール済みのCurrent、現在のrangeで採用できるWanted、`latest` dist-tagが指すLatestを比較する手掛かりになります。

```text
Package         Current  Wanted  Latest
sample-package    1.2.3   1.9.4   2.1.0
```

`^1.2.3` ならWantedは1系、Latestは2系になり得ます。表示だけで更新せず、rangeと公開者のリリース情報を確認します。

推移的依存がどこから入ったか分からない場合は `npm explain` が役立ちます。

```bash
npm outdated
npm explain sample-package
npm view sample-package versions --json
```

`npm view` の最新版が自分の環境へ適合するとは限りません。`engines`、変更履歴、移行ガイドも確認します。

## 安全に更新する手順

range内でも動作は変わり得ます。変更単位を小さくし、戻せる状態で検証します。

### 1. 現状と更新理由を確認する

直接依存か推移的依存か、更新理由と目標版を確認します。

```bash
node --version
npm --version
npm outdated
npm explain sample-package
npm audit
```

脆弱性対応では修正版の系列と破壊的変更も調べます。`npm audit fix --force` でMAJORまで一括適用せず、差分を検証します。

### 2. リリース情報を読む

changelogと移行ガイドを読み、Node.js要件、ESM/CommonJS、型、peerDependencies、既定値の変更を確認します。PATCHでも回帰は起こり得ます。

### 3. 意図した範囲だけ更新する

`npm update` はrange内の候補へ更新し、既定ではpackage.jsonのrangeを変えません。対象を限定して実行します。

```bash
npm update sample-package

git diff -- package.json package-lock.json
```

rangeも変える場合は目標版を指定します。パッケージ名と番号は例です。

```bash
npm install sample-package@2.1.0

git diff -- package.json package-lock.json
```

lockfileでは推移的依存や重複排除も変わり得ます。大きな差分はnpmの版、peer dependency、再解決の理由を確認します。

### 4. プロジェクトの契約を検証する

プロジェクトに合わせて、テスト、型検査、lint、ビルド、主要画面やCLIのスモークテストを行います。

```bash
npm test
npm run typecheck
npm run lint
npm run build
```

実際の `scripts` を使い、可能ならCIと同じNode.js・npmで `npm ci` から検証します。

### 5. 定義とlockfileを一緒にレビューする

更新理由、版、破壊的変更、検証結果をPull Requestへ残し、定義とlockfileを一緒にコミットします。自動更新も、依存の重要度とテスト品質でレビュー条件を分けます。

## caret・tilde・固定の選び方

最適な記号は、アプリかライブラリか、lockfileをどう運用するか、更新をどの頻度で検証できるかで変わります。

| 指定 | 向いている方針 | 注意点 |
| --- | --- | --- |
| `^1.2.3` | 同じMAJORの機能追加・修正を取り込む | SemVer違反や回帰はテストで検出する |
| `~1.2.3` | 同じMINORのPATCHを中心に取り込む | 有用なMINOR更新は範囲変更が必要 |
| `1.2.3` | 更新をすべて明示レビューする | 推移的依存まで固定するのはlockfile |

アプリではlockfileが実際のツリーを記録し、rangeは次の解決時の許容幅になります。自動更新とテストがあればcaret、小刻みにレビューするならtildeや固定が候補です。

ライブラリは、実際に互換性を保てる範囲を宣言し、下限と新しい候補をCIで検証します。`peerDependencies` を開発時の一版へ理由なく固定しません。完全固定でも修正は自動で入らないため、定期確認とテストが必要です。

## よくある誤解

### `^` は常に最新版を入れる

caretは許容範囲です。MAJOR境界を越えず、通常はプレリリースも除外され、lockfileがあれば既存版が維持される場合があります。

### MINORとPATCHなら絶対に壊れない

SemVerは技術的な証明ではありません。バグ、分類ミス、環境差があるため、range内更新にもテストが必要です。

### lockfileがあればpackage.jsonは不要

package.jsonは許容方針、lockfileは解決結果です。`npm ci` は両者の整合を要求し、利用者へ伝わる条件もpackage.json側です。

### `0.2.0` から `0.3.0` は安全なMINOR更新

0.xの公開APIは安定扱いではなく、`^0.2.0` も `0.3.0` を含めません。変更履歴を確認します。

## 公開者は利用者の判断材料を作る

公開者側では、バージョンを上げる前に変更を公開APIへ照らして分類します。

- PATCH：公開契約を保った不具合修正、内部改善。
- MINOR：後方互換なAPI追加、既存APIの非推奨化。
- MAJOR：削除、引数・戻り値・既定動作の非互換変更。

非推奨化はMINORで代替を追加し、次のMAJORで削除すると移行期間を作れます。型だけの変更でも以前のコードがコンパイルできないなら破壊的です。Node.js要件の引き上げやCommonJS削除も評価します。

依存のMAJOR更新を内部で吸収し公開契約を保てるなら、自分まで必ずMAJORにする必要はありません。peer範囲や実行条件が狭まるなら影響を評価します。

変更履歴、移行手順、対応環境を記録します。`npm version` は番号更新を補助しますが、番号の意味は判断しません。

```bash
# 先に変更分類・テスト・作業ツリーを確認する
npm test
git status

# package.jsonなどの版を上げ、既定ではGit tagも作る
npm version patch
npm version minor
npm version major
```

三つを連続実行せず、変更に合う一つを選びます。実行前にリポジトリのリリース手順も確認します。

プレリリースは、安定版利用者へ誤って配布しないようdist-tagを明示します。

```bash
npm version prerelease --preid=rc
npm publish --tag next

npm dist-tag ls sample-package
```

プレリリース番号と `next` タグは別々に管理されます。既知の制約をリリースノートで説明します。

## まとめ

SemVer、npm range、lockfileを同じ「バージョン指定」として扱わないことが、更新判断の出発点です。

- SemVerは公開者が互換性の意味を `MAJOR.MINOR.PATCH` で伝える契約。
- npm rangeは利用者が依存解決で許可するバージョン集合。
- `~1.2.3` は `>=1.2.3 <1.3.0`、`^1.2.3` は `>=1.2.3 <2.0.0`。
- caretは0.xで狭くなり、`^0.2.3` は `0.3.0` を含まない。
- プレリリースは通常のrangeへ自動では含まれず、dist-tagとも別概念。
- package.jsonは方針、package-lock.jsonは実際の依存ツリーを記録する。
- 更新ではリリース情報、lockfile差分、型検査、テスト、ビルドを確認する。
- 公開者はコードだけでなく、型、CLI、設定、対応環境を含む公開APIを基準に版を上げる。

どこまで自動更新の候補へ入れ、どこから人がレビューするかを決め、lockfileとCIで支えることが重要です。
