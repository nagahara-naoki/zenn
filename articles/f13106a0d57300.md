`package.json`を開くと、パッケージのバージョンに`^`や`~`が付いていることがあります。

```json
{
  "dependencies": {
    "sample-package": "^1.2.3"
  }
}
```

この`^1.2.3`が、どのバージョンまで更新を許可しているか説明できるでしょうか。

```text
1.2.4  → 更新できる？
1.8.0  → 更新できる？
2.0.0  → 更新できる？
```

答えは次のとおりです。

```text
1.2.4  → 更新できる
1.8.0  → 更新できる
2.0.0  → 更新できない
```

`^1.2.3`は、基本的に次の範囲を表します。

```text
1.2.3以上、2.0.0未満
```

ただし、バージョンが`0.x.x`の場合は、このルールだけでは正しく判断できません。

SemVerを理解すると、次のような場面で判断しやすくなります。

- パッケージをどこまで安全に更新できるか
- `^`と`~`をどう使い分けるか
- メジャーバージョンアップが必要な理由
- `npm update`でどこまで更新されるか
- `package-lock.json`が何を固定しているか
- `npm audit fix --force`がなぜ危険なのか

この記事では、SemVerの基本からnpmのバージョン範囲まで、実務で必要な内容に絞って解説します。

## SemVerとは

SemVerは、**Semantic Versioning**の略です。

日本語では「セマンティックバージョニング」や「意味的バージョニング」と呼ばれます。

単にリリース回数を表すのではなく、バージョン番号によって変更内容の意味を伝えるためのルールです。

基本的な形式は次のとおりです。

```text
MAJOR.MINOR.PATCH
```

たとえば、`2.4.1`は次の3つに分けられます。

```text
2 . 4 . 1
│   │   └─ PATCH
│   └───── MINOR
└───────── MAJOR
```

それぞれの役割は次のとおりです。

| 種類 | 例 | 意味 |
|---|---:|---|
| MAJOR | `1.0.0` → `2.0.0` | 後方互換性のない変更 |
| MINOR | `1.2.0` → `1.3.0` | 後方互換性のある機能追加 |
| PATCH | `1.2.3` → `1.2.4` | 後方互換性のある不具合修正 |

ここで重要なのが、**後方互換性**です。

## 後方互換性とは

後方互換性があるとは、パッケージを新しいバージョンへ更新しても、既存の利用コードが基本的にそのまま動くことを意味します。

たとえば、次の関数を提供しているパッケージがあるとします。

```ts
export function add(a: number, b: number): number {
  return a + b;
}
```

不具合を修正しても、関数名や引数、戻り値が変わらなければ、利用者はコードを変更せずに更新できます。

```text
1.2.3 → 1.2.4
```

これはPATCHとして公開できる変更です。

一方で、関数名を変更すると、既存コードは動かなくなります。

```ts
export function sum(a: number, b: number): number {
  return a + b;
}
```

利用者は、次のようにコードを修正しなければなりません。

```diff
- import { add } from "sample-package";
+ import { sum } from "sample-package";
```

これは後方互換性のない変更なので、MAJORを上げます。

```text
1.2.3 → 2.0.0
```

## PATCH：後方互換性のある不具合修正

PATCHは、既存の使い方を壊さない不具合修正で上げます。

```text
1.2.3 → 1.2.4
```

たとえば、次のような変更です。

- 特定の入力で計算結果が間違う問題を修正した
- メモリリークを修正した
- エラーメッセージの誤字を修正した
- 既存APIの挙動を仕様どおりに直した
- セキュリティ上の問題を互換性を保ったまま修正した

PATCHを上げた場合、MAJORとMINORは変更しません。

```text
1.2.3
1.2.4
1.2.5
```

ただし、不具合修正であっても、修正によって既存の利用コードが動かなくなる場合は、単純にPATCHとはいえません。

「バグ修正だからPATCH」ではなく、**公開APIとの互換性が保たれているか**が判断基準です。

## MINOR：後方互換性のある機能追加

MINORは、既存の使い方を壊さずに新しい機能を追加したときに上げます。

```text
1.2.3 → 1.3.0
```

たとえば、既存の`add`関数を残したまま、`subtract`関数を追加するケースです。

```ts
export function add(a: number, b: number): number {
  return a + b;
}

export function subtract(a: number, b: number): number {
  return a - b;
}
```

既存利用者のコードはそのまま動き、新しい機能だけが追加されています。

MINORを上げると、PATCHは`0`に戻します。

```text
1.2.3 → 1.3.0
```

次のような変更も、MINORになる可能性があります。

- 新しい関数やクラスを追加した
- 新しいオプションを追加した
- 省略可能な引数を追加した
- 既存APIを非推奨にした
- 後方互換性を保ったまま機能を拡張した

SemVerの仕様では、公開APIの機能を非推奨にした場合もMINORを上げるものとされています。

## MAJOR：後方互換性のない変更

MAJORは、既存利用者のコード修正が必要になる変更で上げます。

```text
1.2.3 → 2.0.0
```

たとえば、次のような変更です。

- 関数やクラスを削除した
- 関数名を変更した
- 引数の型や順番を変更した
- 戻り値の構造を変更した
- 設定ファイルの形式を変更した
- 既存のデフォルト動作を変更した
- サポートする実行環境を大きく変更した

MAJORを上げると、MINORとPATCHは`0`に戻します。

```text
1.8.4 → 2.0.0
```

MAJORが変わる更新では、リリースノートや移行ガイドを確認する必要があります。

```text
1.x.x → 2.x.x
```

自動更新だけで済むとは限らず、利用側のコードや設定変更が必要になる可能性があります。

## 変更の基準は「公開API」

SemVerを正しく運用するには、何を公開APIとして扱うかを明確にする必要があります。

公開APIには、関数やクラスだけでなく、次のようなものも含まれる可能性があります。

- エクスポートしている型
- CLIのコマンドやオプション
- 設定ファイルの形式
- HTTP APIのリクエストとレスポンス
- エラーの種類
- 環境変数
- イベント名
- プラグイン向けの拡張ポイント

たとえば、内部実装を大きく変更しても、公開APIと挙動が変わらなければ、MAJORを上げる必要はないかもしれません。

反対に、コードの変更量が1行だけでも、公開APIを壊すならMAJOR相当です。

SemVerで重要なのは変更量ではなく、**利用者に与える影響**です。

## `0.x.x`は特別扱い

SemVerでは、MAJORが`0`のバージョンは初期開発段階として扱われます。

```text
0.1.0
0.2.5
0.9.9
```

`0.x.x`では、公開APIが安定しているとはみなされません。

そのため、次の更新にも破壊的変更が含まれる可能性があります。

```text
0.2.3 → 0.3.0
```

数字の位置だけを見るとMINORの更新ですが、`0.x.x`では実質的に大きな変更の境界として扱われることがあります。

ここは、npmの`^`を理解するうえでも非常に重要です。

```text
^1.2.3 → 2.0.0未満まで許可
^0.2.3 → 0.3.0未満まで許可
```

同じ`^`でも、MAJORが`0`かどうかで許可範囲が変わります。

## プレリリースバージョン

正式リリース前のバージョンは、ハイフンを付けて表現できます。

```text
1.0.0-alpha
1.0.0-beta
1.0.0-beta.1
1.0.0-rc.1
```

よく使われる名前は次のとおりです。

| 名前 | 一般的な意味 |
|---|---|
| `alpha` | 開発初期で、仕様変更が多い |
| `beta` | 機能は揃っているが、検証中 |
| `rc` | 正式版の候補 |
| 正式版 | プレリリース識別子がない状態 |

バージョンの優先順位は、次のようになります。

```text
1.0.0-alpha
<
1.0.0-beta
<
1.0.0-rc.1
<
1.0.0
```

同じ`1.0.0`でも、プレリリース版は正式版より前のバージョンとして扱われます。

プレリリース版は、通常の安定版と同じ互換性を満たさない可能性があります。

本番環境へ導入する場合は、安定版と同じ感覚で利用しないように注意が必要です。

## ビルドメタデータ

バージョンには、`+`を使ってビルド情報を付けることもできます。

```text
1.2.3+build.123
1.2.3+20260710
1.2.3-beta.1+sha.abcdef
```

この部分をビルドメタデータと呼びます。

ビルドメタデータは、バージョンの優先順位には影響しません。

```text
1.2.3+build.1
1.2.3+build.2
```

この2つは、SemVer上の優先順位としては同じです。

ビルド番号、日時、コミットハッシュなど、成果物を識別するための情報として利用できます。

## SemVerとnpmのバージョン範囲は別のもの

ここで、混同しやすいポイントがあります。

```text
1.2.3
```

これはSemVer形式の**バージョン番号**です。

一方、次の記号は、npmがパッケージの許容バージョンを指定するために使う**バージョン範囲**です。

```text
^1.2.3
~1.2.3
>=1.2.3
1.2.x
```

SemVerは、バージョン番号が何を意味するかを定めます。

npmのバージョン範囲は、そのSemVerを使って「どのバージョンをインストールしてよいか」を表現します。

```json
{
  "dependencies": {
    "package-a": "1.2.3",
    "package-b": "^1.2.3",
    "package-c": "~1.2.3"
  }
}
```

ここからは、それぞれの範囲指定を見ていきます。

## バージョンを完全に固定する

記号を付けずにバージョンを書くと、そのバージョンだけを指定します。

```json
{
  "dependencies": {
    "sample-package": "1.2.3"
  }
}
```

許可されるのは`1.2.3`だけです。

```text
1.2.3 → 許可
1.2.4 → 不許可
1.3.0 → 不許可
2.0.0 → 不許可
```

依存関係を厳密に制御できますが、更新するには`package.json`の指定も変更する必要があります。

## `~`：PATCH更新を許可する

`~1.2.3`は、基本的にPATCHの更新を許可します。

```json
{
  "dependencies": {
    "sample-package": "~1.2.3"
  }
}
```

範囲は次のとおりです。

```text
1.2.3以上、1.3.0未満
```

比較演算子で表すと、次のようになります。

```text
>=1.2.3 <1.3.0
```

具体例を見てみます。

```text
1.2.3 → 許可
1.2.4 → 許可
1.2.9 → 許可
1.3.0 → 不許可
2.0.0 → 不許可
```

PATCHの不具合修正は取り込みたいものの、新機能を含むMINOR更新は自動で取り込みたくない場合に使えます。

### `~1.2`の場合

PATCHを省略した次の指定も可能です。

```text
~1.2
```

これは次の範囲になります。

```text
>=1.2.0 <1.3.0
```

### `~1`の場合

MINORとPATCHを省略すると、次の範囲になります。

```text
~1
```

```text
>=1.0.0 <2.0.0
```

`~`は常にPATCHだけを許可する、と覚えると不正確です。

**どこまでバージョン番号を指定しているか**によって範囲が変わります。

## `^`：左端の0ではない数字を固定する

`^1.2.3`は、一般的にMINORとPATCHの更新を許可します。

```json
{
  "dependencies": {
    "sample-package": "^1.2.3"
  }
}
```

範囲は次のとおりです。

```text
>=1.2.3 <2.0.0
```

具体例は次のとおりです。

```text
1.2.3 → 許可
1.2.4 → 許可
1.3.0 → 許可
1.9.9 → 許可
2.0.0 → 不許可
```

MAJORが変わらない範囲で更新を許可するため、後方互換性のある更新を取り込みやすくなります。

ただし、これは`1.0.0`以上の場合です。

## `^`と`0.x.x`の注意点

`^`は、バージョン番号の**左端にある0ではない数字を変更しない範囲**を許可します。

### `^1.2.3`

左端の0ではない数字は`1`です。

```text
^1.2.3
```

```text
>=1.2.3 <2.0.0
```

### `^0.2.3`

左端の0ではない数字は`2`です。

```text
^0.2.3
```

```text
>=0.2.3 <0.3.0
```

許可される例は次のとおりです。

```text
0.2.3 → 許可
0.2.4 → 許可
0.2.9 → 許可
0.3.0 → 不許可
```

### `^0.0.3`

左端の0ではない数字は`3`です。

```text
^0.0.3
```

```text
>=0.0.3 <0.0.4
```

結果として、実質的に`0.0.3`だけが対象になります。

```text
0.0.3 → 許可
0.0.4 → 不許可
0.1.0 → 不許可
```

`^`を「MAJORが同じなら更新できる」とだけ覚えると、`0.x.x`で間違えます。

次の3つは、まとめて覚えておくと分かりやすいです。

```text
^1.2.3   → >=1.2.3 <2.0.0
^0.2.3   → >=0.2.3 <0.3.0
^0.0.3   → >=0.0.3 <0.0.4
```

## `x`と`*`による指定

特定の部分を任意の数字として扱うこともできます。

### `1.2.x`

```text
1.2.x
```

範囲は次のとおりです。

```text
>=1.2.0 <1.3.0
```

PATCHだけを任意にします。

```text
1.2.0 → 許可
1.2.8 → 許可
1.3.0 → 不許可
```

### `1.x`

```text
1.x
```

範囲は次のとおりです。

```text
>=1.0.0 <2.0.0
```

MINORとPATCHを任意にします。

### `*`

```text
*
```

基本的に、すべての通常バージョンを許可します。

依存パッケージの破壊的変更まで取り込む可能性があるため、通常のアプリケーションで安易に指定するのは避けた方がよいでしょう。

## 比較演算子で範囲を指定する

範囲を明示的に書くこともできます。

```json
{
  "dependencies": {
    "sample-package": ">=1.2.3 <2.0.0"
  }
}
```

利用できる主な演算子は次のとおりです。

| 演算子 | 意味 |
|---|---|
| `>` | より大きい |
| `>=` | 以上 |
| `<` | より小さい |
| `<=` | 以下 |
| `=` | 完全一致 |

複数の条件を半角スペースで並べると、すべての条件を満たす範囲になります。

```text
>=1.2.3 <2.0.0
```

`||`を使うと、どちらかの範囲を満たす指定にできます。

```text
^1.2.3 || ^2.0.0
```

複雑な条件を表現できますが、読み間違いが起きやすくなるため、必要な場合だけ使うのがよいでしょう。

## 主な指定方法の比較

よく使う指定をまとめると、次のようになります。

| 指定 | 許可される範囲 |
|---|---|
| `1.2.3` | `1.2.3`のみ |
| `~1.2.3` | `>=1.2.3 <1.3.0` |
| `^1.2.3` | `>=1.2.3 <2.0.0` |
| `^0.2.3` | `>=0.2.3 <0.3.0` |
| `^0.0.3` | `>=0.0.3 <0.0.4` |
| `1.2.x` | `>=1.2.0 <1.3.0` |
| `1.x` | `>=1.0.0 <2.0.0` |
| `>=1.2.3 <2.0.0` | 指定した比較範囲 |
| `*` | 基本的にすべての通常バージョン |

迷ったときは、範囲を比較演算子へ置き換えて考えると理解しやすくなります。

```text
^1.2.3
↓
>=1.2.3 <2.0.0
```

## `package.json`と`package-lock.json`の違い

SemVerを理解するときは、`package-lock.json`との関係も重要です。

`package.json`には、インストールを許可するバージョン範囲が書かれます。

```json
{
  "dependencies": {
    "sample-package": "^1.2.3"
  }
}
```

一方、`package-lock.json`には、実際に解決された具体的なバージョンが記録されます。

```json
{
  "packages": {
    "node_modules/sample-package": {
      "version": "1.8.2"
    }
  }
}
```

役割を整理すると、次のようになります。

| ファイル | 役割 |
|---|---|
| `package.json` | インストールしてよいバージョン範囲 |
| `package-lock.json` | 実際に解決されたバージョン |

たとえば、`package.json`が`^1.2.3`でも、Lockファイルに`1.8.2`が記録されていれば、通常の`npm install`ではその具体的なバージョンが利用されます。

```text
package.json
^1.2.3
   ↓ 許容範囲

package-lock.json
1.8.2
   ↓ 実際にインストール
```

npmは、Lockファイルのバージョンが`package.json`の範囲を満たしていれば、Lockファイルの具体的なバージョンを利用します。

そのため、`^`を使っているからといって、毎回の`npm install`で必ず最新版に変わるわけではありません。

## `npm install`と`npm ci`

既存プロジェクトで依存関係をインストールする主なコマンドには、`npm install`と`npm ci`があります。

### `npm install`

```bash
npm install
```

`package.json`と`package-lock.json`を比較しながら依存関係をインストールします。

両者に矛盾がなければ、Lockファイルのバージョンが利用されます。

バージョン範囲が変更され、Lockファイルが条件を満たさなくなった場合は、新しいバージョンを解決してLockファイルを更新します。

### `npm ci`

```bash
npm ci
```

Lockファイルを基準に、依存関係を再現するためのコマンドです。

`package.json`と`package-lock.json`が一致していない場合はエラーになります。

CI環境など、同じ依存関係を再現したい場面に向いています。

## `npm outdated`の見方

依存パッケージの更新状況は、次のコマンドで確認できます。

```bash
npm outdated
```

表示される主な項目は次のとおりです。

```text
Package         Current  Wanted  Latest
sample-package  1.2.3    1.9.0   2.1.0
```

それぞれの意味は次のとおりです。

| 項目 | 意味 |
|---|---|
| `Current` | 現在インストールされているバージョン |
| `Wanted` | `package.json`の範囲内で更新できるバージョン |
| `Latest` | npm Registryで`latest`タグが付いているバージョン |

たとえば、次の指定があるとします。

```json
{
  "dependencies": {
    "sample-package": "^1.2.3"
  }
}
```

`1.9.0`は許容範囲ですが、`2.1.0`はMAJORが変わるため範囲外です。

```text
Current: 1.2.3
Wanted:  1.9.0
Latest:  2.1.0
```

この場合、`npm update`で更新される候補は基本的に`Wanted`側です。

MAJORを上げるには、`package.json`の指定変更も必要になります。

## よくある誤解

## 誤解1：`^`は最新版を入れる指定

`^`は、無条件に最新版を入れる指定ではありません。

```text
^1.2.3
```

基本的に許可されるのは次の範囲です。

```text
>=1.2.3 <2.0.0
```

`2.0.0`が公開されても、範囲外なので自動的には入りません。

## 誤解2：MINORとPATCHなら絶対に壊れない

SemVerでは、MINORとPATCHは後方互換性を保つルールです。

しかし、それはパッケージ提供者が正しくSemVerを運用していることが前提です。

実際には、次のようなことも起こり得ます。

- 意図せず破壊的変更が入った
- 不具合によって既存機能が動かなくなった
- 公開APIの認識が提供者と利用者で異なった
- 型定義の変更が利用コードに影響した

SemVerは互換性を伝えるための重要な約束ですが、更新後の動作を保証するテストの代わりにはなりません。

## 誤解3：`package-lock.json`があれば`package.json`は関係ない

Lockファイルのバージョンは、`package.json`の許容範囲を満たしている必要があります。

`package.json`の指定を変更してLockファイルと矛盾した場合、`npm install`は新しい依存関係を解決してLockファイルを更新します。

```text
package.json  → 許可する範囲
package-lock  → 解決済みの具体的な状態
```

どちらか片方だけではなく、役割の異なる2つのファイルとして管理します。

## 誤解4：`0.2.0`から`0.3.0`は安全なMINOR更新

SemVer上、`0.x.x`は初期開発段階です。

```text
0.2.0 → 0.3.0
```

数字の位置はMINORですが、破壊的変更が含まれる可能性があります。

npmの`^0.2.0`も、`0.3.0`を許可しません。

```text
^0.2.0
↓
>=0.2.0 <0.3.0
```

## `^`と`~`はどちらを使うべきか

どちらが常に正しいというわけではありません。

### `^`が向いているケース

```json
{
  "dependencies": {
    "sample-package": "^1.2.3"
  }
}
```

- 後方互換性のある機能追加も取り込みたい
- 定期的にテストを実行できる
- パッケージがSemVerを適切に運用している
- 更新による改善やセキュリティ修正を取り込みたい

### `~`が向いているケース

```json
{
  "dependencies": {
    "sample-package": "~1.2.3"
  }
}
```

- PATCH更新だけを取り込みたい
- MINOR更新も慎重に確認したい
- 依存パッケージの変更影響が大きい
- 安定性を優先したい

### 完全固定が向いているケース

```json
{
  "dependencies": {
    "sample-package": "1.2.3"
  }
}
```

- 更新タイミングを完全に管理したい
- 動作保証する組み合わせを厳密に固定したい
- Lockファイルを使えない配布形態である
- 依存パッケージのわずかな変更も影響が大きい

アプリケーション開発では、`package-lock.json`をリポジトリで管理していれば、`package.json`で範囲を指定しながら、実際の環境はLockファイルで固定できます。

そのうえで、依存関係を定期的に更新し、テストする運用が重要です。

## 安全にパッケージを更新する流れ

SemVerは更新判断の材料になりますが、バージョン番号だけで安全性を判断してはいけません。

次のような流れで確認します。

```text
1. 現在のバージョンを確認する
        ↓
2. 更新先がPATCH・MINOR・MAJORのどれか確認する
        ↓
3. リリースノートを確認する
        ↓
4. package.jsonとLockファイルの差分を確認する
        ↓
5. Lint・型チェック・テスト・ビルドを実行する
        ↓
6. 主要機能を動作確認する
```

利用できるコマンドの例は次のとおりです。

```bash
# 更新状況を確認
npm outdated

# package.jsonの範囲内で更新
npm update

# 特定バージョンへ更新
npm install sample-package@1.5.0

# MAJORを含む最新版へ更新
npm install sample-package@latest

# 変更内容を確認
git diff -- package.json package-lock.json

# 動作確認
npm run lint
npm run typecheck
npm test
npm run build
```

MAJOR更新では、リリースノートだけでなく、公式の移行ガイドも確認します。

MINORやPATCHであっても、テストを省略してよいわけではありません。

## パッケージ提供者側の判断

自分でnpmパッケージやライブラリを公開する場合は、利用者視点でバージョンを決めます。

### PATCHを上げる

```text
1.2.3 → 1.2.4
```

- 公開APIを変えない不具合修正
- 既存利用者に影響しない内部修正
- 後方互換性のあるセキュリティ修正

### MINORを上げる

```text
1.2.3 → 1.3.0
```

- 後方互換性のある機能追加
- 新しいAPIの追加
- 既存APIの非推奨化

### MAJORを上げる

```text
1.2.3 → 2.0.0
```

- 公開APIの削除
- 引数や戻り値の非互換な変更
- 既存利用者の修正が必要な挙動変更
- 設定形式の非互換な変更

判断に迷った場合は、変更したコードの大きさではなく、既存利用者がコードを変更せずに更新できるかを考えます。

## まとめ

SemVerは、バージョン番号に変更内容の意味を持たせるルールです。

基本は次の3つです。

```text
MAJOR.MINOR.PATCH
```

```text
MAJOR → 後方互換性のない変更
MINOR → 後方互換性のある機能追加
PATCH → 後方互換性のある不具合修正
```

npmで特に覚えておきたい範囲指定は次のとおりです。

```text
1.2.3    → 1.2.3だけ
~1.2.3   → >=1.2.3 <1.3.0
^1.2.3   → >=1.2.3 <2.0.0
^0.2.3   → >=0.2.3 <0.3.0
^0.0.3   → >=0.0.3 <0.0.4
```

また、`package.json`と`package-lock.json`は役割が異なります。

```text
package.json      → 許可するバージョン範囲
package-lock.json → 実際に解決された具体的なバージョン
```

SemVerを理解すると、バージョン番号を見ただけで、更新の規模や互換性の可能性を判断しやすくなります。

ただし、SemVerは更新後の安全を保証するものではありません。

リリースノート、依存関係の差分、テスト結果を確認したうえで更新することが大切です。
