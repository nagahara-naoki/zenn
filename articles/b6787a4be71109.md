Dependency Injection（DI、依存性注入）は、ある処理が必要とするオブジェクトや関数を、その処理の内部で固定的に作らず、外側から渡す設計です。生成と利用を分けることで、業務ロジックをHTTP、DB、時刻、乱数、環境設定などの具体的な仕組みから切り離します。

先に結論をまとめます。

- DIの目的は「何でもinterfaceにすること」ではなく、依存の選択と利用を分離すること
- 必須依存はconstructorまたは関数引数から渡し、不完全な状態を作らない
- 業務ロジックは必要最小限の振る舞いに依存し、具体実装の組み立てはcomposition rootへ集める
- 小規模なら手動DIで十分で、containerは登録数やlifecycle管理が複雑になってから検討する
- test doubleを注入できることは効果の一つだが、テスト専用の抽象化を増やすこと自体は目的ではない
- 依存の寿命を誤ると、データ混在、無駄な接続、解放漏れが起きる

## 依存とは何か

ある処理が動くために必要な別の値、関数、オブジェクトを依存と呼びます。次の `UserService` は `ApiUserReader` に依存しています。

```ts
type User = {
  id: number;
  name: string;
};

class ApiUserReader {
  async findById(id: number): Promise<User> {
    const response = await fetch(`https://example.com/users/${id}`);
    if (!response.ok) {
      throw new Error(`failed to fetch user: ${response.status}`);
    }
    return (await response.json()) as User;
  }
}

class UserService {
  private readonly reader = new ApiUserReader();

  async getDisplayName(id: number): Promise<string> {
    const user = await this.reader.findById(id);
    return user.name.trim();
  }
}
```

依存が存在すること自体は問題ではありません。ソフトウェアは複数の部品を組み合わせて動きます。問題は、`UserService` が依存の「使い方」だけでなく「具体実装の選択と生成」まで決めている点です。

このままでは、テストでもHTTP通信が必要です。保存先をメモリやDBへ変えるときはserviceを編集します。認証付きreaderの生成に設定が必要になれば、その設定責務までserviceへ流れ込みます。

DIでは、外側が依存を用意してserviceへ渡します。

## 必要な振る舞いを契約にする

最初に、`UserService` が実際に必要とする操作だけを型として表します。

```ts
interface UserReader {
  findById(id: number): Promise<User>;
}

class UserService {
  constructor(private readonly userReader: UserReader) {}

  async getDisplayName(id: number): Promise<string> {
    const user = await this.userReader.findById(id);
    return user.name.trim();
  }
}
```

serviceはURL、fetch、JSON変換を知りません。「IDからUserを非同期に読む」という能力だけを要求します。実装は外側で用意します。

```ts
class ApiUserReader implements UserReader {
  constructor(private readonly baseUrl: string) {}

  async findById(id: number): Promise<User> {
    const response = await fetch(`${this.baseUrl}/users/${id}`);
    if (!response.ok) {
      throw new Error(`failed to fetch user: ${response.status}`);
    }

    const data = (await response.json()) as unknown;
    return parseUser(data);
  }
}

function parseUser(value: unknown): User {
  if (
    typeof value !== "object" ||
    value === null ||
    typeof (value as { id?: unknown }).id !== "number" ||
    typeof (value as { name?: unknown }).name !== "string"
  ) {
    throw new TypeError("invalid user response");
  }

  return value as User;
}
```

型アサーションだけでは外部JSONを検証できないため、境界実装側でruntime validationを行っています。業務ロジックへ不正な値を入れないことも、依存境界の責務です。実務ではschema libraryを使っても構いません。

重要なのは、巨大な `Repository` interfaceを先に作らないことです。consumerが必要とする最小の操作から契約を導きます。読み取りしか使わないserviceへ `save`、`delete`、`findAll` まで見せると、誤用とtest doubleの実装量が増えます。

## composition rootで一度だけ組み立てる

どの実装を使うか決める場所をcomposition rootと呼びます。CLIならmain関数、Web serverなら起動処理、Reactならappのroot付近など、アプリケーションの最も外側に置きます。

```ts
function createApplication() {
  const userReader = new ApiUserReader("https://example.com");
  const userService = new UserService(userReader);

  return { userService };
}

const app = createApplication();
const displayName = await app.userService.getDisplayName(1);
console.log(displayName);
```

ここで `new` が残っていることは問題ではありません。DIは `new` を禁止する規則ではなく、「選択する場所」と「利用する場所」を分ける設計です。生成コードが外側へ集まり、業務ロジックから消えていれば目的を達成しています。

composition rootには環境変数の読込、adapterの生成、loggerの設定、lifecycleの開始などが集まります。ただし、巨大な一関数へすべてを直書きする必要はありません。機能単位の小さなfactoryへ分け、最上位で結合できます。

```ts
type UserFeature = {
  userService: UserService;
};

function createUserFeature(baseUrl: string): UserFeature {
  const userReader = new ApiUserReader(baseUrl);
  return { userService: new UserService(userReader) };
}
```

組み立て関数は依存関係を隠すservice locatorではありません。引数と戻り値から構成が追え、通常のコードとして検索・デバッグできます。

## test doubleで業務ルールだけを確かめる

同じ `UserReader` 契約を満たすin-memory実装を渡せば、ネットワークなしでserviceを検証できます。

```ts
class InMemoryUserReader implements UserReader {
  constructor(private readonly users: readonly User[]) {}

  async findById(id: number): Promise<User> {
    const user = this.users.find((candidate) => candidate.id === id);
    if (!user) {
      throw new Error(`user not found: ${id}`);
    }
    return user;
  }
}
```

```ts
import assert from "node:assert/strict";

const reader = new InMemoryUserReader([
  { id: 1, name: "  Taro  " },
]);
const service = new UserService(reader);

assert.equal(await service.getDisplayName(1), "Taro");
await assert.rejects(
  () => service.getDisplayName(999),
  /user not found: 999/,
);
```

このテストが示すのは、単にmockできることではありません。`UserService` の責務が「取得済みユーザーの表示名を作る」に絞られたことです。HTTP statusやJSON parsingは `ApiUserReader` のtestで別に確認します。

test doubleにはfake、stub、spyなど複数の形がありますが、用語より契約が重要です。実装の内部呼び出し回数を細かくmockすると、同じ振る舞いを保つrefactoringでもtestが壊れます。可能なら公開結果を検証し、送信など結果を観測できない境界だけspyで記録します。

```ts
interface Notifier {
  send(message: string): Promise<void>;
}

class RecordingNotifier implements Notifier {
  readonly messages: string[] = [];

  async send(message: string): Promise<void> {
    this.messages.push(message);
  }
}
```

手書きfakeは型検査され、意図が読みやすく、mock library固有APIへ依存しません。複雑なprotocolを完全再現しようとしてfake自体が大きくなるなら、contract testや実物に近いintegration testも組み合わせます。

## constructor injectionだけがDIではない

classの必須依存にはconstructor injectionが適しています。生成直後から依存が揃い、`undefined` checkが不要だからです。しかし、DIはclass専用の仕組みではありません。

小さな処理なら、関数引数が最も明快です。

```ts
type Clock = {
  now(): Date;
};

function isExpired(expiresAt: Date, clock: Clock): boolean {
  return expiresAt.getTime() <= clock.now().getTime();
}

const fixedClock: Clock = {
  now: () => new Date("2026-01-01T00:00:00Z"),
};

console.log(
  isExpired(new Date("2025-12-31T23:59:59Z"), fixedClock),
); // true
```

一回の操作だけが必要とする依存ならmethod引数も候補です。たとえばexport処理の進捗通知だけを呼び出しごとに差し替えるなら、class全体の状態として保持する必要はありません。

property injectionやsetter injectionは、必須依存を後から設定するために使うと未完成状態を作ります。循環参照を解くために安易に採用せず、責務分割やfactoryを検討します。フレームワークがlifecycleを保証する場合でも、どの時点で利用可能になるかを明示します。

ReactのpropsやContextも、子componentが必要な値や関数を外側から受け取るという意味ではDIとして利用できます。ただし、すべてのpropsをDIと呼ぶと設計上の議論がぼやけます。外部I/O、現在時刻、feature flagなど、振る舞いを左右する依存をどこで選ぶかに注目します。

## DIとDIPとIoCを区別する

似た用語ですが、同じ意味ではありません。DIは依存を外から渡す手段、DIPは上位方針と下位詳細が抽象へ依存する設計原則、IoCは制御をframeworkなどへ委ねる広い考え方です。DI containerは登録・解決・寿命管理を自動化する道具にすぎません。

`UserService` と `ApiUserReader` が小さな `UserReader` 契約へ依存する例はDIPも適用しています。一方、具体classをconstructorへ渡しても、生成を外へ出していればDIです。

```ts
class MarkdownFormatter {
  format(title: string): string {
    return `# ${title}`;
  }
}

class ReportService {
  constructor(private readonly formatter: MarkdownFormatter) {}
}
```

`MarkdownFormatter` が安定した小さな実装なら、interfaceを追加しない選択は合理的です。逆にinterfaceがあっても、service内部で具体実装を生成していれば選択は分離されません。構文ではなく依存方向と組み立て場所を確認します。

## TypeScriptのinterfaceは実行時に消える

TypeScriptのinterfaceはcompile後のJavaScriptに残りません。手動DIでは型検査だけに使うため問題ありませんが、DI containerがruntimeで依存を識別するときはinterfaceそのものをtokenにできません。

tokenにはclass constructor、文字列、Symbolなどを使います。

```ts
interface Logger {
  info(message: string): void;
}

const LOGGER = Symbol("LOGGER");

type ProviderToken<T> = symbol & { readonly __type?: T };
const loggerToken = LOGGER as ProviderToken<Logger>;
```

実際のcontainer APIはframeworkごとに異なります。NestJSなどdecorator metadataを利用するframeworkでも、interfaceはruntimeに存在しないためcustom tokenが必要です。classをtokenにすると簡潔ですが、上位ロジックが具体class名に結び付く場合があります。

文字列tokenは衝突やtypoが起きやすいため、localな手動registryならSymbolが扱いやすい選択です。ただし、tokenとgeneric型の対応はTypeScriptだけの約束であり、誤ったcastをすればruntimeでは防げません。containerの登録testや起動時validationを用意します。

## containerを導入する判断

依存が数個なら、手動の `new` とfactoryが最も読みやすく、関係がコードに直接現れます。

containerの価値が高まるのは、次の要件が重なったときです。

- 数十以上のproviderを規則的に組み立てる
- singleton、request、transientなど複数scopeを管理する
- module単位でproviderの公開範囲を制御する
- decoratorやmetadataを既に使うframeworkへ統合する
- 起動と終了時のlifecycle hookを統一する

containerは複雑さを消さず、設定とruntime resolutionへ移します。登録漏れ、検索しにくいtoken、暗黙scopeというtrade-offがあります。container APIはcomposition rootとframework adapter付近へ閉じ込め、業務コードから任意に `resolve()` しません。

## service locatorを避ける

次のclassは引数なしで作れますが、内部で何を必要とするか呼び出し側から分かりません。

```ts
interface Container {
  resolve<T>(token: symbol): T;
}

declare const container: Container;
declare const USER_READER: symbol;

class HiddenDependencyService {
  async run(id: number): Promise<User> {
    const reader = container.resolve<UserReader>(USER_READER);
    return reader.findById(id);
  }
}
```

この形は依存をsignatureから隠し、登録漏れを処理途中の失敗にします。`UserReader` を直接渡せば、生成時に不足が分かります。

frameworkのcontrollerなど、framework自身が生成する境界ではdecoratorによる注入が必要なことがあります。それでも、そこから呼ぶ業務serviceは通常の引数で依存を受け取る形に保つと、framework外でもtestできます。

## lifecycleとscopeを依存の一部として考える

何を注入するかだけでなく、いつ生成し、いつ破棄するかも重要です。

```ts
interface DisposableDatabase {
  query(sql: string): Promise<readonly unknown[]>;
  close(): Promise<void>;
}

async function main(database: DisposableDatabase): Promise<void> {
  try {
    await database.query("SELECT 1");
  } finally {
    await database.close();
  }
}
```

一般的なscopeには次の性質があります。

| scope | 主な用途 | 注意点 |
| --- | --- | --- |
| singleton | 設定、stateless service、共有connection pool | request固有状態を保持しない |
| request | 認証情報、trace context、request単位cache | singletonから直接保持しない |
| transient | 短命でmutableな作業オブジェクト | 大量生成のcostと解放を確認する |

singleton serviceへrequest-scoped objectを保存すると、次のrequestから前のユーザーデータが見える危険があります。逆に、DB connection poolを処理ごとに作ると資源を浪費します。寿命の長い依存は、同じかより長い寿命の依存だけを安全に保持できる、という方向を意識します。

生成が非同期な依存は、constructorでPromiseを隠すより、起動時に接続を完了してから注入するか、接続操作を明示したadapterにします。失敗時のretry、shutdown時のclose、test終了時のcleanupまでcomposition rootが管理します。

## 循環依存は設計の警告として扱う

`AService` が `BService` を必要とし、BもAを必要とすると、生成順序が決まりません。containerのforward reference機能で回避できても、二つの責務が強く結合している事実は残ります。

解消方法を次の順で検討します。

1. AとBが共有する処理を第三の小さなserviceへ移す
2. 一方向の結果を値として引数へ渡す
3. 即時応答が不要ならeventを発行して購読側を分離する
4. 一回の操作だけに必要ならmethod引数やcallbackを使う
5. 本当に遅延生成が必要なら、依存そのものではなくfactoryを注入する

factory注入は循環を隠す万能策ではありません。いつ生成されるか分かりにくくなり、scopeも複雑になります。ドメイン上の相互依存が必要かを先に見直します。

## DIを使いすぎない

すべての `new`、関数、定数を注入対象にすると、単純な処理まで複数interfaceとfactoryを通らなければ読めません。

DIの効果が高い境界は次のとおりです。

- DB、HTTP、filesystem、message brokerなどの外部I/O
- 現在時刻、乱数、UUID、環境設定など再現性に影響する値
- メール、課金、監査ログなどtestで実行したくない副作用
- 複数実装を環境やtenantで切り替える仕組み
- 接続や購読などlifecycle管理が必要なresource

一方、決定的な文字列整形、標準的な値オブジェクト、変更可能性の低い内部helperは直接importで十分なことが多いです。「将来差し替えるかもしれない」だけで抽象化せず、変更軸と境界が実際に見えた時点で切り出します。

testのためだけにprivate helperをすべて注入するのではなく、公開APIから観測できる振る舞いをtestします。純粋関数として独立価値があるhelperならexportし、そうでなければ実装詳細のままにします。

## 導入時の確認手順

既存コードへDIを導入するときは、次の順序なら過剰設計を避けられます。

1. 業務処理の中で直接生成・importされている外部境界を一つ選ぶ
2. consumerが実際に使う最小の操作を型にする
3. 依存をconstructorまたは関数引数へ移す
4. production実装の生成をcomposition rootへ移す
5. 小さなfakeで業務ルールのtestを書く
6. エラー契約とlifecycleをproduction/fake間で揃える
7. 手動組み立てが本当に負担になった場合だけcontainerを評価する

一度に全層をinterface化するより、HTTP clientやclockのような明確な境界から始めます。DI後にserviceの引数が増え続けるなら、DIが失敗したのではなく、そのserviceが複数責務を持つ兆候です。依存を束ねた「Dependencies」オブジェクトで隠す前に、classを分割できないか検討します。

## まとめ

DIはframeworkのdecoratorではなく、依存を選ぶコードと使うコードを離すための設計です。

- consumerが必要とする最小の振る舞いを契約にする
- 必須依存はconstructorまたは関数引数で明示する
- production実装はアプリ外側のcomposition rootで組み立てる
- fakeを使い、外部I/Oではなく業務ルールを独立して検証する
- DI、DIP、IoC、DI containerを同じものとして扱わない
- TypeScript interfaceはruntimeに残らないため、containerでは別tokenが必要になる
- scope、初期化、破棄、エラー契約まで依存設計に含める
- service locator、循環依存、過剰なinterfaceは、依存を見えにくくするため避ける
- 小規模な構成では手動DIと通常関数を優先する

良いDIはコードを抽象語で覆うのではなく、「この処理は何を必要とし、実物をどこで選び、どれだけ生存させるか」を明確にします。その三点を説明できれば、containerの有無にかかわらず変更とテストに強い境界を作れます。
