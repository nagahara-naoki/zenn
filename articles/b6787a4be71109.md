DIは、アプリケーション設計でよく出てくる考え方です。

Angular、NestJS、Spring、Laravelなど、多くのフレームワークで使われています。

ただ、最初に聞くと少し難しく感じます。

- DI
- Dependency Injection
- 依存性の注入
- 依存関係の注入
- DIコンテナ

このような言葉が一気に出てくるため、何を理解すればよいのか分かりづらいです。

しかし、DIの考え方自体はかなりシンプルです。

一言でいうと、DIとは**必要なものを自分で作らず、外から渡してもらう設計**です。

この記事では、DIを以下の流れで解説します。

- 依存とは何か
- DIを使わない場合の問題点
- DIとは何か
- DIを使うメリット
- DIの種類
- DIとDIコンテナの違い
- AngularやNestJSでのDI
- DIを使うときの注意点

---

## まず「依存」とは何か

DIを理解するには、まず「依存」という言葉を理解する必要があります。

プログラムにおける依存とは、**あるクラスや関数が動くために、別のクラスやオブジェクトを必要としている状態**のことです。

たとえば、ユーザー情報を取得する `UserService` があるとします。

```ts
class UserRepository {
  findById(id: number) {
    return {
      id,
      name: "Taro",
    };
  }
}

class UserService {
  private repository = new UserRepository();

  getUser(id: number) {
    return this.repository.findById(id);
  }
}
```

このコードでは、`UserService` が `UserRepository` を使っています。

つまり、`UserService` は `UserRepository` に依存しています。

```text
UserService
    ↓ 必要としている
UserRepository
```

ここで重要なのは、**依存すること自体は悪いことではない**という点です。

アプリケーションでは、クラスや関数が他の処理を使うのは自然なことです。

問題になりやすいのは、依存していることそのものではなく、**依存するオブジェクトをクラスの中で直接作っていること**です。

---

## DIを使わないコードの問題点

先ほどのコードをもう一度見てみます。

```ts
class UserService {
  private repository = new UserRepository();

  getUser(id: number) {
    return this.repository.findById(id);
  }
}
```

このコードは普通に動きます。

しかし、設計として見るといくつか問題があります。

`UserService` の中で `new UserRepository()` しているため、`UserService` は `UserRepository` の作り方まで知ってしまっています。

つまり、`UserService` は次の2つの責務を持ってしまっています。

1. ユーザー情報を取得する処理を行う
2. `UserRepository` を作成する

本来、`UserService` はユーザーに関するビジネスロジックに集中したいクラスです。

しかし、依存オブジェクトを自分で作っているため、依存先の生成方法まで抱え込んでしまっています。

これにより、以下のような問題が起きやすくなります。

---

## 問題1：差し替えしにくい

たとえば、テストでは本物の `UserRepository` ではなく、テスト用の `MockUserRepository` を使いたいとします。

```ts
class MockUserRepository {
  findById(id: number) {
    return {
      id,
      name: "Mock User",
    };
  }
}
```

しかし、`UserService` の中で `new UserRepository()` していると、外から簡単に差し替えることができません。

```ts
class UserService {
  private repository = new UserRepository();
}
```

このように書かれている限り、`UserService` は常に `UserRepository` を使います。

テスト用に `MockUserRepository` を使いたくても、`UserService` のコードを書き換える必要があります。

これは、変更に弱い設計です。

---

## 問題2：テストしにくい

実務では、RepositoryがDBや外部APIにアクセスすることがあります。

```ts
class UserRepository {
  async findById(id: number) {
    // 実際にはDBやAPIにアクセスする
  }
}
```

このようなRepositoryを `UserService` の中で直接作っていると、`UserService` のテストをしたいだけなのに、DBや外部APIへの接続も必要になってしまいます。

すると、テストが次のようになりがちです。

- 実行が遅い
- 外部環境に依存する
- DBの状態によって結果が変わる
- APIの障害でテストが落ちる
- テストデータの準備が面倒になる

本来、`UserService` のテストでは、`UserService` のロジックだけを確認したいはずです。

しかし、依存先を内部で直接作っていると、依存先の影響を強く受けてしまいます。

---

## 問題3：責務が増えやすい

クラスの中で依存オブジェクトを作ると、そのクラスは「何を使うか」だけでなく「どう作るか」まで知ることになります。

たとえば、Repositoryの生成に設定値が必要になったとします。

```ts
class UserRepository {
  constructor(private endpoint: string) {}
}
```

すると、`UserService` 側にもその設定が入り込む可能性があります。

```ts
class UserService {
  private repository = new UserRepository("https://api.example.com");

  getUser(id: number) {
    return this.repository.findById(id);
  }
}
```

このように、依存先の生成方法が複雑になるほど、利用する側のクラスも複雑になっていきます。

`UserService` はユーザー処理に集中したいのに、Repositoryの作り方まで気にしなければならなくなります。

---

## DIとは何か

ここでDIの登場です。

DIは **Dependency Injection** の略です。

日本語では、**依存性の注入** または **依存関係の注入** と呼ばれます。

言葉だけ見ると難しく感じますが、やっていることはシンプルです。

> DIとは、クラスや関数が必要とする依存オブジェクトを、自分で作るのではなく、外部から渡してもらう設計方法です。

先ほどのコードをDIの形に変えてみます。

```ts
class UserRepository {
  findById(id: number) {
    return {
      id,
      name: "Taro",
    };
  }
}

class UserService {
  constructor(private repository: UserRepository) {}

  getUser(id: number) {
    return this.repository.findById(id);
  }
}

const repository = new UserRepository();
const service = new UserService(repository);

console.log(service.getUser(1));
```

大きな違いはここです。

```ts
constructor(private repository: UserRepository) {}
```

`UserService` の中で `new UserRepository()` していません。

代わりに、外から `UserRepository` のインスタンスを受け取っています。

```ts
const repository = new UserRepository();
const service = new UserService(repository);
```

これがDIです。

---

## DIの流れ

DIの流れをシンプルにすると、次のようになります。

```text
1. 利用する側のクラスが、必要な依存を定義する
2. 外部で依存オブジェクトを作成する
3. 作成した依存オブジェクトを利用する側に渡す
4. 利用する側は、受け取った依存オブジェクトを使う
5. 必要に応じて、依存オブジェクトを別実装に差し替える
```

図で表すと、次のようなイメージです。

```text
外部
  ↓ UserRepositoryを作る
UserRepository
  ↓ 渡す
UserService
  ↓ 利用する
getUser()
```

記事に画像を入れる場合は、この位置にDIの流れの図を差し込むと読みやすくなります。

```md
![DIの流れ](./di-flow.png)
```

DIのポイントは、**利用する側が依存オブジェクトを作らない**ことです。

利用する側は、受け取ったものを使うだけです。

---

## DIを使うと何が嬉しいのか

DIを使うメリットはいくつかあります。

特に重要なのは、以下の4つです。

- 差し替えしやすくなる
- テストしやすくなる
- 変更に強くなる
- 責務が分かれやすくなる

順番に見ていきます。

---

## メリット1：差し替えしやすくなる

DIを使うと、依存オブジェクトを外から渡せます。

そのため、本番用とテスト用を簡単に差し替えられます。

```ts
class UserRepository {
  findById(id: number) {
    return {
      id,
      name: "Real User",
    };
  }
}

class MockUserRepository {
  findById(id: number) {
    return {
      id,
      name: "Mock User",
    };
  }
}

class UserService {
  constructor(private repository: UserRepository) {}

  getUser(id: number) {
    return this.repository.findById(id);
  }
}
```

本番では `UserRepository` を渡します。

```ts
const repository = new UserRepository();
const service = new UserService(repository);
```

テストでは `MockUserRepository` を渡します。

```ts
const mockRepository = new MockUserRepository();
const service = new UserService(mockRepository);
```

このように、`UserService` のコードを変更せずに、使うRepositoryを切り替えられます。

これがDIの大きなメリットです。

---

## インターフェースを使うとさらに柔軟になる

先ほどのコードには、少し気になる点があります。

`UserService` のコンストラクタが `UserRepository` に依存しています。

```ts
constructor(private repository: UserRepository) {}
```

これでもDIではありますが、より柔軟にするならインターフェースを使います。

```ts
interface IUserRepository {
  findById(id: number): {
    id: number;
    name: string;
  };
}

class UserRepository implements IUserRepository {
  findById(id: number) {
    return {
      id,
      name: "Real User",
    };
  }
}

class MockUserRepository implements IUserRepository {
  findById(id: number) {
    return {
      id,
      name: "Mock User",
    };
  }
}

class UserService {
  constructor(private repository: IUserRepository) {}

  getUser(id: number) {
    return this.repository.findById(id);
  }
}
```

この形にすると、`UserService` は具体的な `UserRepository` ではなく、`IUserRepository` という抽象に依存します。

```text
UserService
    ↓ 具体クラスではなく抽象に依存
IUserRepository
    ↑
UserRepository / MockUserRepository
```

これにより、`UserService` は「findByIdメソッドを持っているもの」であれば、具体的な実装を気にせず使えます。

この考え方は、設計原則でいう **依存関係逆転の原則** にもつながります。

---

## メリット2：テストしやすくなる

DIを使うと、テストが書きやすくなります。

たとえば、`UserService` のテストで本物のDBに接続したくない場合、モックを渡せます。

```ts
class MockUserRepository {
  findById(id: number) {
    return {
      id,
      name: "Test User",
    };
  }
}

const mockRepository = new MockUserRepository();
const service = new UserService(mockRepository);

const user = service.getUser(1);

console.log(user.name); // Test User
```

このテストでは、本物のDBや外部APIにアクセスしていません。

`UserService` に必要なRepositoryの代わりに、テスト用のRepositoryを渡しているだけです。

これにより、テストが次のようになります。

- 速い
- 安定する
- 外部環境に依存しない
- テストデータを用意しやすい
- ロジックだけを確認しやすい

DIは、単に設計をきれいにするためだけのものではありません。

実務では、**テストしやすいコードにするための重要な考え方**でもあります。

---

## メリット3：変更に強くなる

DIを使うと、依存先の実装を変更しても、利用する側への影響を小さくできます。

たとえば、最初はメモリ上のデータを使っていたとします。

```ts
class InMemoryUserRepository implements IUserRepository {
  findById(id: number) {
    return {
      id,
      name: "Memory User",
    };
  }
}
```

あとからAPI経由で取得する実装に変えたくなったとします。

```ts
class ApiUserRepository implements IUserRepository {
  findById(id: number) {
    return {
      id,
      name: "API User",
    };
  }
}
```

DIを使っていれば、`UserService` は変更しなくて済みます。

```ts
const repository = new ApiUserRepository();
const service = new UserService(repository);
```

変更するのは、外から渡す実装だけです。

`UserService` は `IUserRepository` に依存しているため、具体的なデータ取得方法を知る必要がありません。

これにより、コード全体が変更に強くなります。

---

## メリット4：責務が分かれやすくなる

DIを使うと、クラスの責務を分けやすくなります。

DIを使わない場合、`UserService` は依存オブジェクトの生成まで担当していました。

```ts
class UserService {
  private repository = new UserRepository();
}
```

DIを使う場合、`UserService` は受け取ったRepositoryを使うだけです。

```ts
class UserService {
  constructor(private repository: IUserRepository) {}
}
```

これにより、`UserService` はユーザーに関する処理に集中できます。

依存オブジェクトを作る責務は外側に移動します。

```text
UserService
  → ユーザー処理に集中する

外側のコード
  → どのRepositoryを使うか決める
```

このように、DIはクラスの責務を整理する助けになります。

---

## DIの主な種類

DIにはいくつか種類があります。

代表的なものは次の3つです。

- コンストラクタインジェクション
- セッターインジェクション
- メソッドインジェクション

実務では、コンストラクタインジェクションがよく使われます。

---

## コンストラクタインジェクション

コンストラクタインジェクションは、コンストラクタで依存オブジェクトを受け取る方法です。

```ts
class UserService {
  constructor(private repository: IUserRepository) {}

  getUser(id: number) {
    return this.repository.findById(id);
  }
}
```

この方法のメリットは、依存関係が分かりやすいことです。

`UserService` を作るには `IUserRepository` が必要だと、コンストラクタを見るだけで分かります。

```ts
const repository = new UserRepository();
const service = new UserService(repository);
```

また、必要な依存を渡さないとインスタンスを作れないため、依存の渡し忘れを防ぎやすいです。

基本的には、このコンストラクタインジェクションを使うことが多いです。

---

## セッターインジェクション

セッターインジェクションは、setterメソッドを使って依存オブジェクトを渡す方法です。

```ts
class UserService {
  private repository?: IUserRepository;

  setRepository(repository: IUserRepository) {
    this.repository = repository;
  }

  getUser(id: number) {
    if (!this.repository) {
      throw new Error("repository is not set");
    }

    return this.repository.findById(id);
  }
}
```

この方法では、インスタンスを作ったあとに依存オブジェクトを設定できます。

```ts
const service = new UserService();
service.setRepository(new UserRepository());
```

柔軟ではありますが、設定忘れが起きる可能性があります。

そのため、必須の依存関係にはコンストラクタインジェクションを使う方が分かりやすいです。

---

## メソッドインジェクション

メソッドインジェクションは、特定のメソッドを呼び出すときに依存オブジェクトを渡す方法です。

```ts
class UserService {
  getUser(id: number, repository: IUserRepository) {
    return repository.findById(id);
  }
}
```

この方法は、そのメソッドでだけ必要な依存を渡したい場合に使えます。

ただし、毎回引数として渡す必要があるため、何度も使う依存にはあまり向いていません。

---

## DIとDIコンテナの違い

DIを学ぶときに混乱しやすいのが、DIとDIコンテナの違いです。

この2つは同じものではありません。

```text
DI
  → 依存オブジェクトを外から渡す設計方法

DIコンテナ
  → 依存オブジェクトの生成や注入を自動で管理する仕組み
```

DIは考え方です。

DIコンテナは、そのDIを便利に実現するための仕組みです。

---

## 手動DIの例

ここまで見てきたコードは、手動でDIをしています。

```ts
const repository = new UserRepository();
const service = new UserService(repository);
```

これはDIコンテナを使っていません。

しかし、依存オブジェクトを外から渡しているため、DIです。

つまり、DIコンテナがなくてもDIはできます。

---

## DIコンテナの例

DIコンテナを使うと、依存オブジェクトの生成や注入をフレームワークが自動で行ってくれます。

たとえば、AngularではServiceをComponentに注入できます。

```ts
@Injectable({
  providedIn: "root",
})
export class UserService {
  getUser(id: number) {
    return {
      id,
      name: "Taro",
    };
  }
}
```

```ts
@Component({
  selector: "app-user",
  template: `<p>{{ user.name }}</p>`,
})
export class UserComponent {
  user = this.userService.getUser(1);

  constructor(private userService: UserService) {}
}
```

この場合、`UserComponent` の中で `new UserService()` はしていません。

AngularのDIコンテナが `UserService` を作成し、`UserComponent` に渡してくれます。

---

## NestJSでのDIの例

NestJSでもDIはよく使われます。

```ts
@Injectable()
export class UserService {
  findUser(id: number) {
    return {
      id,
      name: "Taro",
    };
  }
}
```

```ts
@Controller("users")
export class UserController {
  constructor(private readonly userService: UserService) {}

  @Get(":id")
  getUser(@Param("id") id: string) {
    return this.userService.findUser(Number(id));
  }
}
```

このコードでも、`UserController` の中で `new UserService()` はしていません。

NestJSのDIコンテナが `UserService` を作成して、`UserController` に注入してくれます。

---

## ReactにDIはあるのか

Reactには、AngularやNestJSのような標準のDIコンテナはありません。

しかし、DIの考え方自体はReactでも使えます。

たとえば、コンポーネントに必要な関数やデータ取得処理をpropsで渡すことも、広い意味ではDI的な考え方です。

```tsx
type UserListProps = {
  fetchUsers: () => Promise<string[]>;
};

function UserList({ fetchUsers }: UserListProps) {
  // fetchUsersを使ってユーザー一覧を取得する
}
```

この場合、`UserList` は自分で `fetchUsers` を作っていません。

外から渡された `fetchUsers` を使っています。

Contextを使って依存を渡すこともできます。

```tsx
const ApiClientContext = createContext<ApiClient | null>(null);

function UserPage() {
  const apiClient = useContext(ApiClientContext);

  if (!apiClient) {
    throw new Error("ApiClient is not provided");
  }

  // apiClientを使う
}
```

ReactではDIコンテナという形ではなく、propsやContextを使って依存を渡すことがあります。

## DIを使わない場合と使う場合の比較

ここで、DIを使わない場合と使う場合を比較します。

---

## DIを使わない場合

```ts
class UserService {
  private repository = new UserRepository();

  getUser(id: number) {
    return this.repository.findById(id);
  }
}
```

このコードでは、`UserService` が `UserRepository` を自分で作っています。

```text
UserService
  ├─ UserRepositoryを作る
  └─ UserRepositoryを使う
```

この設計では、`UserService` が依存先の生成方法まで知ってしまいます。

そのため、差し替えやテストがしにくくなります。

---

## DIを使う場合

```ts
class UserService {
  constructor(private repository: IUserRepository) {}

  getUser(id: number) {
    return this.repository.findById(id);
  }
}
```

このコードでは、`UserService` はRepositoryを自分で作りません。

外から渡されたRepositoryを使うだけです。

```text
外部
  └─ Repositoryを作る

UserService
  └─ Repositoryを使う
```

これにより、`UserService` の責務がシンプルになります。

また、Repositoryを差し替えやすくなります。

---

## DIを使うときの注意点

DIは便利な考え方ですが、何でもDIすればよいわけではありません。

使い方を間違えると、逆にコードが分かりづらくなることもあります。

---

## 注意点1：小さすぎる処理に無理に使わない

単純な値の変換や、非常に小さい処理にまでDIを使うと、コードが必要以上に複雑になることがあります。

たとえば、次のような単純な関数にDIを持ち込む必要はあまりありません。

```ts
function double(value: number) {
  return value * 2;
}
```

DIは、主に次のような依存に対して効果を発揮します。

- DBアクセス
- 外部APIアクセス
- ファイル操作
- ログ出力
- メール送信
- 認証処理
- 設定値に依存する処理
- テスト時に差し替えたい処理

何でもDIにするのではなく、差し替えたいもの、テストで分離したいものに使うと効果的です。

---

## 注意点2：依存が多すぎるクラスは設計を見直す

コンストラクタにたくさんの依存が並ぶ場合、そのクラスは多くの責務を持ちすぎている可能性があります。

```ts
class UserService {
  constructor(
    private userRepository: UserRepository,
    private mailService: MailService,
    private logger: Logger,
    private paymentService: PaymentService,
    private notificationService: NotificationService,
  ) {}
}
```

依存が多いこと自体が絶対に悪いわけではありません。

しかし、あまりにも多い場合は、そのクラスが色々なことをやりすぎているサインかもしれません。

その場合は、クラスを分割できないか考えるとよいです。

---

## 注意点3：DIコンテナに頼りすぎると追いづらくなる

DIコンテナを使うと、依存オブジェクトを自動で注入してくれるため便利です。

しかし、自動で注入される分、どこで何が作られているのか分かりづらくなることもあります。

特に大きなアプリケーションでは、以下の点を意識するとよいです。

- どのクラスがどの依存を必要としているか
- どの実装が注入されているか
- スコープはどうなっているか
- シングルトンなのか、リクエストごとなのか
- テスト時にどう差し替えるか

DIコンテナは便利ですが、魔法のように使うと理解しづらくなります。

依存関係を明確に保つことが大切です。

---

## DIは「目的」ではなく「手段」

DIを学ぶと、つい何でもDIにしたくなることがあります。

しかし、DIは目的ではありません。

DIは、コードを次のようにするための手段です。

- テストしやすくする
- 変更に強くする
- 差し替えしやすくする
- 責務を分けやすくする
- クラス同士の結合を弱くする

つまり、DIを使うこと自体がゴールではありません。

大事なのは、DIによってコードが読みやすく、変更しやすく、保守しやすくなることです。

---

## まとめ

DIとは、**クラスや関数が必要とする依存オブジェクトを、自分で作らず外から渡してもらう設計方法**です。

DIを使わない場合、利用する側のクラスが依存オブジェクトを自分で作ることになります。

```ts
class UserService {
  private repository = new UserRepository();
}
```

この場合、`UserService` は `UserRepository` の作り方まで知ってしまいます。

その結果、差し替えやテストが難しくなります。

DIを使う場合は、依存オブジェクトを外から渡します。

```ts
class UserService {
  constructor(private repository: IUserRepository) {}
}
```

これにより、`UserService` は受け取ったRepositoryを使うだけになります。

DIのメリットは次の通りです。

- 依存オブジェクトを差し替えやすい
- テストしやすい
- 変更に強い
- 責務を分けやすい
- クラス同士の結合を弱くできる

また、DIとDIコンテナは別物です。

```text
DI
  → 依存を外から渡す設計方法

DIコンテナ
  → 依存の生成や注入を自動管理する仕組み
```

AngularやNestJSなどのフレームワークでは、DIコンテナによって依存関係の管理が自動化されています。

ただし、DIは何でも使えばよいものではありません。

小さすぎる処理に無理に使うと、かえって複雑になります。

DIはあくまで、コードを柔軟にするための手段です。

まずは次の一文で理解しておくとよいです。

> DIとは、必要なものを自分で作らず、外から渡してもらう設計である。

この考え方を押さえておくと、Angular、NestJS、SpringなどのDIを使うフレームワークも理解しやすくなります。
