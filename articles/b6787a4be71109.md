Dependency Injection（DI、依存性注入）とは、ある処理が必要とするオブジェクトを、その処理の内部で固定的に生成せず、外から渡す設計です。

DIの目的は「newをなくすこと」ではありません。依存の選択と利用を分離し、変更・テスト・ライフサイクル管理をしやすくすることです。

## まず依存とは何か

```ts
type User = {
  id: number;
  name: string;
};

class UserRepository {
  async findById(id: number): Promise<User> {
    const response = await fetch(`/api/users/${id}`);
    return response.json();
  }
}

class UserService {
  private readonly repository = new UserRepository();

  async getDisplayName(id: number): Promise<string> {
    const user = await this.repository.findById(id);
    return user.name.trim();
  }
}
```

`UserService` は `UserRepository` がなければ動きません。この関係が依存です。

問題は依存が存在することではなく、`UserService` が利用方法に加えて生成方法まで決めていることです。

- テストでも実際の通信が必要になる
- 保存先を変更するには `UserService` を編集する
- repositoryの設定やライフサイクルまでserviceが抱える

## constructor injection

依存をconstructorから受け取る形へ変えます。

```ts
interface UserReader {
  findById(id: number): Promise<User>;
}

class UserService {
  constructor(private readonly userReader: UserReader) {}

  async getDisplayName(id: number): Promise<string> {
    const user = await this.userReader.findById(id);
    return user.name.trim();
  }
}

class ApiUserReader implements UserReader {
  async findById(id: number): Promise<User> {
    const response = await fetch(`/api/users/${id}`);

    if (!response.ok) {
      throw new Error(`failed to fetch user: ${response.status}`);
    }

    return response.json();
  }
}

const userService = new UserService(new ApiUserReader());
```

`UserService` は「`UserReader` として使えるものが必要」とだけ宣言し、具体的な取得方法を選びません。

どの実装を組み合わせるか決める場所をcomposition rootと呼ぶことがあります。上の最後の1行が、その最小例です。

## テストで差し替える

```ts
class InMemoryUserReader implements UserReader {
  constructor(private readonly users: readonly User[]) {}

  async findById(id: number): Promise<User> {
    const user = this.users.find((candidate) => candidate.id === id);

    if (!user) {
      throw new Error("user not found");
    }

    return user;
  }
}

const service = new UserService(
  new InMemoryUserReader([{ id: 1, name: " Taro " }]),
);

console.log(await service.getDisplayName(1)); // Taro
```

serviceのテストでネットワークへ接続せず、必要な条件を小さく再現できます。

ただしテストダブルを使えること自体より、serviceが「名前を整形する」という責務へ集中できたことが重要です。

## DIとDependency Inversion Principleは別

DIとDIP（依存関係逆転の原則）は関連しますが、同じものではありません。

- DI：依存を外から渡す手段
- DIP：上位方針が下位の具体実装へ直接依存せず、両者が抽象へ依存するという設計原則

```ts
class UserService {
  constructor(private readonly userReader: UserReader) {}
}
```

この例では、serviceが具体的な `ApiUserReader` ではなく `UserReader` へ依存しています。

一方、具体クラスをそのままconstructorへ渡すだけでもDIではあります。必ずinterfaceが必要という意味ではありません。差し替えの可能性と抽象化コストを比較します。

## DIとDIコンテナは別

DIコンテナは、依存の登録、生成、注入、ライフサイクルを管理する仕組みです。

```text
DI
└─ 依存を外から渡す設計

DIコンテナ
└─ 依存の解決と生成を自動化する道具
```

小規模なコードでは、手動で組み立てるだけで十分です。

```ts
const userReader = new ApiUserReader();
const userService = new UserService(userReader);
```

依存が増え、scopeや破棄、設定の分岐を管理する必要が出たときに、コンテナの価値が高まります。

## NestJSでのDI

NestJSではproviderをmoduleへ登録し、constructorから受け取れます。

```ts
@Injectable()
class UserService {
  constructor(
    @Inject(USER_READER)
    private readonly userReader: UserReader,
  ) {}
}
```

TypeScriptのinterfaceは実行時に消えるため、interfaceを注入対象として識別するにはtokenなどが必要です。具体クラスを型として使う場合と同じ感覚でinterfaceを指定できるわけではありません。

また、singleton、request scope、transientなど、providerのscopeによってインスタンス寿命が変わります。コンテナを使う場合は「何が注入されるか」だけでなく「いつ生成・破棄されるか」も確認します。

## ReactのpropsやContextはDIか

コンポーネントが必要な処理をpropsから受け取る形は、依存を外から渡すという意味でDI的です。

```tsx
type UserButtonProps = {
  loadUser: (id: number) => Promise<User>;
};

function UserButton({ loadUser }: UserButtonProps) {
  const handleClick = async () => {
    const user = await loadUser(1);
    console.log(user.name);
  };

  return <button onClick={handleClick}>Load</button>;
}
```

ただし、すべてのpropsやContextをDIと呼ぶ必要はありません。UIデータを渡しているだけなのか、外部I/Oやサービスの実装を注入しているのかを区別すると、議論が明確になります。

## constructor以外の注入

### 引数として渡す

```ts
async function getDisplayName(
  id: number,
  userReader: UserReader,
): Promise<string> {
  const user = await userReader.findById(id);
  return user.name.trim();
}
```

関数単位の小さな依存には、これが最も単純です。

### setterやpropertyへ後から設定する

任意依存や循環関係で使われることがありますが、「設定前に使える不完全な状態」を作りやすくなります。必須依存はconstructorで要求する方が安全です。

### メソッド引数として渡す

特定操作にだけ必要な依存なら、そのメソッドの引数として渡す方がscopeを明確にできます。

## DIを使いすぎる兆候

- 値を1つ計算するだけなのにinterfaceと実装が何層もある
- 実装が1つで変更理由もないのに、抽象化だけ増えている
- コンテナの登録を見ないと処理を追えない
- service locatorからどこでも依存を取得している
- constructor引数が増え続けている

特にservice locatorは、必要な依存が関数やconstructorのシグネチャへ現れません。コンテナそのものを業務コードへ渡すより、必要な依存を明示的に注入します。

## 判断基準

DIを検討しやすい依存は次の通りです。

- DB、HTTP、ファイルなどの外部I/O
- 時刻、乱数、環境設定
- ロガーや通知
- テストで制御したい処理
- ライフサイクル管理が必要なクライアント

一方、文字列整形や小さな純粋関数までクラス化して注入する必要はありません。

## まとめ

- 依存とは、処理が動くために必要な別の値・オブジェクト
- DIは、その依存を内部で固定生成せず外から渡す設計
- 生成と利用を分けると、変更とテストがしやすくなる
- DI、DIP、DIコンテナは同じものではない
- 小規模なら引数や手動組み立てで十分
- 抽象化とコンテナには追跡コストもある

DIは目的ではなく、依存関係を明示し、適切な場所で組み立てるための手段です。
