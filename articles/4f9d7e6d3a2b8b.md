`setTimeout`の待ち時間を0ミリ秒にしても、コールバックはすぐに実行されません。`Promise.then()`と一緒に使うと、コードに書いた順とも違う結果になります。

```js
console.log("A");

setTimeout(() => console.log("B"), 0);

Promise.resolve().then(() => console.log("C"));

console.log("D");
```

出力は `A → D → C → B` です。この順番を決める仕組みが、Event Loopです。

この記事ではブラウザ上のJavaScriptを対象に、タスクとマイクロタスクがいつ実行されるのかを追います。ゴールは、ログの出力順と、重い処理で画面が固まる理由を同じ仕組みから説明することです。

## Event Loopは、実行する仕事の順番を調整する

<!--
この節で先に結論を置く。

- Event Loopは非同期処理そのものを実行する装置ではない
- 実行可能になった仕事へ、いつ実行機会を渡すか調整する
- ブラウザのメインスレッドでは、JavaScript、ユーザー操作への応答、描画などが実行機会を取り合う
-->

## 実行順を理解するための登場人物は4つ

<!--
図を一枚入れ、次の関係を整理する。

1. 実行中のJavaScriptとコールスタック
2. タイマーや通信を扱うブラウザ側の機能
3. setTimeoutやイベントなどが入るタスク
4. Promiseの継続処理などが入るマイクロタスク

用語の暗記ではなく、「処理を待つ場所」と「コードを実行する場所」を分けるために説明する。
-->

## 1回の流れは「タスク1つ、マイクロタスク、次の仕事」

<!--
記事の中心。概念モデルとして次の順序を図と本文で示す。

1. 実行できるタスクを一つ選ぶ
2. そのタスクに含まれるJavaScriptを最後まで実行する
3. たまったマイクロタスクを空になるまで実行する
4. ブラウザが必要に応じて描画などを進める
5. 次のタスクへ進む

描画はループのたびに必ず行われるわけではない、と補足する。
-->

## コードを一行ずつ追うと、出力順が決まる

<!--
冒頭のコードへ戻る。「現在の処理」「タスク」「マイクロタスク」「出力」の4列で状態表を作る。

- AとDは現在のJavaScriptでそのまま出力される
- Promiseの処理はマイクロタスクへ入る
- setTimeoutの処理は後で実行するタスクになる
- 現在の処理が終わると、次のタスクより先にマイクロタスクが実行される

読者が自力で A → D → C → B を再現できるところまで説明する。
-->

## `setTimeout(0)`は「今すぐ実行」という指定ではない

<!--
0ミリ秒は実行時刻の予約ではない。待ち時間の条件を満たした後、コールバックをタスクとして実行できる状態にする指定だと説明する。

「最短でも指定時間を待つ」「順番が回るまでさらに待つ」の二段階に分ける。
-->

## `await`の後ろもマイクロタスクとして再開する

<!--
短いコードを追加し、awaitの前後で処理が分かれる様子を追う。

- awaitより前は同期的に進む
- 待っているPromiseが解決すると、続きが実行可能になる
- 続きはその場で割り込まず、マイクロタスクとして再開する

新しいモデルを増やさず、前節までの仕組みでasync/awaitを説明し直す。
-->

## 長い処理が続くと、画面へ順番が回らない

<!--
実務上の意味を示す。

- 長い同期処理が一つのタスクを占有すると、クリック処理や描画を進められない
- マイクロタスクを増やし続けた場合も、次のタスクや描画が遅れる可能性がある
- 非同期構文を使うだけでは、CPU負荷の高い計算は軽くならない

必要ならWeb Workerの記事へつなげる。
-->

## Node.jsのEvent Loopは同じ図だけで説明し切れない

<!--
Node.jsにはタイマーやI/Oなどを扱う固有のフェーズがある。本記事ではブラウザと共通する考え方だけに触れ、詳しい処理順は別記事の範囲だと明示する。この節は短くする。
-->

## 迷ったら、3つの場所へ処理を書き分ける

<!--
冒頭の疑問を一文で回収する。

実行順に迷ったときは、各処理を次の三つへ書き分ける。

- 今実行しているJavaScript
- 次回以降に実行するタスク
- 現在の処理後に確認されるマイクロタスク

最後に「Event Loopは、実行可能になった仕事をいつ実行するか調整する仕組み」と再統合する。
-->
