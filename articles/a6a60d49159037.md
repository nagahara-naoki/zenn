1つの目的を達成するために、細かい処理をいくつも呼び出していませんか？

例えば、ユーザー情報を取得して画面に表示する処理を考えてみます。

```js
const cacheKey = `user:${id}`;

let user = cache.get(cacheKey);

if (!user) {
  const response = await fetch(`/api/users/${id}`);

  if (!response.ok) {
    throw new Error("ユーザー取得に失敗しました");
  }

  user = await response.json();

  cache.set(cacheKey, user);
}

renderUser(user);
```

これでも動きます。

でも、実際のアプリではもっと複雑になります。

- loading状態を管理する
- error状態を管理する
- キャッシュする
- stale状態を判定する
- 再取得する
- window focus時にrefetchする
- retryする
- 複数コンポーネントで同じデータを共有する

これを毎回コンポーネント側で書くのは大変です。

そこで使えるのが **Facadeパターン** です。

---

## Facadeパターンとは？

Facadeパターンは、**複雑な内部処理を隠し、外から使いやすいシンプルな入口を用意するパターン**です。

簡単に言うと、

> 利用者には「これを呼べばいい」という窓口だけを見せる

という考え方です。

例えば、ユーザー登録処理なら、内部ではいろいろな処理が動くかもしれません。

```js
validateUser(user);
checkDuplicateEmail(user.email);
saveUser(user);
createDefaultSettings(user);
sendWelcomeEmail(user);
writeLog(user);
```

でも、呼び出し側にはこう見せます。

```js
await registerUser(user);
```

呼び出し側は、内部の細かい手順を知る必要がありません。

これがFacadeパターンです。

---

## Facadeを使わない場合の問題

ユーザー登録処理を、画面側でそのまま組み立てている例です。

```js
async function handleSubmit(user) {
  validateUser(user);

  const exists = await checkDuplicateEmail(user.email);

  if (exists) {
    throw new Error("このメールアドレスは既に使われています");
  }

  const savedUser = await saveUser(user);

  await createDefaultSettings(savedUser);
  await sendWelcomeEmail(savedUser);

  console.log("ユーザーを登録しました");
}
```

このコードには、次の問題があります。

1. 画面側が登録処理の手順を知りすぎている
2. 同じ手順を別画面でも使うと重複する
3. 処理の順番を間違えるとバグになる

たとえば、別の画面でもユーザー登録をしたくなったら、同じような処理をもう一度書くことになります。

これは保守しづらいです。

---

## Facade関数で改善する

ユーザー登録に必要な処理を、`registerUser` にまとめます。

```js
async function registerUser(user) {
  validateUser(user);

  const exists = await checkDuplicateEmail(user.email);

  if (exists) {
    throw new Error("このメールアドレスは既に使われています");
  }

  const savedUser = await saveUser(user);

  await createDefaultSettings(savedUser);
  await sendWelcomeEmail(savedUser);

  return savedUser;
}
```

画面側はこうなります。

```js
async function handleSubmit(user) {
  const savedUser = await registerUser(user);

  console.log("ユーザーを登録しました", savedUser);
}
```

画面側は「ユーザーを登録する」という目的だけに集中できます。

内部でどの順番で何を呼ぶかは、`registerUser` が担当します。

---

## Facadeで何が良くなるのか？

### 1. 呼び出し側がシンプルになる

Facadeなしの場合です。

```js
validateUser(user);
checkDuplicateEmail(user.email);
saveUser(user);
createDefaultSettings(user);
sendWelcomeEmail(user);
```

Facadeありの場合です。

```js
await registerUser(user);
```

呼び出し側の意図がかなり読みやすくなります。

---

### 2. 内部手順を隠せる

ユーザー登録の細かい処理は、Facadeの中に閉じ込められます。

```js
async function registerUser(user) {
  // 登録に必要な処理をここにまとめる
}
```

呼び出し側は、登録処理の内部手順を知りすぎなくて済みます。

---

### 3. 仕様変更に強くなる

例えば、登録後に管理者通知を追加したい場合です。

```js
async function registerUser(user) {
  validateUser(user);

  const savedUser = await saveUser(user);

  await createDefaultSettings(savedUser);
  await sendWelcomeEmail(savedUser);
  await notifyAdmin(savedUser);

  return savedUser;
}
```

呼び出し側は変わりません。

```js
await registerUser(user);
```

変更箇所をFacade内に集められるのが強みです。

---

## Facadeは「ただ関数にまとめるだけ」ではない

Facadeは、単に関数化することではありません。

大事なのは、**複雑な内部処理を隠し、利用者にとって分かりやすい入口を設計すること** です。

例えば、これは普通の関数です。

```js
function formatDate(date) {
  return date.toLocaleDateString();
}
```

これはFacadeとは言いにくいです。

一方、これはFacadeに近いです。

```js
async function login(email, password) {
  validateLoginForm(email, password);

  const result = await loginApi(email, password);

  saveToken(result.token);
  saveCurrentUser(result.user);
  redirectToHome();

  return result.user;
}
```

内部では複数の処理を呼んでいます。

でも、外側には `login(email, password)` という入口だけを見せています。

---

## 有名OSSではどう使われている？

Facadeパターンに近い考え方は、**TanStack Queryの `useQuery`** に見ることができます。

TanStack Queryは、サーバー状態の取得、キャッシュ、再取得、retry、stale管理などを扱うライブラリです。

Reactでは、次のように使います。

```tsx
import { useQuery } from "@tanstack/react-query";

function UserProfile({ id }) {
  const {
    data: user,
    isPending,
    isError,
    error,
  } = useQuery({
    queryKey: ["user", id],
    queryFn: () => fetchUser(id),
  });

  if (isPending) {
    return <p>Loading...</p>;
  }

  if (isError) {
    return <p>{error.message}</p>;
  }

  return <p>{user.name}</p>;
}
```

呼び出し側は、`useQuery` に `queryKey` と `queryFn` を渡すだけです。

でも、裏側ではかなり多くのことが行われます。

---

## useQueryをFacadeとして見る

`useQuery` は、Reactコンポーネントにとってかなりシンプルな入口です。

```tsx
const result = useQuery({
  queryKey: ["user", id],
  queryFn: () => fetchUser(id),
});
```

この1つのHookの裏側には、次のような処理があります。

- query keyに対応するキャッシュを探す
- データがなければfetchする
- loading / error / success状態を管理する
- stale状態を管理する
- 必要に応じてrefetchする
- retryする
- 複数コンポーネントで同じデータを共有する
- コンポーネントに結果オブジェクトを返す

これらをコンポーネント側で毎回書く必要はありません。

`useQuery` という入口にまとまっています。

これがFacade的です。

---

## TanStack Queryが隠している複雑さ

TanStack Query公式サイトでは、Queryは非同期データに対して、cache、lifecycle、fetching、sharing、refetching、mutating、observingのための宣言的APIを提供すると説明されています。

つまり、server stateにはかなり多くの課題があります。

```txt
server state
  ↓
remote
  ↓
shared
  ↓
cached
  ↓
refetched
  ↓
invalidated
  ↓
stale
```

これを自前で全部扱うと大変です。

`useQuery` は、その複雑さをHook APIとして隠しています。

```tsx
const { data, isPending, isError } = useQuery({
  queryKey: ["todos"],
  queryFn: fetchTodos,
});
```

これだけで、コンポーネント側は必要な状態を受け取れます。

---

## QueryCacheを直接触らなくてよい

TanStack Queryには `QueryCache` という低レベルな仕組みがあります。

公式ドキュメントでは、`QueryCache` はTanStack Queryのstorage mechanismであり、queryのdata、meta information、stateを保存すると説明されています。

ただし、通常は `QueryCache` を直接操作せず、特定のcacheには `QueryClient` を使うと説明されています。

そして、Reactコンポーネントではさらに `useQuery` を使います。

```tsx
useQuery({
  queryKey: ["posts"],
  queryFn: fetchPosts,
});
```

つまり、利用者は低レベルなcacheの詳細を直接扱わなくてもよいのです。

```txt
QueryCache
  ↓
QueryClient
  ↓
useQuery
  ↓
React component
```

このように、内部の複雑さを段階的に隠して、Reactユーザーには `useQuery` という使いやすい入口を提供しています。

---

## useQueryの戻り値もFacade的

`useQuery` は、ただdataだけを返すわけではありません。

公式ドキュメントでは、戻り値として次のような状態が説明されています。

- `status`
- `isPending`
- `isSuccess`
- `isError`
- `data`
- `error`
- `isStale`
- `isFetching`
- `refetch`

コンポーネント側では、これらを使ってUIを分岐できます。

```tsx
if (isPending) {
  return <p>Loading...</p>;
}

if (isError) {
  return <p>Error</p>;
}
```

内部のquery状態を、Reactで扱いやすい結果オブジェクトとしてまとめて返している点もFacade的です。

---

## 補足：Redux ToolkitのconfigureStoreもFacade的

補足として、Redux Toolkitの `configureStore` もFacade的に見ることができます。

Redux storeを手作業で設定しようとすると、いろいろな処理が必要です。

- root reducerを作る
- middlewareを設定する
- thunkを追加する
- DevToolsを有効にする
- enhancerを組み合わせる
- storeを作る

Redux Toolkitでは、次のように書けます。

```ts
import { configureStore } from "@reduxjs/toolkit";
import rootReducer from "./reducers";

const store = configureStore({
  reducer: rootReducer,
});
```

Redux Toolkit公式ドキュメントでは、`configureStore` はreducerオブジェクトを渡した場合に `combineReducers` でroot reducerを作り、middlewareを `applyMiddleware` に渡し、DevToolsも扱うと説明されています。

つまり、Redux store setupの複雑さを `configureStore` という入口にまとめています。

これはFacade的です。

---

## configureStoreをFacadeとして見る

`configureStore` を使う側は、細かいRedux setupを直接組み立てません。

```ts
const store = configureStore({
  reducer: {
    user: userReducer,
    posts: postsReducer,
  },
});
```

内部では、次のような処理が行われます。

- slice reducersをroot reducerにまとめる
- default middlewareを追加する
- middleware enhancerを作る
- Redux DevToolsを設定する
- 最終的にstoreを作る

利用者は、Reduxの低レベルな設定を毎回書かなくて済みます。

これもFacadeパターンに近い考え方です。

---

## 実務でFacadeを使うならどこ？

Facadeパターンは、次のような場面で使いやすいです。

- ユーザー登録処理
- ログイン処理
- ファイルアップロード処理
- 注文確定処理
- 決済処理
- APIクライアント
- 外部サービス連携
- 複雑な初期化処理

例えば、ログイン処理です。

```js
async function login(email, password) {
  validateLoginForm(email, password);

  const result = await loginApi(email, password);

  saveToken(result.token);
  saveCurrentUser(result.user);

  return result.user;
}
```

呼び出し側はこうです。

```js
const user = await login(email, password);
```

ログインに必要な細かい手順を、`login` という入口にまとめられます。

---

## 使いすぎには注意

Facadeは便利ですが、何でも1つにまとめればよいわけではありません。

悪い例です。

```js
const appFacade = {
  login() {},
  logout() {},
  createPost() {},
  deletePost() {},
  uploadFile() {},
  sendNotification() {},
  exportCsv() {},
  importCsv() {},
};
```

関係ない処理まで1つに集めると、巨大な「何でも屋」になります。

Facadeは、関連する一連の処理をまとめるものです。

また、名前が曖昧なFacadeも危険です。

```js
await execute(data);
await process(user);
await handle(input);
```

これでは何が起きるのか分かりません。

良いFacadeは、名前から目的が分かります。

```js
await registerUser(user);
await uploadProfileImage(file);
await checkoutCart(cart);
```

Facadeは、内部を隠すからこそ、名前がとても重要です。

---

## まとめ

Facadeパターンは、**複雑な内部処理を隠し、外から使いやすいシンプルな入口を用意するパターン**です。

TanStack Queryの `useQuery` は、server stateのfetch、cache、stale管理、retry、refetch、結果状態の管理などをHook APIにまとめています。

利用者は、低レベルな `QueryCache` や細かいfetch状態管理を直接扱わず、`useQuery` という入口から必要な情報を受け取れます。

Redux Toolkitの `configureStore` も、Redux store setupの複雑さを1つのAPIにまとめるFacade的な例です。

Facadeで大事なのは、ただ関数にまとめることではありません。

大事なのは、**利用者にどの入口を見せると分かりやすいかを設計すること** です。

複数の処理を呼び出し側が毎回組み立てているなら、こう考えてみるとよいです。

> この一連の処理、1つの分かりやすい入口にまとめた方がよくない？

そう思ったときが、Facadeパターンを使うタイミングです！
