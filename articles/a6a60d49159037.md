Facadeは、複数のオブジェクトや手順から成るsubsystemに、用途に合った小さな入口を提供するパターンです。

単にコードを関数へ移すのではなく、利用側が知る必要のない順序・依存・例外処理を境界の内側へまとめます。

## 複雑さが利用側へ漏れた例

```ts
async function handleCheckout(cartId: string): Promise<void> {
  const cart = await cartRepository.findById(cartId);
  const inventory = await inventoryService.reserve(cart.items);
  const payment = await paymentService.charge(cart.total);
  await orderRepository.save({ cart, inventory, payment });
  await mailService.sendReceipt(payment.customerId);
}
```

各画面やAPI handlerがこの手順を組み立てると、順序、エラー処理、重複実行防止が散らばります。

## Facadeを作る

```ts
class CheckoutFacade {
  constructor(
    private readonly carts: CartRepository,
    private readonly inventory: InventoryService,
    private readonly payments: PaymentService,
    private readonly orders: OrderRepository,
  ) {}

  async checkout(cartId: string): Promise<Order> {
    const cart = await this.carts.findById(cartId);
    const reservation = await this.inventory.reserve(cart.items);

    try {
      const payment = await this.payments.charge(cart.total);
      return await this.orders.save({ cart, reservation, payment });
    } catch (error) {
      await this.inventory.release(reservation.id);
      throw error;
    }
  }
}
```

利用側の入口は小さくなります。

```ts
const order = await checkoutFacade.checkout(cartId);
```

Facadeは内部の複雑さを消したのではありません。責任を持って扱う場所を決めました。

## 良いFacadeの条件

- 利用側のユースケースに合った名前を持つ
- subsystemの型や実装詳細を必要以上に返さない
- 重要な失敗を握りつぶさない
- 内部コンポーネントを個別利用する道を不必要に禁止しない
- 何でも入る巨大serviceにならない

Facadeが業務ルールを持つapplication serviceになる場合もあります。パターン名より、責務の境界を明示することが重要です。

## TanStack QueryのuseQueryをFacade的に読む

```tsx
function UserProfile({ userId }: { userId: number }) {
  const query = useQuery({
    queryKey: ["user", userId],
    queryFn: () => fetchUser(userId),
  });

  if (query.isPending) return <p>Loading...</p>;
  if (query.isError) return <p>{query.error.message}</p>;

  return <p>{query.data.name}</p>;
}
```

`useQuery` の背後には、QueryClient、QueryCache、observers、retry、stale判定、refetchなどの仕組みがあります。

コンポーネントはそれらを直接組み立てず、query keyとquery functionを中心としたAPIから利用します。この点はFacade的です。

ただし `useQuery` はReact向けhookであり、GoF Facadeの公式実装例として説明されているわけではありません。複雑なsubsystemへ目的別APIを提供する考え方を学ぶための対応付けです。

## 戻り値も入口の一部

Facadeは入力だけでなく、返す情報も設計します。

`useQuery` はdataだけでなく、`isPending`、`isError`、`error`、`refetch` など、コンポーネントが必要とする状態をまとめて返します。

自作Facadeでも内部オブジェクトをそのまま漏らさず、利用側が判断できる小さなresult typeを用意します。

```ts
type CheckoutResult =
  | { ok: true; orderId: string }
  | { ok: false; reason: "out_of_stock" | "payment_failed" };
```

## configureStoreもFacade的

Redux Toolkitの `configureStore` は、reducer、middleware、DevToolsなどのstore setupへ1つの入口を提供します。

```ts
const store = configureStore({
  reducer: {
    users: usersReducer,
    cart: cartReducer,
  },
});
```

低レベルAPIを個別に組み合わせるより、推奨構成を簡潔に作れます。

## 使うべき場面

- 同じ複数手順を複数の利用側が組み立てている
- 操作順序やrollbackを一元管理したい
- 外部SDKの広いAPIを用途別に絞りたい
- UIからinfraの詳細を隠したい

## 使わなくてよい場面

単一関数を別名で呼ぶだけのwrapperは、価値より間接層が増えることがあります。

```js
const getUser = (id) => api.getUser(id);
```

変換、ポリシー、エラー処理、複数手順の調整など、Facadeが引き受ける明確な責務があるかを確認します。

## まとめ

Facadeは、複雑さを隠して存在しないことにするパターンではありません。

- subsystemへ用途に合った入口を作る
- 手順と失敗処理を一貫させる
- 利用側へ必要な情報だけ返す
- 巨大な万能serviceにしない
