状態が変わったとき、表示更新、保存、監視、通知など複数の処理を動かしたい場面があります。変更元がそれらを直接呼ぶと、利用側の追加・削除のたびに変更元まで修正しなければなりません。一方、イベントを導入するだけで安心とも限りません。解除忘れ、通知順序、listenerの例外、通知中の登録変更、非同期処理の競合まで決める必要があります。

Observer（オブザーバー）は、ある対象の変化を複数の購読者へ通知する振る舞いパターンです。本記事ではTypeScriptで小さなSubjectを作り、購読解除、型付きevent、例外方針、再入可能性、テストまで発展させます。Node.jsのEventEmitterとRxJSも公式資料に照らして読み、古典的なObserverとの共通点と違いを明確にします。

## 変更元が利用側を直接知る問題

ユーザー情報の更新後に3つの処理を行う例です。

```ts
type User = Readonly<{ id: string; name: string }>;

function updateUserBefore(user: User): void {
  renderUser(user);
  saveUserToStorage(user);
  sendUserAnalytics(user);
}
```

`updateUserBefore` は、更新という中心責務だけでなく、UI、保存先、分析基盤を知っています。通知先を増やすたびに変更し、browser以外で再利用するときは不要な依存を外さなければなりません。testでは3つすべてを準備する必要があります。

単にcallback配列を公開する案もありますが、外部から配列を消去・並べ替えでき、重複登録や解除の規則も不明です。Observerを導入するなら、購読と解除をAPIとして設計します。

```ts
const listeners: Array<(user: User) => void> = [];

// 公開配列は誰でも破壊できる
listeners.length = 0;
```

## Observerを正確に定義する

GoFのObserverは、SubjectとObserverの間に1対多の依存関係を定義し、Subjectの状態が変わると登録済みObserverへ通知します。Subjectは具体的な利用処理ではなく、共通のObserver契約だけを知ります。購読者を実行時に追加・削除できるため、変更元と利用側の直接依存を弱められます。

通知に値を含めるpush型と、通知後にObserverがSubjectから状態を読むpull型があります。本記事は値を引数で渡すpush型を採用します。JavaScriptではObserverをclassにせず、関数listenerとして表すのが自然です。

Observerは「疎結合にする魔法」ではありません。通知名、payload、同期性、順序、失敗、解除というevent契約を共有します。直接呼び出しから時間的な結合が見えにくくなるため、契約を明示しなければデバッグはむしろ難しくなります。

## 最小のSubjectを実装する

`Set` でlistenerを保持し、`subscribe` が解除関数を返す形にします。解除を別APIとして探させず、購読の結果として受け取れるため、cleanupを近くへ書けます。

```ts
type Listener<T> = (value: T) => void;
type Unsubscribe = () => void;

class Subject<T> {
  private readonly listeners = new Set<Listener<T>>();

  subscribe(listener: Listener<T>): Unsubscribe {
    this.listeners.add(listener);
    let active = true;

    return () => {
      if (!active) return;
      active = false;
      this.listeners.delete(listener);
    };
  }

  notify(value: T): void {
    for (const listener of [...this.listeners]) {
      listener(value);
    }
  }
}
```

利用側は必要な期間だけ購読します。解除関数を複数回呼んでも安全なidempotent設計にしてあります。

```ts
const users = new Subject<User>();

const unsubscribe = users.subscribe((user) => {
  console.log("updated", user.id, user.name);
});

users.notify({ id: "u_1", name: "Ada" });
unsubscribe();
unsubscribe(); // 何も起きない
users.notify({ id: "u_2", name: "Lin" }); // 通知されない
```

`notify` でSetのsnapshotを作るのは意図的です。listenerが通知中に自分や別listenerを解除しても、現在の通知対象を安定させます。この実装では、通知開始時に登録されていたlistenerは、その途中で解除されても今回だけは呼ばれます。通知中に追加されたlistenerは次回からです。別の意味も選べますが、仕様とtestを揃える必要があります。

## 型付きeventへ発展させる

eventが増えたとき、event名とpayloadを別々のUnionで定義すると誤った組み合わせを許しがちです。event mapを1つ定義し、keyに応じてpayload型を決めます。

```ts
type UserEvents = {
  updated: User;
  deleted: { id: string };
  failed: { id: string; error: Error };
};

class TypedEventBus<Events extends object> {
  private readonly listeners: {
    [K in keyof Events]?: Set<(payload: Events[K]) => void>;
  } = {};

  on<K extends keyof Events>(
    type: K,
    listener: (payload: Events[K]) => void,
  ): Unsubscribe {
    const set = (this.listeners[type] ??= new Set());
    set.add(listener);
    return () => set.delete(listener);
  }

  emit<K extends keyof Events>(type: K, payload: Events[K]): void {
    const snapshot = [...(this.listeners[type] ?? [])];
    for (const listener of snapshot) listener(payload);
  }
}
```

```ts
const userEvents = new TypedEventBus<UserEvents>();

userEvents.on("deleted", ({ id }) => console.log("deleted", id));
userEvents.emit("deleted", { id: "u_1" });

// 型エラー：deletedのpayloadにnameは定義されていない
// userEvents.emit("deleted", { name: "Ada" });
```

event mapは便利ですが、アプリ全体の万能busへすべてを集めると、誰が何を発行し、誰が依存するか分からなくなります。featureやlifecycleなど意味のある範囲で所有し、公開するeventを絞ります。業務上必須の手順を「誰かが購読しているはず」の暗黙eventへしないことも重要です。

## 通知中の例外をどう扱うか

最小実装では、1つのlistenerがthrowすると、その時点で `notify` が終了し、後続listenerは呼ばれません。これは分かりやすい一方、監視listenerの不具合が画面更新を止める可能性があります。逆に例外を握りつぶすと障害へ気づけません。

用途に応じて方針を選びます。独立した通知先をすべて実行したいなら、errorを収集し、最後に `AggregateError` として返せます。

```ts
class ResilientSubject<T> {
  private readonly listeners = new Set<Listener<T>>();

  subscribe(listener: Listener<T>): Unsubscribe {
    this.listeners.add(listener);
    return () => this.listeners.delete(listener);
  }

  notify(value: T): void {
    const errors: unknown[] = [];
    for (const listener of [...this.listeners]) {
      try {
        listener(value);
      } catch (error) {
        errors.push(error);
      }
    }
    if (errors.length > 0) {
      throw new AggregateError(errors, "one or more observers failed");
    }
  }
}
```

この方針でも、発行元がerrorを扱わなければ最終的には失敗します。logだけして成功扱いにする、最初のerrorで停止する、すべて実行して集約する、listenerごとに隔離queueへ送るなど、用途ごとに決めます。課金や在庫確保のように一連の成功が必要なら、Observerより明示的なworkflowやtransactionを使うべきです。

## 非同期listenerは別の契約にする

同期 `emit` がasync関数を受け入れると、返されたPromiseを無視し、rejectionが未処理になる危険があります。同期と非同期を曖昧に混ぜず、非同期版では完了方法を契約へ含めます。

```ts
type AsyncListener<T> = (value: T) => Promise<void>;

class AsyncSubject<T> {
  private readonly listeners = new Set<AsyncListener<T>>();

  subscribe(listener: AsyncListener<T>): Unsubscribe {
    this.listeners.add(listener);
    return () => this.listeners.delete(listener);
  }

  async notify(value: T): Promise<void> {
    const results = await Promise.allSettled(
      [...this.listeners].map((listener) => listener(value)),
    );
    const errors = results
      .filter((result): result is PromiseRejectedResult =>
        result.status === "rejected",
      )
      .map((result) => result.reason);

    if (errors.length > 0) throw new AggregateError(errors);
  }
}
```

`Promise.allSettled` は並列実行です。登録順に待つ必要があるなら `for...of` と `await` を使います。ただし遅いlistenerが全体を止めます。fire-and-forgetでよいなら、queueへeventを渡し、再試行やdead letterを別に管理する方が運用しやすい場合があります。

連続したeventに対して前の非同期listenerがまだ動いていることもあります。最新だけ残す、順番にqueueする、並列を許す、古い処理をabortする、といったbackpressure方針は単純なObserverだけでは決まりません。RxJSなどのstream abstractionが有効になる領域です。

## 再入と通知順序を決める

listenerが通知中に同じSubjectへ `notify` すると、入れ子で次の通知が始まります。深い再帰、順序の逆転、状態の中間値観測につながることがあります。

```ts
const numbers = new Subject<number>();

numbers.subscribe((value) => {
  console.log("A", value);
  if (value === 1) numbers.notify(2);
});
numbers.subscribe((value) => console.log("B", value));

numbers.notify(1);
// A 1, A 2, B 2, B 1
```

この順序が困るなら、通知をqueueへ積んで現在の配信後に処理します。ただし同期APIなのに内部をmicrotaskへ送ると、呼び出し直後に通知済みという前提が壊れます。再入を禁止してerrorにする選択もあります。重要なのは、偶然の実装詳細にせず公開契約として決めることです。

## 購読の寿命を管理する

長寿命のSubjectが、短寿命の画面やobjectを閉じ込めたlistenerを保持すると、不要になってもGCされません。購読を開始した場所で解除方法も決めます。`AbortSignal` を受け取ると、複数のcleanupを1つのlifecycleへ結び付けられます。

```ts
function subscribeWithSignal<T>(
  subject: Subject<T>,
  listener: Listener<T>,
  signal: AbortSignal,
): Unsubscribe {
  if (signal.aborted) return () => {};

  const unsubscribe = subject.subscribe(listener);
  const onAbort = () => unsubscribe();
  signal.addEventListener("abort", onAbort, { once: true });

  return () => {
    signal.removeEventListener("abort", onAbort);
    unsubscribe();
  };
}

const controller = new AbortController();
subscribeWithSignal(users, renderUser, controller.signal);
controller.abort();
```

Reactならeffectのcleanup、Web Componentなら `disconnectedCallback`、Node.js resourceなら `close`／`dispose` と対応させます。`WeakRef` や `WeakMap` を使えば解除不要になる、とは考えないでください。GC時期は非決定的で、listenerが別の場所から参照されていれば残ります。明示的な解除が基本です。

## テストで通知規則を固定する

値が届くことだけでなく、解除、snapshot、例外方針を確認します。

```ts
import assert from "node:assert/strict";
import test from "node:test";

test("unsubscribe stops later notifications", () => {
  const subject = new Subject<number>();
  const received: number[] = [];
  const unsubscribe = subject.subscribe((value) => received.push(value));

  subject.notify(1);
  unsubscribe();
  subject.notify(2);

  assert.deepEqual(received, [1]);
});
```

snapshotの意味もテストします。この実装では、AがBを解除してもBは現在の通知だけ受け取ります。

```ts
test("notification uses a listener snapshot", () => {
  const subject = new Subject<number>();
  const calls: string[] = [];
  let unsubscribeB = () => {};

  subject.subscribe(() => {
    calls.push("A");
    unsubscribeB();
  });
  unsubscribeB = subject.subscribe(() => calls.push("B"));

  subject.notify(1);
  subject.notify(2);
  assert.deepEqual(calls, ["A", "B", "A"]);
});
```

重複登録についても契約が必要です。`Set` は同じ関数参照を2回追加しても1件ですが、同じ処理内容の別arrow functionは別listenerです。重複を許すArray型実装もあります。libraryの挙動を真似るのではなく、用途に合った意味を選びます。

## Node.js EventEmitterをObserver的に読む

Node.js公式は、多くのcore APIがevent-driven architectureを採用し、emitterが名前付きeventを発行するとlistener関数が呼ばれると説明しています。`on` で登録し、`emit` で通知する構造はObserverに近い実例です。

```ts
import { EventEmitter } from "node:events";

const emitter = new EventEmitter();
const onSaved = (id: string) => console.log("saved", id);

emitter.on("saved", onSaved);
emitter.emit("saved", "post-1");
emitter.off("saved", onSaved);
```

公式仕様では `emit` は登録順にlistenerを同期呼び出しし、listenerの戻り値を無視します。通常の関数listenerでは `this` がemitterを参照しますが、arrow functionではそうなりません。また既定で同一eventへ10個を超えるlistenerを追加すると、memory leakの発見を助けるwarningが出ます。上限を増やしてwarningを消す前に、解除忘れを調べるべきです。

Node.js公式がEventEmitterをGoF Observerの実装として分類しているわけではありません。本記事での対応付けは、登録・通知・解除という構造上の類似を示す教育的な類推です。特に `'error'` eventの特別扱いや同期通知など、Node.js固有の契約を確認して利用する必要があります。

## RxJSは単純なObserverを越える

RxJSではObservableへ `subscribe` し、Observerの `next`、`error`、`complete` 通知を受け取ります。解除にはSubscriptionの `unsubscribe` を使います。

```ts
import { interval } from "rxjs";

const subscription = interval(1_000).subscribe({
  next: (value) => console.log(value),
  error: (error) => console.error(error),
  complete: () => console.log("complete"),
});

setTimeout(() => subscription.unsubscribe(), 5_000);
```

RxJS公式はObservableを、同期または非同期に0個以上の値をpushできる仕組みとして説明しています。同時に、Observableは通常のEventEmitterと同じではなく、一般的なcold Observableは購読ごとに独立して実行されると注意しています。Subjectやmulticastされたsourceは購読者間で実行を共有するため、cold／hotを一括りにできません。

RxJSはObserverという用語と契約を公式に持ちますが、operator、lazy execution、completion、backpressureに関する選択肢など、GoFの最小構造より広いstream abstractionです。「複数へ通知するから全部RxJS」とせず、時間を伴う複数値の合成、キャンセル、切り替えが必要かで選びます。

## より単純な代替案とトレードオフ

呼び出し先が1つで結果を待つ必要があるなら、通常の関数呼び出しやPromiseが最も明確です。親から子へ値を渡すだけなら引数、Reactならpropsで十分です。業務手順を順番に実行して全体の成否を決めるなら、明示的なorchestratorを使います。processを越えた信頼性が必要ならmessage brokerやqueueが候補です。

Observerは発行元と購読者のcompile-timeな依存を減らす一方、実行時の流れを追いにくくします。listener数に比例して同期処理時間が増え、登録順へ暗黙に依存する危険もあります。event payloadを後から変更すると、多数の購読者へ影響します。疎結合とは、契約が不要になることではありません。

## 失敗しやすい設計

- 解除関数を返さず、購読の寿命を管理できない。
- async listenerを同期emitへ渡し、rejectionと完了を無視する。
- listenerの例外を握りつぶす、または1件の監視失敗で必須処理を止める。
- 通知中の追加・解除・再入について規則がない。
- event名をstringで乱用し、payloadとの対応を型付けしない。
- global event busへすべてを集め、依存関係を不可視にする。
- 登録順を業務上の実行順として暗黙利用する。
- 高頻度eventへ遅いlistenerを同期接続し、UIやevent loopを塞ぐ。

初回購読時に現在値を即時通知するかも重要です。状態を表すstreamでは便利ですが、event履歴を表す通知では過去eventの再送に見えます。状態とeventを同じSubjectへ混ぜず、意味を分けて設計します。

## 使うかどうかの判断基準

Observerが向くのは、1つの変化を独立した複数の利用側へ知らせたい、購読者が実行時に増減する、発行元が具体的な利用処理を知るべきでない場合です。UI event、状態変更通知、監視hookなどが代表例です。

導入前には「通知は状態か出来事か」「同期か非同期か」「順序と再入をどうするか」「1つの失敗が他へ影響するか」「いつ解除するか」「eventを失ってよいか」を確認します。結果が必要な1対1処理、厳密な業務workflow、永続的な配送保証には、別の抽象が適しています。

## まとめ

Observerは、Subjectが具体的な利用者を知らず、共通契約を通して変化を通知できるようにします。実装の中心はlistener配列ではなく、購読、解除、通知順序、例外、同期性、lifecycleという契約です。小さな関数listenerから始め、時間を伴う値の合成が必要ならRxJSなどを検討します。

Node.js EventEmitterとRxJSにはObserver的な構造や用語がありますが、それぞれ固有の契約を持ちます。公式ドキュメントの説明とGoFパターンへの教育的な対応付けを分け、利用するAPIの実際の通知規則をtestで固定することが、安全なイベント設計につながります。
