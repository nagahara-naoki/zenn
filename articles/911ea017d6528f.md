Observerは、ある対象の変化を複数の購読者へ通知するパターンです。

利用側が状態を繰り返し確認する代わりに、変化した側が登録済みのlistenerを呼び出します。

## 最小実装

```ts
type Listener<T> = (value: T) => void;

class Subject<T> {
  private readonly listeners = new Set<Listener<T>>();

  subscribe(listener: Listener<T>): () => void {
    this.listeners.add(listener);

    return () => {
      this.listeners.delete(listener);
    };
  }

  notify(value: T): void {
    for (const listener of [...this.listeners]) {
      listener(value);
    }
  }
}
```

利用側は通知を購読し、不要になったら解除します。

```ts
const subject = new Subject<number>();

const unsubscribe = subject.subscribe((value) => {
  console.log("received", value);
});

subject.notify(1);
unsubscribe();
subject.notify(2); // 通知されない
```

解除関数までAPIに含めることが重要です。

## Observerが解決する問題

通知元が利用側の具体的な処理を知っていると、依存が増え続けます。

```js
function updateUser(user) {
  renderUser(user);
  saveUserToStorage(user);
  sendUserAnalytics(user);
}
```

Observerでは通知元がlistenerだけを知り、どの機能が購読するかを外側で組み立てられます。

一方、実行順序や失敗処理は見えにくくなります。単一の同期処理を分割するためだけに使うものではありません。

## 通知中に購読が変わる場合

最小実装では、`[...this.listeners]` でsnapshotを作っています。

listenerが通知中に自分や別listenerを解除した場合でも、現在の反復処理を安定させるためです。

実際の実装では、次も設計対象になります。

- listenerが例外を投げたら残りへ通知するか
- 同じlistenerの重複登録を許すか
- 購読直後に現在値を通知するか
- 非同期listenerを待つか
- 完了やエラーをどう表すか

## RxJSのsubscribe

RxJSではObservableを `subscribe` し、next・error・completeの通知を受け取れます。

```ts
import { interval } from "rxjs";

const subscription = interval(1_000).subscribe({
  next: (value) => console.log(value),
  error: (error) => console.error(error),
  complete: () => console.log("complete"),
});

setTimeout(() => {
  subscription.unsubscribe();
}, 5_000);
```

`unsubscribe` は、不要になった実行やresourceを片付けるために使います。

### Observableは作っただけでは実行されないことが多い

```ts
const values$ = interval(1_000);
```

この時点では、一般的なcold Observableの実行は始まりません。`subscribe` が実行開始の入口になります。

ただしRxJSのObservableがすべてcoldとは限りません。Subject、DOM event、共有operatorなどでは、購読者間でsourceを共有するhotな性質を持つことがあります。

「Observableは常に購読者ごとに独立実行」と一般化せず、sourceとmulticastingを確認します。

## RxJSは単純なObserverより広い

RxJSは通知登録だけでなく、時間とともに届く値をoperatorで変換・合成できます。

```ts
const searchResults$ = searchInput$.pipe(
  debounceTime(300),
  distinctUntilChanged(),
  switchMap((query) => search(query)),
);
```

Observerの購読・通知を基礎に持ちながら、Observableというpush collectionとoperator compositionを提供します。

GoF Observerと完全に同じものとしてではなく、Observerの考え方を発展させた抽象として読む方が適切です。

## Zustandのsubscribe

Zustandのvanilla storeも状態変更を購読できます。

```ts
const store = createStore<{ count: number }>()(() => ({ count: 0 }));

const unsubscribe = store.subscribe((state, previousState) => {
  console.log(state.count, previousState.count);
});
```

storeが更新されるとlistenerへ通知し、戻り値で解除できます。この構造もObserver的です。

## メモリリークを防ぐ

長寿命のsubjectが短寿命の画面やオブジェクトをlistener経由で参照すると、不要になっても回収されない可能性があります。

購読を開始した場所で、終了方法も決めます。

- コンポーネント破棄時にunsubscribeする
- `AbortSignal` やcleanup callbackへ紐付ける
- RxJSでは `takeUntil` などで寿命を表す
- one-shot通知なら一度で解除する

## 使うべき場面

- 1つの変化を複数の独立した利用側へ知らせる
- 購読者を実行時に追加・削除したい
- event、状態変更、streamを扱う
- 通知元と利用側を疎結合にしたい

## 使わなくてよい場面

呼び出し元が結果をすぐ必要とする単一処理なら、通常の関数呼び出しやPromiseの方が制御フローを追いやすくなります。

Observerを使うときは、通知順序、解除、例外、完了を設計に含めます。

## まとめ

- Observerは購読者を登録し、変化を通知する
- APIには解除方法も含める
- 通知中の変更や例外方針を決める
- RxJSはObserverを含む、より広いstream抽象
- sourceがcoldかhotかを確認する
