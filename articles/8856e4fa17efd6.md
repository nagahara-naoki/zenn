Promiseを学ぶと、`then`、`catch`、`async`、`await`、`Promise.all` が一度に現れます。結果を待ちたいだけなのに、Promiseそのものを表示したり、エラーを握りつぶしたり、独立した通信を一つずつ待って遅くしたりしがちです。

結論から言えば、Promiseは「あとで利用可能になる一つの結果」を表すオブジェクトです。結果は成功値か失敗理由のどちらかで確定し、一度確定したら変わりません。利用側は、**値を返して次へつなぐ、処理できない失敗は投げて上位へ伝える、独立した処理はまとめて開始する**、という3点を守ると読みやすくなります。

`async` / `await` はPromiseと別の仕組みではありません。Promiseの連鎖を、同期処理に近い見た目で書く構文です。この記事では注文情報を取得する処理を育てながら、状態、連鎖、エラー、並行実行、実行順序、キャンセル、デバッグまで整理します。

## Promiseは「未来の値」を受け渡す

注文APIからデータを取得する最小例です。`fetch` はすぐにレスポンス本体を返しません。`Promise<Response>` を返します。

```js
function fetchOrder(orderId) {
  return fetch(`/api/orders/${orderId}`).then((response) => {
    if (!response.ok) {
      throw new Error(`注文の取得に失敗しました: HTTP ${response.status}`);
    }

    return response.json();
  });
}

fetchOrder("order-42")
  .then((order) => console.log(order))
  .catch((error) => console.error(error));
```

処理を「Promiseを作る側」と「結果を使う側」に分けると理解しやすくなります。

- 作る側：処理が完了したら成功値か失敗理由を通知する。
- 使う側：成功後の処理を登録し、必要な場所で失敗を処理する。
- Promise：一回限りの結果と、その後続処理をつなぐ。

Promiseが通信を実行するわけではありません。通信はFetch API、タイマーはホスト環境、ファイル読み込みはNode.jsなどのAPIが行います。Promiseは、それらの非同期な結果を共通の形で扱うための契約です。

## pending・fulfilled・rejected

Promiseには次の状態があります。

| 状態 | 意味 |
| --- | --- |
| pending | まだ結果が確定していない |
| fulfilled | 成功値で確定した |
| rejected | 失敗理由で確定した |

fulfilledとrejectedをまとめてsettledと呼びます。一度settledになったPromiseの結果は変わりません。後から別の値で `resolve` や `reject` を呼んでも無視されます。

```js
const promise = new Promise((resolve, reject) => {
  resolve({ id: "order-42" });
  reject(new Error("このrejectは結果を変更しない"));
  resolve({ id: "order-99" });
});

promise.then(console.log); // { id: "order-42" }
```

「resolved」と「fulfilled」は厳密には同義ではありません。別のPromiseを使ってresolveすると、外側のPromiseはその結果を採用します。内側がpendingなら、外側も最終値をまだ利用できません。

```js
let finish;
const inner = new Promise((resolve) => {
  finish = resolve;
});

const outer = Promise.resolve(inner);
outer.then((value) => console.log(value));

finish("completed");
```

普段は「成功・失敗・待機中」の三状態で十分です。Promiseやthenableを包むライブラリを作る場合だけ、resolveが別の非同期結果を採用する可能性まで意識します。

## Promiseコンストラクターは必要なときだけ使う

コールバック形式のAPIをPromiseへ変換するときは、`new Promise` のexecutorへ処理を書きます。executorはPromise生成時に**同期的に**呼び出されます。`resolve` と `reject` は、後でsettleさせるために保持できます。

```js
function wait(ms, signal) {
  return new Promise((resolve, reject) => {
    if (signal?.aborted) {
      reject(signal.reason ?? new DOMException("Aborted", "AbortError"));
      return;
    }

    const onAbort = () => {
      clearTimeout(timerId);
      reject(signal.reason ?? new DOMException("Aborted", "AbortError"));
    };
    const timerId = setTimeout(() => {
      signal?.removeEventListener("abort", onAbort);
      resolve();
    }, ms);

    signal?.addEventListener("abort", onAbort, { once: true });
  });
}
```

すでにPromiseを返す `fetch` や `response.json()` を、理由なく `new Promise` で包む必要はありません。settle漏れ、エラー伝播漏れ、不要な入れ子を生みます。

```js
// 不要なラップ
function loadBad(url) {
  return new Promise((resolve, reject) => {
    fetch(url).then(resolve).catch(reject);
  });
}

// そのまま返せばよい
function load(url) {
  return fetch(url);
}
```

executorを `async` 関数にするのも避けます。executorの戻り値は無視されるため、`await` 後に投げられた例外が外側のPromiseの `reject` へ自動的につながりません。

```js
// アンチパターン: 外側がsettleしない経路を作りやすい
const bad = new Promise(async (resolve) => {
  const response = await fetch("/api/orders/order-42");
  resolve(await response.json());
});

// async関数自身がPromiseを返す
async function loadOrder() {
  const response = await fetch("/api/orders/order-42");
  return response.json();
}
```

Promiseコンストラクター内で同期的に投げられた例外はrejectへ変換されます。しかし、イベントコールバックやタイマー内で後から投げた例外はexecutorの呼び出しを離れているため、明示的に `reject` する必要があります。

## thenは新しいPromiseを返す

`then` は元のPromiseを書き換えません。常に新しいPromiseを返します。成功ハンドラーが通常の値を返せば、その値で次がfulfilledになります。Promiseを返せば、その結果が平坦化されて次へ渡ります。例外を投げれば、次はrejectedになります。

```js
function fetchOrderSummary(orderId) {
  return fetchOrder(orderId)
    .then((order) => {
      return fetch(`/api/users/${order.userId}`).then((response) => {
        if (!response.ok) throw new Error(`HTTP ${response.status}`);
        return response.json();
      }).then((user) => ({ order, user }));
    })
    .then(({ order, user }) => ({
      orderId: order.id,
      customerName: user.name,
      total: order.total,
    }));
}
```

この例は動きますが、最初の `then` が深くなっています。Promiseを返すことさえ守れば、処理を小さな関数へ分けて平らにできます。

```js
function fetchJson(url, label) {
  return fetch(url).then((response) => {
    if (!response.ok) {
      throw new Error(`${label}の取得に失敗しました: HTTP ${response.status}`);
    }
    return response.json();
  });
}

function fetchOrderSummary(orderId) {
  return fetchJson(`/api/orders/${orderId}`, "注文")
    .then((order) =>
      fetchJson(`/api/users/${order.userId}`, "利用者")
        .then((user) => ({ order, user })),
    )
    .then(({ order, user }) => ({
      orderId: order.id,
      customerName: user.name,
      total: order.total,
    }));
}
```

よくある失敗は、波括弧を付けたハンドラーからPromiseをreturnしないことです。次の `then` へは `undefined` が渡り、内側の失敗も意図した `catch` から外れます。

```js
fetchOrder("order-42")
  .then((order) => {
    fetchJson(`/api/users/${order.userId}`, "利用者"); // returnがない
  })
  .then((user) => {
    console.log(user); // undefined
  });
```

連鎖の途中で始めた非同期処理は必ずreturnする、または `await` する。この一つの規則が、多くのタイミング不具合を防ぎます。

## catchは上流の失敗を受け取る

`catch(onRejected)` は `then(undefined, onRejected)` と同じ形です。それ以前の連鎖で起きたrejectや、成功ハンドラー内で投げられた例外を受け取ります。

```js
fetchOrderSummary("order-42")
  .then((summary) => renderSummary(summary))
  .catch((error) => {
    console.error("注文画面の読み込みに失敗しました", error);
    renderError("注文情報を表示できませんでした");
  });
```

`catch` 内で何も投げずに終えると、`catch` が返す新しいPromiseは `undefined` でfulfilledになります。そこで回復値を返すなら意図どおりですが、記録だけして失敗を上位へ伝えたいなら再throwします。

```js
async function loadForPage(orderId) {
  try {
    return await fetchOrderSummary(orderId);
  } catch (error) {
    console.error("[order:load-failed]", { orderId, error });
    throw error;
  }
}
```

同じ失敗を各層で記録するとログが重複します。どの層が回復するか、利用者向け表示を決めるか、運用ログを残すかを決め、責務のある境界で処理します。低レベルの情報を足すなら `Error` の `cause` で元の理由を保てます。

## finallyは結果を変えない後始末に使う

`finally` は成功でも失敗でも実行され、ローディング表示の解除やリソースの後始末に向きます。通常は元の値または失敗をそのまま通過させます。

```js
setLoading(true);

fetchOrderSummary("order-42")
  .then(renderSummary)
  .catch(renderError)
  .finally(() => {
    setLoading(false);
  });
```

ただし、`finally` 内で例外を投げたりrejectedなPromiseを返したりすると、元の結果を新しい失敗で置き換えます。後始末の失敗を優先すべき場面もありますが、意図せず元のエラーを隠さないようにします。

## async / awaitで同じ流れを直線的に書く

`async` 関数は必ずPromiseを返します。通常の値をreturnすれば、その値でfulfilledなPromiseになります。例外を投げればrejectedになります。`await` はPromiseがsettleするまで、そのasync関数の続きだけを中断します。JavaScript全体のスレッドを停止するわけではありません。

```js
async function fetchOrderSummary(orderId) {
  const order = await fetchJson(`/api/orders/${orderId}`, "注文");
  const user = await fetchJson(`/api/users/${order.userId}`, "利用者");

  return {
    orderId: order.id,
    customerName: user.name,
    total: order.total,
  };
}

async function showOrder(orderId) {
  setLoading(true);
  try {
    renderSummary(await fetchOrderSummary(orderId));
  } catch (error) {
    renderError("注文情報を表示できませんでした");
  } finally {
    setLoading(false);
  }
}
```

`await` はPromiseでない値にも使えますが、概念上はPromiseとして扱われ、続きは非同期に再開されます。戻り値をすぐ使いたい同期関数へ、理由なく `async` を付けるとAPIがPromiseへ変わるため注意します。

## 依存する処理と独立した処理を分ける

上の注文と利用者の取得は、利用者IDを注文から得るので逐次実行が必要です。一方、注文と配送状況をどちらも注文IDから取得できるなら独立しています。先に両方を開始し、`Promise.all` でまとめて待ちます。

```js
async function fetchOrderPage(orderId) {
  const orderPromise = fetchJson(`/api/orders/${orderId}`, "注文");
  const shippingPromise = fetchJson(
    `/api/shipping/${orderId}`,
    "配送状況",
  );

  const [order, shipping] = await Promise.all([
    orderPromise,
    shippingPromise,
  ]);

  const user = await fetchJson(`/api/users/${order.userId}`, "利用者");
  return { order, shipping, user };
}
```

配列を作ってから `Promise.all` する書き方でも、`map` の各コールバックは同期的に呼ばれ、非同期処理が開始されます。大量の要求を無制限に並行化するとAPIや端末を圧迫するため、件数が多い場合は同時実行数を制限します。

`Promise.all` は一つがrejectすると、返したPromiseも直ちにrejectします。しかし、すでに開始した他の通信を自動で止めません。中止したい場合は各処理へ同じ `AbortSignal` を渡すなど、別途キャンセルを設計します。

## Promiseの結合方法を選ぶ

静的メソッドは「複数結果のうち何を必要とするか」で選びます。

| API | fulfilledになる条件 | rejectedになる条件 | 主な用途 |
| --- | --- | --- | --- |
| `Promise.all` | 全部成功 | 一つでも失敗 | 全結果が必須 |
| `Promise.allSettled` | 全処理が確定 | 通常rejectしない | 成功・失敗を個別表示 |
| `Promise.any` | 一つでも成功 | 全部失敗 | 複数候補の最初の成功 |
| `Promise.race` | 最初に確定した結果 | 最初が失敗なら失敗 | 最初のsettleを採用 |

例えば複数ウィジェットを個別表示する画面なら、一つの失敗で全体を捨てる `all` より `allSettled` が合います。

```js
const results = await Promise.allSettled([
  fetchJson("/api/profile", "プロフィール"),
  fetchJson("/api/recommendations", "おすすめ"),
  fetchJson("/api/notices", "お知らせ"),
]);

for (const result of results) {
  if (result.status === "fulfilled") {
    renderWidget(result.value);
  } else {
    console.error(result.reason);
  }
}
```

`Promise.any` がすべて失敗すると `AggregateError` でrejectします。`race` は最速の成功を探すAPIではありません。最初にsettleした結果を返すので、最初が失敗ならその失敗です。名前だけで選ばず、必要な結果条件を言葉にしてから使います。

## fetchの失敗条件を誤解しない

Fetch APIのPromiseは、HTTP 404や500を受信しただけでは通常rejectしません。ネットワークエラーや中止などではrejectしますが、HTTPステータスは `response.ok` や `response.status` で判定します。

```js
async function fetchJson(url, label, { signal } = {}) {
  const response = await fetch(url, { signal });

  if (!response.ok) {
    const error = new Error(
      `${label}の取得に失敗しました: HTTP ${response.status}`,
    );
    error.status = response.status;
    throw error;
  }

  return response.json();
}
```

`response.json()` もPromiseを返し、不正なJSONならrejectします。HTTPエラーと解析エラーを利用者へ同じ表示にするか、再試行条件を分けるかはアプリケーション側の設計です。

## キャンセルはAbortSignalを処理へ渡す

Promise自体には、汎用的な `cancel()` はありません。結果への関心を失っても、背後の通信やタイマーが自動停止するわけではありません。Fetch APIなら `AbortController` のsignalを渡します。

```js
async function showOrder(orderId, signal) {
  try {
    const order = await fetchJson(
      `/api/orders/${orderId}`,
      "注文",
      { signal },
    );
    renderOrder(order);
  } catch (error) {
    if (error.name === "AbortError") return;
    throw error;
  }
}

const controller = new AbortController();
showOrder("order-42", controller.signal).catch(renderError);

// 画面を離れたときなどに呼ぶ
controller.abort(new DOMException("画面を離れました", "AbortError"));
```

キャンセル可能にする責任は、Promise側にはありません。実処理を提供するAPI側にあります。自作APIでも、signalを受け取り、開始前に `signal.aborted` を確認し、処理中はabortイベントで後始末する契約を揃えると合成しやすくなります。

## thenのコールバックは同期実行されない

Promiseコンストラクターのexecutorは同期的に動きますが、`then`、`catch`、`finally` の反応処理は、すでにsettledなPromiseへ登録しても現在のJavaScript実行が終わった後に実行されます。

```js
console.log("A");

const promise = new Promise((resolve) => {
  console.log("B");
  resolve();
});

promise.then(() => console.log("C"));
setTimeout(() => console.log("D"), 0);

console.log("E");
// A, B, E, C, D
```

ブラウザーでは、現在のtaskが終わるとmicrotask checkpointが行われ、Promise reactionはmicrotaskとして処理されます。`setTimeout` のコールバックは後続のtaskです。そのため上の登録順では `C` が `D` より先です。

ただし、「Promiseは常にsetTimeoutより先」と文脈なしに覚えるのは危険です。どの時点で各処理がキューへ入ったか、別taskやイベントをまたいだかで順序は変わります。大量のmicrotaskを連鎖させると、次のtaskや描画を遅らせる可能性もあります。実行順はコードの行だけでなく、taskとmicrotaskへ登録された時点で追います。

## 未処理のrejectを残さない

Promiseがrejectしても、呼び出し側が `await`、return、`catch` のいずれでも扱わなければ、未処理のrejectionになります。ブラウザーは `unhandledrejection`、Node.jsはプロセス設定に応じた警告や終了などで表面化します。挙動へ依存せず、非同期処理の所有者を決めます。

```js
button.addEventListener("click", () => {
  void showOrder("order-42").catch((error) => {
    console.error("注文表示に失敗しました", error);
    renderError("注文を表示できませんでした");
  });
});
```

`void` はPromiseを処理済みにする機能ではありません。「戻り値を待たない」という意図を表すだけです。必ず内部または直後で失敗を処理します。テストでは未処理rejectionを失敗として検出する設定にすると、returnし忘れを見つけやすくなります。

## デバッグとテストの確認順

非同期処理が期待どおり動かないときは、次の順で追います。

1. 関数が通常値とPromiseのどちらを返す契約か確認する。
2. 連鎖中のPromiseをreturnまたはawaitしているか確認する。
3. Networkパネルで要求、HTTP状態、応答本文、中止を確認する。
4. 例外を途中の `catch` がfulfilledへ変えていないか確認する。
5. 独立処理を逐次実行していないか、逆に依存処理を並行化していないか確認する。
6. AbortSignalが開始から下位APIまで渡っているか確認する。
7. 未処理rejectionと、Promiseを表示しただけの箇所を確認する。

自動テストでは、固定時間の `setTimeout` で待つより、対象Promiseを直接awaitします。失敗を期待するテストも、catchして終わらせるよりテストランナーのrejection検証を使います。タイマーを含む処理はfake timerの進め方とmicrotaskの処理順をテストランナーの仕様に合わせます。

## Promiseが向かない処理

Promiseは一回だけ確定する結果に適しています。クリックの連続、WebSocketの複数メッセージ、継続的な位置情報のように何度も値が届く処理は、イベント、async iterator、ReadableStreamなどが自然です。Promiseへ無理に変換すると最初の一件しか表せません。

同期的に結果が出る計算をPromiseで包む必要もありません。呼び出し側へ不要な非同期境界とエラー処理を要求します。Promiseを選ぶ基準は「処理が難しそう」かどうかではありません。「一つの結果が今はなく、後で成功または失敗として確定するか」です。

## まとめ

Promiseは非同期処理そのものではなく、後で確定する一回限りの結果を受け渡す契約です。状態名を暗記するより、生成側と利用側の責任、連鎖で返す値、処理間の依存関係を確認すると設計しやすくなります。

- Promiseはpendingからfulfilledまたはrejectedへ一度だけ確定する。
- `then` は新しいPromiseを返し、returnした値やPromiseを次へ渡す。
- 処理できない失敗は握りつぶさず、throwして責任のある境界へ伝える。
- `async` 関数はPromiseを返し、`await` はその関数の続きだけを中断する。
- 独立した処理はまとめて開始し、必要な成功条件に合う結合APIを選ぶ。
- Promise自体にキャンセルはなく、AbortSignalを実処理へ渡す。
- 実行順はtaskとmicrotaskへ登録された時点で考える。

最も大切な習慣は、開始した非同期処理を「誰がawaitするか」「誰が失敗を処理するか」「不要になったら誰が止めるか」まで決めることです。この所有関係が明確なら、`then` と `async` / `await` のどちらで書いても、流れを追えるコードになります。
