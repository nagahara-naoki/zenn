`npm install`を実行したあと、次のような表示を見たことはないでしょうか。`critical`や`high`という文字を見ると、不安になってすぐ修正したくなります。

```text
8 vulnerabilities (5 moderate, 2 high, 1 critical)

To address all issues, run:
  npm audit fix --force
```

そこで出てくるのが、次のコマンドです。

```bash
npm audit fix --force
```

しかし、`--force`は強力な修復コマンドではありません。**互換性を守るための制限を外し、破壊的変更を含むアップデートを許可するオプション**です。

脆弱性の件数を0件にできたとしても、アプリケーションが起動しなくなったり、ビルドが失敗したり、気づきにくい不具合が入り込んだりする可能性があります。

この記事では、次の内容を解説します。

- `npm audit`が調べているもの
- `npm audit fix`と`--force`の違い
- `--force`をすぐに使ってはいけない理由
- 脆弱性が見つかったときの安全な対応手順
- 修正できない脆弱性との向き合い方

## `npm audit`とは

`npm audit`は、プロジェクトの依存関係に既知の脆弱性が含まれていないかを調べるコマンドです。

```bash
npm audit
```

プロジェクトが直接インストールしているパッケージだけでなく、そのパッケージが内部で利用している依存パッケージも調査対象になります。

たとえば、プロジェクトが次のような依存関係を持っているとします。

```text
my-app
└─ framework-tool
   └─ dev-server
      └─ vulnerable-package
```

この場合、`vulnerable-package`を自分で`package.json`に追加していなくても、`npm audit`には脆弱性として表示されます。

このような、自分が直接追加していない依存関係を**推移的依存関係**と呼びます。

## `npm audit fix`は何をしているのか

次のコマンドを実行すると、npmは脆弱性を解消できるバージョンへの更新を試みます。

```bash
npm audit fix
```

ただし、通常の`npm audit fix`は、基本的に現在の依存バージョンの指定範囲を尊重します。

たとえば、`package.json`が次の状態だったとします。

```json
{
  "dependencies": {
    "sample-package": "^2.3.0"
  }
}
```

`^2.3.0`では、原則として`2.x.x`の範囲内で更新されます。

```text
2.3.0 → 2.8.1
```

一方、破壊的変更を含む可能性があるメジャーバージョンアップは、通常の`npm audit fix`では勝手に行われません。

```text
2.3.0 → 3.0.0
```

これは、セキュリティ修正のためにアプリケーションを壊してしまわないようにするための保護です。

## `--force`を付けると何が変わるのか

`npm audit fix --force`を実行すると、npmは現在の依存バージョンの指定範囲を超えた更新も許可します。

```bash
npm audit fix --force
```

たとえば、脆弱性を解消するために`3.0.0`への更新が必要であれば、メジャーバージョンアップであっても更新対象になる可能性があります。

```text
2.3.0 → 3.0.0
```

npmの公式ドキュメントでも、`--force`は次のような保護を外すオプションとして説明されています。

- 宣言された依存バージョンの範囲外をインストールする
- SemVer上のメジャーバージョン変更を許可する
- 競合するPeer Dependenciesのインストールを許可する
- Node.jsやnpmのバージョン条件を無視する場合がある

つまり、`--force`は安全な修復を保証しません。**npmが通常は止める変更を強制的に進めるもの**です。

## すぐに`--force`してはいけない3つの理由

### 1. メジャーバージョンが変わる可能性がある

メジャーバージョンの更新には、破壊的変更が含まれる可能性があります。

たとえば、次のような変更です。

- 関数やクラスが削除された
- APIの引数や戻り値が変わった
- 設定ファイルの書き方が変わった
- Node.jsの最低バージョンが引き上げられた
- 他のパッケージとの組み合わせ条件が変わった

脆弱性は解消されても、アプリケーションが正常に動かなければ修正完了とはいえません。

### 2. 関係のないパッケージまで大きく変わることがある

監査結果には、次のような表示が出ることがあります。

```text
fix available via `npm audit fix --force`

Will install framework-tool@5.0.0,
which is a breaking change
```

問題があるのは深い階層にある小さな依存パッケージでも、それを更新するために上位のフレームワークやビルドツールを大きく変更しなければならない場合があります。

たとえば、次の依存関係を考えてみます。

```text
my-app
└─ framework-tool@9
   └─ dev-server
      └─ vulnerable-package
```

`vulnerable-package`だけを安全なバージョンへ更新できなければ、npmは`framework-tool`自体の変更を提案することがあります。

その結果、次のような問題が起こる可能性があります。

- ビルド設定が使えなくなる
- プラグインの互換性が崩れる
- テスト環境が起動しなくなる
- TypeScriptやNode.jsの対応バージョンが合わなくなる

### 3. 「脆弱性0件」と「安全」は同じではない

`npm audit`の結果が0件になったとしても、アプリケーション全体の安全が保証されるわけではありません。

`npm audit`が主に検出するのは、依存パッケージについて公開されている既知の脆弱性です。

次のような問題は、別途確認する必要があります。

- アプリケーション自身のXSSやSQLインジェクション
- 認証・認可の実装ミス
- 秘密情報の誤公開
- 安全ではない設定
- 未報告の脆弱性
- 依存パッケージの不正な処理

そのため、件数を0にすることだけを目的に依存関係を壊すのは本末転倒です。

## Severityだけで対応を決めない

`npm audit`では、一般的に次のような深刻度が表示されます。

```text
low
moderate
high
critical
```

もちろん、`high`や`critical`は優先して確認する必要があります。

ただし、深刻度だけでは、本番への影響を機械的には判断できません。

少なくとも、次の点を確認します。

### 本番環境で使われるパッケージか

脆弱性が次のどちらに含まれているかで、影響は変わります。

```json
{
  "dependencies": {},
  "devDependencies": {}
}
```

- `dependencies`: 本番実行時にも利用される可能性が高い
- `devDependencies`: ビルド、テスト、開発サーバーなどで利用される

ただし、`devDependencies`だから無条件に安全というわけではありません。

CIで動作するツールや、外部入力を処理する開発サーバーに脆弱性がある場合は、開発環境やビルド環境が攻撃対象になる可能性があります。

本番依存だけの監査結果を分けて確認する場合は、次のコマンドを使えます。

```bash
npm audit --omit=dev
```

これはdev dependencyを無視した監査結果であり、実際のデプロイ構成を自動判定するものではありません。デプロイ先でbuildする構成や、CIが外部から受け取ったデータを処理する構成では、開発依存も脅威モデルへ含めます。

### 脆弱な処理を実際に利用しているか

パッケージをインストールしていても、脆弱性のある機能を利用していない場合があります。

ここでは次を見ます。

- 脆弱なAPIを呼び出しているか
- 外部から入力を受け取る箇所で利用しているか
- 本番環境で実行されるコードか
- 攻撃成立に特別な条件が必要か

このような「実際に脆弱なコードへ到達できるか」という観点は、**到達可能性**と呼ばれます。

### 修正版が本当に存在するか

監査結果によっては、次のように表示される場合があります。

```text
No fix available
```

これは、コマンドを工夫すれば直るという意味ではありません。

考えられる状況には、次のようなものがあります。

- パッケージ側で修正版が公開されていない
- 上位パッケージが古い依存関係を固定している
- パッケージがメンテナンスされていない
- 修正には別のパッケージへの移行が必要

この場合は、`--force`で押し切る前に、代替パッケージや回避策を検討します。

## 脆弱性が出たときの安全な対応手順

ここからは、実際に`npm audit`で脆弱性が見つかったときの流れを見ていきます。

### 1. 作業前の状態を保存する

依存関係を変更する前に、現在の状態をGitへ保存します。

```bash
git status
```

未コミットの変更がある場合は、コミットするか、作業内容を退避します。

依存関係の更新では、主に次のファイルが変更されます。

```text
package.json
package-lock.json
```

変更前後の差分を確認できる状態にしておくことが重要です。

作業用ブランチを作成しておくと、問題が起きた場合に戻しやすくなります。

```bash
git switch -c fix/npm-audit
```

### 2. まず監査結果を読む

最初に、修正を加えず監査結果を確認します。

```bash
npm audit
```

より詳細に調べたい場合は、JSON形式でも出力できます。

```bash
npm audit --json
```

見る項目は次です。

- 脆弱性のあるパッケージ名
- 深刻度
- 影響を受けるバージョン
- 修正版の有無
- 直接依存か推移的依存か
- `--force`が必要と表示されているか
- どの上位パッケージから入っているか

### 3. 依存経路を確認する

問題のパッケージが、どこからインストールされているかを確認します。

```bash
npm explain パッケージ名
```

例として、`vulnerable-package`を調べる場合は次のように実行します。

```bash
npm explain vulnerable-package
```

また、依存ツリーは`npm ls`でも確認できます。

```bash
npm ls vulnerable-package
```

表示例は次のようになります。

```text
my-app
└─ framework-tool
   └─ dev-server
      └─ vulnerable-package
```

この結果から、自分で直接更新できるパッケージなのか、上位パッケージの対応を待つ必要があるのかを判断できます。

### 4. `dry-run`で変更内容を確認する

実際に変更する前に、`npm audit fix`が何をしようとしているかを確認します。

```bash
npm audit fix --dry-run
```

詳細をJSON形式で確認することもできます。

```bash
npm audit fix --dry-run --json
```

ここでは、次の点を確認します。

- どのパッケージが更新されるか
- メジャーバージョンが変わらないか
- `package.json`の範囲外へ更新されないか
- 大きなフレームワークの変更が含まれていないか

### 5. まずは`--force`なしで修正する

互換性を保ったまま更新できるものは、通常の`npm audit fix`で修正します。

```bash
npm audit fix
```

`npm audit fix`は内部でインストール処理を行い、`package-lock.json`や`node_modules`を更新します。

実行後は、必ず差分を確認します。

```bash
git diff
```

特に次の点を確認します。

- 意図しないパッケージが更新されていないか
- 大量の依存関係が変更されていないか
- `package.json`のバージョン指定が変わっていないか
- Lockファイルだけの変更か、直接依存も変わったか

### 6. ビルドとテストを実行する

脆弱性の件数が減っても、動作確認を省略してはいけません。

プロジェクトに合わせて、次のようなコマンドを実行します。

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

E2Eテストがある場合は、可能な範囲で実行します。

```bash
npm run e2e
```

テストが少ないプロジェクトでは、主要な画面や機能を手動で確認します。

- アプリケーションが起動するか
- ログインできるか
- API通信が成功するか
- フォームを送信できるか
- ビルド成果物が正常に生成されるか

### 7. 直接依存を個別に更新する

`npm audit fix`で解決できない場合は、影響を受ける上位パッケージを個別に更新できないか確認します。

```bash
npm outdated
```

特定のパッケージを更新する場合は、変更履歴や移行ガイドを確認したうえで実行します。

```bash
npm install パッケージ名@更新先バージョン
```

フレームワークやビルドツールを更新する場合は、公式のアップデート手順を優先します。

一度にすべてを更新せず、変更単位を小さくすると原因を追いやすくなります。

### 8. 推移的依存には`overrides`も検討する

脆弱なパッケージが推移的依存関係にあり、互換性のある修正版が存在する場合は、`overrides`でバージョンを指定できることがあります。

```json
{
  "overrides": {
    "vulnerable-package": "3.2.1"
  }
}
```

ただし、`overrides`も安全を保証する機能ではありません。

上位パッケージが想定していないバージョンへ差し替えるため、次の確認が必要です。

- 上位パッケージの要求バージョンと互換性があるか
- テストとビルドが成功するか
- 実行時の挙動に問題がないか
- 上位パッケージが正式対応したら削除できるか

`overrides`を追加する場合は、理由をコメントやPull Requestに残しておくと、将来削除しやすくなります。

JSONにはコメントを書けないため、コミットメッセージや管理チケットに記録しておく方法が現実的です。

## それでも`--force`を使う場合

`--force`を絶対に使ってはいけないわけではありません。

必要な変更内容を理解し、破壊的変更への対応を行える状況であれば、選択肢になることがあります。

実行する場合は、少なくとも次の条件を満たしていることを確認します。

- 作業用ブランチで実行している
- 更新対象のパッケージを把握している
- メジャーバージョン変更の内容を確認している
- 移行ガイドを読んでいる
- 自動テストを実行できる
- 問題が起きたときに元へ戻せる
- 本番リリース前に十分な検証ができる

そのうえで実行します。

```bash
npm audit fix --force
```

実行後は、`npm audit`の件数だけでなく、依存関係の差分を確認します。

```bash
git diff -- package.json package-lock.json
```

さらに、依存ツリーが意図した状態になっているかを確認します。

```bash
npm ls
```

最後に、Lint、型チェック、テスト、ビルドを実行します。

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

`--force`を使うこと自体よりも、**内容を確認せずに実行し、テストせずにマージすること**が危険です。

## 修正できない脆弱性はどうするか

すべての脆弱性をすぐに0件へできるとは限りません。

修正版が存在しない場合や、更新による影響が大きすぎる場合は、リスクを整理して管理します。

### 影響範囲を確認する

次の点を調べます。

- 本番環境で使用されるか
- 外部入力を処理するか
- 脆弱な機能を利用しているか
- 攻撃成立に必要な条件は何か
- 一時的な回避策があるか

### 代替手段を検討する

状況に応じて、次の対応を検討します。

- 上位パッケージを更新する
- 別のパッケージへ移行する
- 脆弱な機能を利用しない
- 外部からアクセスできないようにする
- 入力値を制限する
- 公式の修正版が出るまで監視する

### 判断を記録する

すぐに修正しない場合は、理由を残します。放置とは分けて扱います。

記録しておきたい内容は次のとおりです。

```text
・対象パッケージ
・脆弱性の内容
・本番環境への影響
・現時点で修正しない理由
・一時的な回避策
・再確認する期限
・担当者
```

脆弱性対応では、0件という数字だけでなく、**リスクを把握し、継続的に管理できていること**が重要です。

## 実務で使える確認フロー

迷ったときは、次の順番で対応すると安全です。

```text
1. npm auditで内容を確認する
        ↓
2. npm explainで依存経路を確認する
        ↓
3. dry-runで変更内容を確認する
        ↓
4. --forceなしのnpm audit fixを試す
        ↓
5. package.jsonとLockファイルの差分を確認する
        ↓
6. Lint・型チェック・テスト・ビルドを実行する
        ↓
7. 解決しなければ直接依存の更新を検討する
        ↓
8. 推移的依存ならoverridesや上位パッケージの更新を検討する
        ↓
9. 変更内容を理解できる場合だけ--forceを検討する
```

実行するコマンドは次のとおりです。

```bash
# 監査結果を確認
npm audit

# 依存経路を確認
npm explain パッケージ名

# 変更予定を確認
npm audit fix --dry-run

# 互換性のある範囲で修正
npm audit fix

# 差分を確認
git diff -- package.json package-lock.json

# 動作確認
npm run lint
npm run typecheck
npm test
npm run build
```

## まとめ

`npm audit fix --force`は、脆弱性を自動的かつ安全に直してくれる魔法のコマンドではありません。`--force`を付けると、メジャーバージョンアップや依存バージョン範囲外の更新など、通常はnpmが止める変更を許可します。

脆弱性が表示されたときは、件数だけを見てすぐに実行せず、次の順番で考えます。

1. どのパッケージに脆弱性があるのか
2. どの依存経路から入っているのか
3. 本番環境で影響を受けるのか
4. 互換性を保った修正ができるのか
5. 更新後の動作を検証できるのか

脆弱性を放置してよいわけではありません。とはいえ、アプリケーションを壊してまで監査結果を0件にすることも、正しい対応とはいえません。

軸になるのは、コマンドの提案をそのまま実行することではありません。**変更内容とリスクを理解したうえで、安全に依存関係を更新すること**です。
