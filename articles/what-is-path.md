CLIツールをインストールしたあと、コマンドを実行すると次のようなエラーが出ることがあります。

```console
$ sample-cli --version
zsh: command not found: sample-cli
```

考えられる原因は、大きく二つ。ツール自体がインストールされていないか、インストールされていてもシェルが実行ファイルを見つけられないかです。後者を解決するため、ツールの説明には「PATHを通してください」と書かれていることがあります。

とはいえ、初めて見ると何をすればよいのか分かりません。この記事では、PATHの仕組みと確認方法、設定方法を順番に説明します。

コマンド例はmacOSとLinuxを中心に紹介し、最後にWindowsでの確認方法も取り上げます。

## PATHとは、コマンドの検索先をまとめた環境変数

PATH（パス）は、**コマンドを探すディレクトリの一覧**を保存した環境変数です。

ターミナルで `ls` と入力すると、シェルはPATHに登録されたディレクトリを順番に調べ、`ls` という実行ファイルを探します。見つかればそのファイルを実行し、最後まで見つからなければ `command not found` と表示します。

ここでいうPATHと、ファイルの場所を表す「パス」は関係していますが、同じものではありません。

- `/Users/example/report.txt`：ファイルやディレクトリの場所を表すパス
- `PATH`：コマンドの検索先をまとめた環境変数

一般に「PATHを通す」とは、コマンドの実行ファイルが置かれたディレクトリを、環境変数 `PATH` に追加することです。

## シェルはPATHを左から順番に探す

現在のPATHは、次のコマンドで確認できます。

```sh
echo "$PATH"
```

macOSでは、たとえば次のような結果が表示されます。

```text
/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin
```

macOSやLinuxでは、複数のディレクトリが `:` で区切られています。シェルは左から順番に実行ファイルを探します。

```text
1. /opt/homebrew/bin
2. /usr/local/bin
3. /usr/bin
4. /bin
```

同じ名前のコマンドが複数のディレクトリにある場合は、原則として先に見つかったものが実行されます。PATHでは、ディレクトリが登録されているかどうかと、その並び順の両方が重要です。

## コマンドの実体は実行ファイル

普段は意識しませんが、`ls` や `git` などのコマンドにも実体となるファイルがあります。現在使われる実行ファイルの場所は、`command -v` で確認できます。

```console
$ command -v git
/usr/bin/git
```

この結果から、`git` の実行ファイルが `/usr/bin` にあると分かります。`/usr/bin` がPATHに含まれているため、ファイルの場所をすべて入力せずに `git` だけで実行できます。

PATHを使わず、実行ファイルを絶対パスで直接指定することもできます。

```sh
/usr/bin/git --version
```

絶対パスなら実行できるのにコマンド名だけでは実行できない場合、その実行ファイルがあるディレクトリにPATHが通っていない可能性があります。

## 手を動かしてPATHの仕組みを確かめる

簡単なコマンドを自作すると、PATHの働きを確認できます。まず、ホームディレクトリに `my-tools` というディレクトリを作ります。

```sh
mkdir -p "$HOME/my-tools"
```

次に、次の内容で `$HOME/my-tools/hello` というファイルを作成します。

```sh
#!/bin/sh

echo "Hello from my command!"
```

作成したファイルへ実行権限を付けます。

```sh
chmod +x "$HOME/my-tools/hello"
```

ファイルの場所を指定すれば、この時点でも実行できます。

```console
$ "$HOME/my-tools/hello"
Hello from my command!
```

しかし、`my-tools` がPATHに含まれていなければ、コマンド名だけでは実行できません。

```console
$ hello
zsh: command not found: hello
```

そこで、`my-tools` を現在のPATHの先頭へ追加します。

```sh
export PATH="$HOME/my-tools:$PATH"
```

もう一度実行すると、今度はコマンド名だけで呼び出せます。

```console
$ hello
Hello from my command!
```

これが「PATHが通った」状態です。

## PATHへの追加には一時的な設定と永続的な設定がある

先ほど実行した `export` は、現在開いているターミナルでのみ有効です。ターミナルを閉じると設定は失われます。

```sh
export PATH="$HOME/my-tools:$PATH"
```

毎回使うコマンドなら、シェルの設定ファイルに同じ内容を記述します。どのファイルを使うかはシェルによって異なります。

| シェル | 主な設定ファイル |
| --- | --- |
| zsh | `~/.zshrc` |
| Bash | `~/.bashrc` |

利用中のシェルは、次のコマンドで確認できます。

```sh
echo "$SHELL"
```

たとえばzshを使っているなら、`~/.zshrc` に次の1行を追加します。

```sh
export PATH="$HOME/my-tools:$PATH"
```

新しいターミナルを開けば設定が読み込まれます。すぐに反映したい場合は、次のコマンドを実行します。

```sh
source "$HOME/.zshrc"
```

Bashの場合は、利用環境に応じて `~/.bashrc` などの設定ファイルを読み込みます。

```sh
source "$HOME/.bashrc"
```

OSやツールによって推奨される設定先は異なります。インストール時にPATH設定の案内が表示された場合は、まずその手順を確認してください。

## PATHを通しても動かないときの確認手順

`command not found` が出たからといって、必ずPATHだけが原因とは限りません。次の順番で確認すると、問題を切り分けやすくなります。

### 1. ツールがインストールされているか確認する

インストール自体が失敗していれば、PATHを変更しても実行できません。まず、利用したパッケージマネージャーの一覧やインストールログを確認します。

ツールによっては、インストールの最後に次のような案内が表示されます。

```text
Add /Users/example/.local/bin to your PATH
```

この場合、実行ファイルの保存先は `/Users/example/.local/bin` です。このディレクトリをPATHへ追加します。

### 2. 実行ファイルのあるディレクトリがPATHに含まれているか確認する

PATHを1行ずつ表示すると、登録内容を読みやすくできます。

```sh
printf '%s\n' "$PATH" | tr ':' '\n'
```

実行ファイルが `/Users/example/.local/bin/sample-cli` にあるなら、PATHへ追加するのはファイルそのものではなく、その親ディレクトリです。

```sh
# 正しい例
export PATH="$HOME/.local/bin:$PATH"
```

```sh
# 誤った例：実行ファイル自体を追加している
export PATH="$HOME/.local/bin/sample-cli:$PATH"
```

### 3. 設定ファイルが読み込まれているか確認する

設定ファイルへ追記しても、すでに開いているターミナルには自動で反映されません。新しいターミナルを開くか、`source` コマンドで設定を読み直します。

### 4. 実行権限を確認する

ファイルは存在していても、実行権限がないとコマンドとして実行できません。権限は `ls -l` で確認できます。

```sh
ls -l "$HOME/.local/bin/sample-cli"
```

自分で作成したスクリプトで実行権限が足りない場合は、次のように追加します。

```sh
chmod +x "$HOME/.local/bin/sample-cli"
```

配布されたツールの権限がおかしい場合は、むやみに変更する前に公式のインストール手順を見直してください。

### 5. シェルが記憶している検索結果を更新する

シェルが以前の検索結果を保持していることがあります。新しいターミナルを開いても解決しない場合は、利用中のシェルに応じて検索結果を更新します。

```sh
# zsh
rehash

# Bash
hash -r
```

更新後、`command -v` で認識されているか確認します。

```sh
command -v sample-cli
```

## WindowsではPathをセミコロンで区切る

Windowsにも同じ役割を持つ環境変数 `Path` があります。PowerShellでは、次のコマンドで登録されているディレクトリを1行ずつ確認できます。

```powershell
$env:Path -split ';'
```

コマンドの場所を確認するには `Get-Command` を使います。

```powershell
Get-Command git
```

Windowsでは、環境変数の設定画面からユーザー環境変数の `Path` を編集できます。設定後は、新しいターミナルを開いて動作を確認します。既存の値をすべて置き換えるとほかのコマンドが動かなくなるため、必要なディレクトリを新しい項目として追加してください。

## PATHを書き換えるときの注意点

PATHの設定ミスは、別のコマンドが動かなくなる原因になります。特に次の点に注意してください。

### 既存のPATHを消さない

次の書き方では、もともと登録されていた検索先が失われます。

```sh
# 避ける
export PATH="$HOME/my-tools"
```

既存の設定を残すには、`$PATH` を含めます。

```sh
export PATH="$HOME/my-tools:$PATH"
```

### 信頼できないディレクトリを追加しない

PATHに登録したディレクトリへ悪意のある実行ファイルが置かれると、意図しないコマンドを実行するおそれがあります。誰でも書き込めるディレクトリや、出どころの分からないディレクトリは追加しないでください。

また、カレントディレクトリを表す `.` をPATHへ追加する設定も、同名の不正なファイルを誤って実行する原因になるため避けたほうが安全です。

### 同じ設定を何度も追加しない

インストーラーの案内に従うたび、同じ `export PATH=...` を設定ファイルへ追記してしまうことがあります。設定前に `~/.zshrc` や `~/.bashrc` を確認し、同じ行がすでにないか探しましょう。

## まとめ：PATHが分かればcommand not foundを切り分けられる

PATHは、シェルがコマンドを探すディレクトリの一覧です。「PATHが通っていない」とは、実行ファイルのあるディレクトリが、その検索先に含まれていない状態を指します。

エラーが出たら、まず次の3点を確認します。

1. ツールが実際にインストールされているか
2. 実行ファイルがどこにあるか
3. その親ディレクトリがPATHに含まれているか

PATHは一度仕組みを理解すれば、さまざまなCLIで起きる `command not found` の調査に使えます。設定例をそのままコピーする前に、「どの実行ファイルを、どのディレクトリから見つけたいのか」を確認すると、落ち着いて解決できるようになります。
