「JavaScriptは宣言をスコープの先頭へ巻き上げる」と教わり、`var` は `undefined` なのに `let` はエラー、関数宣言は呼べるのに関数式は呼べない、という例外の多さに戸惑っていないでしょうか。

結論から言うと、ソースコードが物理的に移動するわけではありません。**スコープのコードを評価する前に宣言を処理してbindingを準備し、その後で文を上から評価する**と捉えると整理できます。違いを生むのは、bindingがいつ作られ、いつ初期化され、いつ値が代入されるかです。

「hoisting」はECMAScript仕様の中心的なアルゴリズム名ではなく、観察される複数の挙動をまとめた説明用語です。実務では、巻き上げに依存した書き方を増やすより、エラーから宣言の状態を正しく読み取るために仕組みを理解するのが有効です。

この記事では、起動処理を作る例を直しながら、`var`、`let`、`const`、関数、class、importの違い、TDZ、循環依存、デバッグ方法まで説明します。

## 最初に比較表

宣言より前で識別子へアクセスした結果を、モジュールまたはstrict modeに近い前提でまとめます。

| 書き方 | bindingの準備 | 宣言行より前の読み取り |
| --- | --- | --- |
| `var value` | 作成され `undefined` で初期化 | `undefined` |
| `let value` | 作成されるが未初期化 | `ReferenceError` |
| `const value` | 作成されるが未初期化 | `ReferenceError` |
| `class User` | 作成されるが未初期化 | `ReferenceError` |
| `function load() {}` | 関数オブジェクトで初期化 | 呼び出せる |
| `const load = () => {}` | `const` として未初期化 | `ReferenceError` |
| `var load = () => {}` | `undefined` で初期化 | 呼ぶと `TypeError` |

表を暗記するより、「bindingの作成」「初期化」「代入または宣言の評価」を分けます。`let` と `const` はbinding自体が存在しないのではなく、初期化前なので読み取れません。この期間がTemporal Dead Zone、略してTDZです。

## コードは移動せず、宣言が先に処理される

起動処理を宣言より前で呼んだ例を見ます。関数宣言の `startApp` は呼び出せますが、その中で読む `apiUrl` はまだ初期化されていません。

```js
startApp();

const apiUrl = "https://example.test";

function startApp() {
  console.log(`connecting to ${apiUrl}`);
}
```

実行すると `apiUrl` へのアクセスで `ReferenceError` になります。説明用に二段階へ分けると、次のイメージです。これは仕様のソース変換をそのまま表すコードではなく、処理順を理解するための疑似コードです。

```text
【宣言の準備】
- startApp bindingを作り、関数オブジェクトで初期化する
- apiUrl bindingを作るが、まだ初期化しない

【文の評価】
- startApp()を実行する
- const宣言を評価し、apiUrlを文字列で初期化する
```

関数やグローバル、モジュールのコードを実行するとき、仕様ではDeclaration Instantiationに相当する処理が行われます。実際のアルゴリズムは実行コンテキストや宣言の種類ごとに分かれますが、学習時には「準備してから評価する」という軸が役立ちます。

安全な起動コードは、依存する値を初期化した後に入口を呼びます。関数宣言を下へ置けることと、依存値まで利用可能であることは別問題です。

```js
const apiUrl = "https://example.test";

function startApp() {
  console.log(`connecting to ${apiUrl}`);
}

startApp();
```

## varは宣言と代入が別になる

`var` のbindingは、関数コードなら関数の宣言処理時に作られ、`undefined` で初期化されます。初期化式の代入は、その文へ到達したときに実行されます。

```js
function readPort() {
  console.log(port); // undefined
  var port = 3000;
  console.log(port); // 3000
}

readPort();
```

よくある「先頭へ移動したコード」への書き換えは、結果を説明する比喩としては使えます。しかし、エンジンが実際にこのソースへ変換しているわけではありません。

```js
// 結果を説明するためのイメージであり、実際の変換ではない
function readPort() {
  var port;
  console.log(port);
  port = 3000;
  console.log(port);
}
```

`var` はブロックスコープを作らないため、`if` や `for` の外からも同じ関数内なら参照できます。さらに同じスコープで再宣言できるので、意図しない上書きを見逃しやすくなります。

```js
function chooseEndpoint(useMock) {
  if (useMock) {
    var endpoint = "http://localhost:3000";
  }

  return endpoint; // falseならundefined
}
```

ブラウザーの古典的なscript最上位にある `var` は、条件を満たすとグローバルオブジェクトのプロパティにもなります。一方、`let`、`const`、classのグローバルbindingは同じ扱いではなく、ES Modulesの最上位も別です。`window.someName` と識別子 `someName` を同一視すると、実行形式を変えたときに壊れます。

新しいコードで `var` を選ぶ積極的な理由はほとんどありません。値を再代入するなら `let`、しないなら `const` を使うと、スコープと初期化位置が明確になります。

## let・constとTDZ

`let` と `const` のbindingはスコープの開始時点から存在しますが、宣言を評価して初期化するまでアクセスできません。スコープの先頭から宣言直前までがTDZです。

```js
const mode = "production";

function boot() {
  console.log(mode); // ReferenceError
  const mode = "development";
}

boot();
```

関数内の `mode` は外側の `mode` をshadowingしています。宣言行より前だから外側へ探索が戻るわけではありません。内側のbindingはすでに存在するものの未初期化なので、そこで `ReferenceError` になります。

通常、未宣言変数でも安全に確認できると説明される `typeof` も、TDZ内では例外になります。

```js
console.log(typeof notDeclared); // "undefined"

{
  console.log(typeof token); // ReferenceError
  let token = "abc";
}
```

これは、`notDeclared` というbindingが見つからない場合と、未初期化の `token` bindingが見つかった場合の違いです。設定の有無を `typeof` で判定するコードでも、同一スコープに後続宣言がないか確認する必要があります。

`const` は宣言時に初期値が必須で、bindingへの再代入を禁止します。オブジェクト自体を不変にする機能ではありません。巻き上げの説明と、値の可変性の説明を混ぜないようにします。

```js
const config = { retries: 2 };
config.retries = 3; // オブジェクトの変更は可能

// config = {};     // bindingへの再代入なのでTypeError
```

TDZは単なる不便ではありません。初期化前の値を `undefined` として処理し、後続の不具合へつなげるより、その場で失敗させます。宣言を利用箇所より前に置けば、通常はTDZへ依存せず読めるコードになります。

## 関数宣言は先に呼べる

関数宣言は、スコープの宣言処理で関数オブジェクトまで作られるため、宣言より前から呼べます。主要処理を上に置き、補助関数を下に置く構成も可能です。

```js
const config = loadConfig();
startApp(config);

function loadConfig() {
  return { endpoint: "https://example.test", retries: 2 };
}

function startApp({ endpoint }) {
  console.log(`connecting to ${endpoint}`);
}
```

ただし、関数の中で参照する値まで初期化済みとは限りません。先ほどの `startApp` と `apiUrl` の例のように、関数を呼べることと、関数本体が安全に完了することを分けて考えます。

同じスコープへ同名の関数宣言や `var` 宣言を重ねたときの処理順には細かな規則があります。それを利用して後の宣言で上書きするコードは、読み手が結果を予測しにくいため避けます。lintの重複宣言ルールで早期に検出する方が安全です。

## 関数式とアロー関数は変数側の規則に従う

関数式やアロー関数では、右辺の関数オブジェクトは代入文を評価したときに作られます。左辺が `const` なら宣言前はTDZ、`var` なら値は `undefined` です。

```js
// connect(); // ReferenceError
const connect = function connectToApi() {
  return "connected";
};

// parse(); // ReferenceError
const parse = (text) => JSON.parse(text);
```

`var` を使った関数式を宣言前に呼ぶと、識別子の読み取り自体は成功しますが、`undefined` を関数として呼ぶため `TypeError` になります。

```js
run(); // TypeError: run is not a function

var run = function () {
  console.log("running");
};
```

この違いはデバッグの手掛かりです。`Cannot access ... before initialization` ならTDZ、`... is not a function` で値が `undefined` なら、`var` の代入前や誤ったimport/exportを疑えます。

関数宣言と `const` の関数式のどちらが常に優れているわけではありません。宣言前から利用可能にしたい名前付き処理には関数宣言、値として組み立てるコールバックや条件付きの実装には関数式が自然です。プロジェクト内で意図を揃える方が、巻き上げだけを理由に統一するより重要です。

## ブロック内の関数宣言に依存しない

ES Modulesやstrict modeでは、ブロック内の関数宣言はそのブロックへスコープされます。しかし、非strictの古いWeb向けコードには互換性規則があり、ブロック外での見え方が複雑です。

```js
"use strict";

if (true) {
  function createClient() {
    return { mode: "mock" };
  }

  console.log(createClient());
}

// console.log(createClient()); // ReferenceError
```

実行環境差を避けるなら、ブロック内で `const` の関数式を使い、必要な範囲を明示します。条件で実装を切り替えるなら、外側の変数へ関数値を選んで代入する方が意図を読み取りやすくできます。

```js
const createClient = useMock
  ? () => ({ mode: "mock" })
  : () => ({ mode: "production" });
```

## class宣言もTDZを持つ

class宣言は関数宣言のように先にインスタンス化できません。bindingは作られますが、class定義の評価まで未初期化です。

```js
// const client = new ApiClient(); // ReferenceError

class ApiClient {
  constructor(endpoint) {
    this.endpoint = endpoint;
  }
}

const client = new ApiClient("https://example.test");
```

class内部ではクラス名を参照できます。`extends` の式、computed property name、static field、static blockなどには評価順の規則があるため、複雑な副作用を埋め込むと理解しにくくなります。class定義は型の形を示す場所に留め、重い初期化や外部I/Oは明示的な関数へ分けるのが無難です。

class式を変数へ代入する場合も、外側から見た利用可能時点は変数宣言の規則に従います。`const ApiClient = class {}` なら `const` の宣言前はTDZです。

## importはモジュールのリンクと評価で考える

`import` 宣言はモジュールのトップレベルにしか書けませんが、記述位置より前のコードからimportしたbindingを参照できます。モジュールは実行前に依存関係を読み込み、リンクしてから評価されるためです。

```js
// app.js
console.log(formatPrice(1200));

import { formatPrice } from "./price.js";
```

ただし、これを単純に「importも巻き上がる」とだけ覚えると、循環依存を説明できません。importは値のコピーではなく、export元のbindingへのlive bindingです。依存モジュールの評価順や、export元bindingの初期化時点が関わります。

次のような循環では、`a.js` の `valueA` が初期化される前に `b.js` が読み取ろうとして、`ReferenceError` になり得ます。

```js
// a.js
import { valueB } from "./b.js";
export const valueA = `A -> ${valueB}`;
```

```js
// b.js
import { valueA } from "./a.js";
export const valueB = `B -> ${valueA}`;
```

循環を見つけたら、共有定数を第三のモジュールへ移す、初期化時の読み取りを関数呼び出しまで遅らせる、依存方向を一方向に直す、といった方法を検討します。循環自体が常に禁止ではありませんが、トップレベルで相互の値を必要とする設計は壊れやすくなります。

## デフォルト引数にも評価順がある

関数のデフォルト引数は呼び出し時に左から評価されます。前の引数は後ろのデフォルト式から参照できますが、後ろの引数を先に読むと未初期化でエラーになります。また、関数本体で宣言した変数はデフォルト引数の評価環境から利用できません。

```js
function createRequest(
  endpoint,
  timeout = 3000,
  options = { endpoint, timeout },
) {
  return options;
}

console.log(createRequest("/api/users"));
```

複雑なデフォルト式は、巻き上げ以前にAPIを読みにくくします。外部I/Oや状態変更は避け、必要なら関数本体で明示的に初期値を組み立てます。

## switchのcaseは同じブロックスコープ

`switch` の各 `case` は、自動的に別のブロックスコープを作りません。同名の `let` や `const` を複数caseで宣言すると構文エラーになります。caseを波括弧で囲むと、宣言の範囲が明確になります。

```js
switch (mode) {
  case "development": {
    const client = createMockClient();
    start(client);
    break;
  }
  case "production": {
    const client = createApiClient();
    start(client);
    break;
  }
}
```

これはTDZの実行時エラーではなく、同一スコープでの字句宣言重複による早期エラーです。「宣言前アクセス」だけでなく、まずパーサーが受理したかを区別します。

## エラー文から状態を推測する

巻き上げに関連しそうな不具合では、例外の種類と発生位置を確認します。メッセージの具体的な文言はエンジンで異なりますが、概ね次のように切り分けられます。

- `ReferenceError: Cannot access 'x' before initialization`：同じスコープにbindingはあるがTDZにいる。
- `ReferenceError: x is not defined`：スコープチェーン上にbindingが見つからない。スペル、import、宣言範囲を疑う。
- `TypeError: x is not a function`：読み取りはできたが呼び出し可能な値ではない。`var` の代入前、export形式、上書きを疑う。
- `SyntaxError`：重複した字句宣言、import位置など、評価前の構文・早期エラーを疑う。

ブレークポイントで停止し、SourcesパネルのScope欄からLocal、Script、Module、Globalなどを確認すると、どのbindingを参照しているか分かります。ビルド後だけ発生する場合は、正しいsource mapが読み込まれているか、scriptとmoduleの実行形式が変わっていないかも確認します。

最小再現を作るときは、Node.jsのCommonJS、ES Modules、ブラウザーの古典的scriptを混ぜません。最上位スコープとstrict modeの扱いが異なるためです。対象と同じ実行形式で再現させます。

## 実務での設計ルール

巻き上げの知識は必要ですが、知識がないと読めない配置を積極的に作る必要はありません。次の方針にすると、初期化順の不具合を減らせます。

1. `var` を避け、再代入しないbindingは `const` にする。
2. 値や依存は利用前に初期化し、モジュールの入口は最後に呼ぶ。
3. 関数宣言を先に呼ぶ場合でも、関数が読む外部値の初期化を確認する。
4. ブロック内関数宣言や重複宣言の互換挙動へ依存しない。
5. importの循環を可視化し、トップレベルの相互読み取りを避ける。
6. lintで未定義変数、利用前宣言、重複宣言を検出する。

宣言を常にファイル先頭へ集めればよいわけでもありません。関連する値を利用箇所の近くに置くことは可読性を高めます。重要なのは、初期化より前に評価される経路がなく、所有するスコープが短く、依存順が読めることです。

## まとめ

巻き上げは、コードが上へ移動する現象ではありません。スコープの評価前に宣言を処理してbindingを準備するため、宣言の種類ごとに「前から使えるように見える」挙動が生まれます。

- `var` は先に `undefined` で初期化され、代入は文の評価時に行われる。
- `let`、`const`、classはbindingが存在しても、宣言評価まではTDZにある。
- 関数宣言は関数オブジェクトまで初期化されるため、宣言前に呼べる。
- 関数式とアロー関数は、代入先である変数宣言の規則に従う。
- importはモジュールのリンク、live binding、評価順まで含めて理解する。
- エラーの種類とスコープを確認し、物理的なコード移動という比喩だけで判断しない。

普段は初期化順が上から自然に読めるコードを書き、予想外のエラーに遭遇したときに「作成済みか、初期化済みか、代入済みか」を確認する。この使い方が、巻き上げの知識を最も実務的に生かせます。
