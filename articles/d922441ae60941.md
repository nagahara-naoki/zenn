Factoryは、オブジェクトの生成手順を利用側から分離する考え方です。

JavaScriptでは、必ずしもclassや大きなパターン実装は必要ありません。通常の関数が、十分に良いFactoryになることもあります。

## 直接生成の問題

```ts
type ApiClient = {
  baseUrl: string;
  timeoutMs: number;
  headers: Record<string, string>;
};

const client: ApiClient = {
  baseUrl: process.env.API_URL ?? "",
  timeoutMs: 5_000,
  headers: {
    "x-app-version": "1.0.0",
  },
};
```

同じ初期化が複数箇所へ広がると、必須設定の追加や既定値の変更を漏らしやすくなります。

## Factory関数へ集める

```ts
type Environment = "development" | "production";

function createApiClient(environment: Environment): ApiClient {
  const baseUrl =
    environment === "production"
      ? "https://api.example.com"
      : "http://localhost:3000";

  return {
    baseUrl,
    timeoutMs: 5_000,
    headers: {
      "x-app-version": "1.0.0",
    },
  };
}

const client = createApiClient("production");
```

利用側は完成したclientを受け取り、生成に必要な既定値や分岐を知りません。

Factoryが有効なのは、単に `new` を関数で包んだときではなく、次の責務を引き受けるときです。

- 必須値の検証
- 既定値の適用
- 環境に応じた実装選択
- 複数オブジェクトの組み立て
- 生成失敗の表現

## 生成に失敗する場合

入力検証をFactoryへ集めると、不完全なオブジェクトが後段へ流れにくくなります。

```ts
function createApiClientFromEnv(
  env: Record<string, string | undefined>,
): ApiClient {
  const baseUrl = env.API_URL;

  if (!baseUrl) {
    throw new Error("API_URL is required");
  }

  return {
    baseUrl,
    timeoutMs: 5_000,
    headers: {},
  };
}
```

非同期I/Oが必要なら、Promiseを返すasync Factoryにもできます。

## JotaiのatomをFactory的に読む

Jotaiの `atom` はatom configを生成する関数です。

```ts
import { atom } from "jotai";

const countAtom = atom(0);
const doubledAtom = atom((get) => get(countAtom) * 2);
```

引数の形に応じてprimitive atom、read-only derived atomなどの設定を作ります。利用側はatom configの内部構造を直接組み立てません。

この「入力から必要な構成オブジェクトを生成する」という点はFactory的に読めます。

ただし、Jotai公式がGoFのFactory Methodパターンとして説明しているわけではありません。ここでの目的は、実在APIを通して生成責務の分離を見ることです。

## Redux ToolkitのcreateSlice

`createSlice` も設定から複数の成果物を生成します。

```ts
const counterSlice = createSlice({
  name: "counter",
  initialState: { value: 0 },
  reducers: {
    increment(state) {
      state.value += 1;
    },
  },
});
```

結果にはreducer、action creators、action typesなどが含まれます。利用側がそれぞれを個別に組み立てなくてよい点でFactory的です。

## Factory Methodとの違い

「Factory」は広い言葉です。GoFのFactory Methodは、生成処理をサブクラス側へ委ねる構造を指します。

この記事の関数Factoryは、より一般的な「生成を専用の関数へ集める」方法です。用語を使うときは、どの意味かを明示します。

## 使うべき場面

- 生成ルールが複数箇所で重複している
- 入力に応じて実装や種類を切り替える
- 不正な状態のオブジェクトを作らせたくない
- 利用側から設定や依存の組み立てを隠したい

## 使わなくてよい場面

```js
const point = { x: 10, y: 20 };
```

この程度の単純な値へFactoryを追加しても、間接層が増えるだけです。

生成ルール、検証、分岐がなく、オブジェクトリテラルやconstructorで意図が明確なら、そのまま作る方が読みやすくなります。

## まとめ

Factoryの価値は「生成を隠すこと」ではなく、生成に関する判断を1か所へ集めることです。

- 利用側は完成品の使い方へ集中できる
- 必須値や既定値を統一できる
- 実装選択を生成側へ閉じ込められる
- 単純な生成には無理に導入しない
