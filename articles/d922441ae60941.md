オブジェクト生成は、最初はリテラルや `new` の1行で終わります。しかし、必須値の検証、環境別の既定値、依存オブジェクトの組み立て、生成失敗の表現が加わると、生成する側が本来知らなくてよい判断まで抱え始めます。

Factoryは、完成したオブジェクトを得るまでの判断と組み立てを、利用側から分離する考え方です。本記事ではTypeScriptの関数Factoryを中心に、入力検証、依存注入、非同期生成、テスト、ライフサイクルまで段階的に設計します。重要なのは `new` を隠すことではなく、「有効なオブジェクトをどう作るか」という知識を1か所へ集めることです。

## 生成コードが各所へ散った状態

APIクライアントを画面やジョブごとに直接組み立てる例から考えます。

```ts
type ApiClient = {
  baseUrl: string;
  timeoutMs: number;
  headers: Record<string, string>;
};

const client: ApiClient = {
  baseUrl: process.env.API_URL ?? "",
  timeoutMs: Number(process.env.API_TIMEOUT_MS ?? "5000"),
  headers: {
    "x-app-version": process.env.APP_VERSION ?? "unknown",
  },
};
```

短く見えますが、空のURL、`NaN`、負のtimeoutがそのまま入り得ます。同じ生成コードを別のentry pointへコピーすれば、ある場所だけ既定値が異なる、ヘッダーを付け忘れる、といった不整合も起きます。利用側は通信したいだけなのに、環境変数名と設定規則を知っています。

さらに実クライアントが認証、logger、`fetch` 実装を必要とするなら、生成順序まで呼び出し側へ漏れます。

```ts
// 問題のある利用例：各所が同じ配線と既定値を再現する
const transport = new FetchTransport(globalThis.fetch, 5_000);
const auth = new BearerAuth(process.env.API_TOKEN ?? "");
const users = new UsersApi(transport, auth, console);
```

この配線が1か所だけで安定しているなら、まだFactoryは不要です。複数の利用側で同じ生成規則を再現し始めたとき、または不完全なinstanceを作れてしまうときが分離の合図です。

## Factoryという言葉の範囲を整理する

広い意味のFactoryは、値を受け取り、利用可能なオブジェクトを返す生成専用の関数やオブジェクトです。JavaScriptでは普通の関数だけで十分なことが多く、本記事もこの意味で「関数Factory」を扱います。

一方、GoFのFactory Methodは、生成のための操作を定義し、どの具象製品を作るかをsubclassへ委ねる生成パターンです。Abstract Factoryは、関連する製品群を具象classを指定せず作るinterfaceを提供します。「Factory」と呼ばれる関数が、どちらかのGoFパターンへ自動的に分類されるわけではありません。

この区別は実装選択に影響します。JavaScriptで1種類の設定済みobjectを作るだけなら、継承階層を導入せず関数を使う方が自然です。必要になった責務だけをFactoryへ持たせます。

## 最小の関数Factoryを作る

まず、環境ごとの違いと共通の既定値を1つの関数へ集めます。戻り値を `Readonly` にし、生成後に設定が偶然書き換わるのを型で防ぎます。

```ts
type Environment = "development" | "test" | "production";

type ApiClientConfig = Readonly<{
  baseUrl: string;
  timeoutMs: number;
  headers: Readonly<Record<string, string>>;
}>;

function createApiClientConfig(environment: Environment): ApiClientConfig {
  const baseUrlByEnvironment: Record<Environment, string> = {
    development: "http://localhost:3000",
    test: "http://localhost:3001",
    production: "https://api.example.com",
  };

  return {
    baseUrl: baseUrlByEnvironment[environment],
    timeoutMs: 5_000,
    headers: { "x-app-version": "1.0.0" },
  };
}
```

利用側は完成した設定を受け取り、環境ごとのURLやtimeoutの由来を知りません。

```ts
const config = createApiClientConfig("production");

console.log(config.baseUrl);   // https://api.example.com
console.log(config.timeoutMs); // 5000
```

ただし、処理を関数へ移しただけでは価値が十分とは限りません。Factoryが有効なのは、検証、既定値、具象実装の選択など、生成時に守る契約がある場合です。

## 外部入力を境界で検証する

TypeScriptの型は、環境変数やJSONの実行時値を検証しません。`as Environment` とキャストすると、未知の文字列を型検査から隠すだけです。Factoryの入力へ入る前に値を解析します。

```ts
function parseEnvironment(value: string | undefined): Environment {
  if (value === "development" || value === "test" || value === "production") {
    return value;
  }
  throw new Error(`invalid APP_ENV: ${value ?? "<missing>"}`);
}

function parsePositiveInteger(
  name: string,
  value: string | undefined,
  fallback: number,
): number {
  if (value === undefined) return fallback;
  const parsed = Number(value);
  if (!Number.isSafeInteger(parsed) || parsed <= 0) {
    throw new Error(`${name} must be a positive integer`);
  }
  return parsed;
}
```

環境変数を受け取るFactoryは、グローバルな `process.env` を内部で直接読むより、辞書として引数に受け取るとテストしやすくなります。URLも `new URL()` で構文を確かめ、許可するprotocolを限定します。

```ts
function createApiConfigFromEnv(
  env: Readonly<Record<string, string | undefined>>,
): ApiClientConfig {
  const environment = parseEnvironment(env.APP_ENV);
  const defaults = createApiClientConfig(environment);
  const baseUrl = new URL(env.API_URL ?? defaults.baseUrl);

  if (!new Set(["http:", "https:"]).has(baseUrl.protocol)) {
    throw new Error("API_URL must use http or https");
  }

  return {
    ...defaults,
    baseUrl: baseUrl.toString().replace(/\/$/, ""),
    timeoutMs: parsePositiveInteger(
      "API_TIMEOUT_MS",
      env.API_TIMEOUT_MS,
      defaults.timeoutMs,
    ),
    headers: {
      "x-app-version": env.APP_VERSION ?? "unknown",
    },
  };
}
```

このFactoryは「不正な設定なら起動時に失敗する」という方針です。通信するたびに設定エラーが出るより、entry pointで即座に原因を示せます。ただし、利用者入力から生成する場合は例外ではなく、検証エラーを値として返す方が扱いやすいこともあります。失敗の表現は利用境界に合わせます。

### 生成失敗を値で返す選択肢

起動設定は例外で停止するのが自然でも、画面で利用者が入力した接続先を試す機能では、入力不備は予想された結果です。判別可能なUnion型を返せば、呼び出し側がerror messageの文字列を解析せず分岐できます。

```ts
type ConfigResult =
  | { ok: true; value: ApiClientConfig }
  | { ok: false; reason: "invalid_url" | "invalid_timeout" };

function tryCreateApiConfig(
  input: { baseUrl: string; timeoutMs: number },
): ConfigResult {
  let url: URL;
  try {
    url = new URL(input.baseUrl);
  } catch {
    return { ok: false, reason: "invalid_url" };
  }

  if (url.protocol !== "http:" && url.protocol !== "https:") {
    return { ok: false, reason: "invalid_url" };
  }

  if (!Number.isSafeInteger(input.timeoutMs) || input.timeoutMs <= 0) {
    return { ok: false, reason: "invalid_timeout" };
  }

  return {
    ok: true,
    value: { baseUrl: url.toString(), timeoutMs: input.timeoutMs, headers: {} },
  };
}
```

例外とResultのどちらが常に優れているわけではありません。呼び出し側が回復・表示できる失敗は値、設定破損や予期しない初期化障害は原因を保持した例外、というように分けます。Factory間で同じ失敗を別々の方法で表すと利用側が複雑になるため、project内の境界ごとに方針を揃えます。

`reason` は画面表示文ではなく安定した識別子にします。表示文をFactoryから返すと、翻訳やUI表現が生成処理へ入り込みます。入力欄ごとの詳細が必要なら、field名とcodeを持つ検証errorを返し、presentation層で文言へ変換します。これによりFactoryのtestは文言ではなく、失敗の意味を固定できます。

## 依存まで組み立てる

次に、実際の通信を行うclientを作ります。テスト時に通信を差し替えられるよう、`fetch` とloggerを依存として受け取ります。Factoryは既定の依存を選びますが、上書きも可能にします。

```ts
type Logger = Pick<Console, "info" | "error">;
type FetchLike = typeof fetch;

class ApiClientImpl {
  constructor(
    private readonly config: ApiClientConfig,
    private readonly fetchImpl: FetchLike,
    private readonly logger: Logger,
  ) {}

  async getJson<T>(path: string, signal?: AbortSignal): Promise<T> {
    const url = new URL(path, `${this.config.baseUrl}/`);
    const timeoutSignal = AbortSignal.timeout(this.config.timeoutMs);
    const requestSignal = signal
      ? AbortSignal.any([signal, timeoutSignal])
      : timeoutSignal;
    this.logger.info("request", url.toString());
    const response = await this.fetchImpl(url, {
      headers: this.config.headers,
      signal: requestSignal,
    });
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    return (await response.json()) as T;
  }
}
```

```ts
type ApiClientDependencies = Readonly<{
  fetchImpl?: FetchLike;
  logger?: Logger;
}>;

function createApiClient(
  config: ApiClientConfig,
  dependencies: ApiClientDependencies = {},
): ApiClientImpl {
  return new ApiClientImpl(
    config,
    dependencies.fetchImpl ?? globalThis.fetch,
    dependencies.logger ?? console,
  );
}
```

呼び出し側は完成品だけを使います。`ApiClientImpl` のconstructorをexportせず、Factoryだけを公開すれば生成経路を強制できます。ただし、それによって高度な利用者の拡張やテストを不必要に妨げる場合もあります。公開範囲は「常に隠す」ではなく、守りたい不変条件に合わせます。

## テストで生成規則を確認する

Factoryのテストでは、生成されたobjectのprivate fieldを覗くのではなく、公開された振る舞いを確認します。偽の `fetch` とloggerを渡せば、ネットワークなしで検証できます。

```ts
import assert from "node:assert/strict";
import test from "node:test";

test("factory applies validated configuration", async () => {
  const requestedUrls: string[] = [];
  const fakeFetch: FetchLike = async (input) => {
    requestedUrls.push(input.toString());
    return Response.json({ id: 1, name: "Ada" });
  };

  const client = createApiClient(
    createApiConfigFromEnv({ APP_ENV: "test" }),
    { fetchImpl: fakeFetch, logger: { info() {}, error() {} } },
  );

  const user = await client.getJson<{ id: number; name: string }>("users/1");
  assert.deepEqual(user, { id: 1, name: "Ada" });
  assert.deepEqual(requestedUrls, ["http://localhost:3001/users/1"]);
});
```

不正入力が生成段階で拒否されることも固定します。これは「半分だけ初期化されたclientを返さない」というFactoryの重要な契約です。

```ts
test("factory rejects invalid timeout", () => {
  assert.throws(
    () =>
      createApiConfigFromEnv({
        APP_ENV: "production",
        API_TIMEOUT_MS: "zero",
      }),
    /positive integer/,
  );
});

test("factory rejects an unsupported environment", () => {
  assert.throws(
    () => createApiConfigFromEnv({ APP_ENV: "staging" }),
    /invalid APP_ENV/,
  );
});
```

型で隠れたprivate構造に依存するテストは、内部整理だけで壊れます。一方、URL、エラー、通信結果という利用者が観測できる契約を検証すれば、Factoryと製品classの実装を安全に変更できます。

## 非同期Factoryと後始末

DB connectionや暗号鍵の読み込みなど、完成までI/Oが必要ならFactoryも非同期になります。constructor内でPromiseを開始すると、利用可能になる時点が曖昧です。`create` が準備完了後のresourceだけを返す方が扱いやすくなります。

```ts
type Database = {
  query(sql: string): Promise<unknown>;
  close(): Promise<void>;
};

type OpenConnection = (url: string) => Promise<Database>;

async function createDatabase(
  url: string,
  openConnection: OpenConnection,
): Promise<Database> {
  const connection = await openConnection(url);
  await connection.query("SELECT 1");

  return {
    query: (sql) => connection.query(sql),
    close: () => connection.close(),
  };
}
```

非同期Factoryで接続後の検証に失敗した場合は、途中で得たresourceを解放する必要があります。生成失敗がresource leakを生まないよう、所有権の移動点を明確にします。

```ts
async function createVerifiedDatabase(
  url: string,
  openConnection: OpenConnection,
): Promise<Database> {
  const connection = await openConnection(url);
  try {
    await connection.query("SELECT 1");
    return {
      query: (sql) => connection.query(sql),
      close: () => connection.close(),
    };
  } catch (error) {
    await connection.close();
    throw error;
  }
}
```

Factoryが毎回新しいinstanceを返すのか、cacheした共有instanceを返すのかも契約です。無断でcacheすると、テスト間やrequest間で状態が共有されます。共有が必要なら、Factoryではなくcomposition rootで1回だけ生成して渡す方法も検討します。

## JotaiのatomをFactory的に読む

Jotai公式ドキュメントは `atom` を「atom configを作る関数」と説明しています。初期値を渡すprimitive atom、read関数を渡すread-only derived atom、readとwriteを渡すwritable derived atomなど、引数に応じた設定objectが返ります。値そのものはatom configではなくstore側に保持されます。

```ts
import { atom } from "jotai";

const countAtom = atom(0);
const doubledAtom = atom((get) => get(countAtom) * 2);
const incrementAtom = atom(null, (_get, set) => {
  set(countAtom, (count) => count + 1);
});
```

利用側がatom configの内部構造を組み立てず、目的に応じた引数から完成した設定を得る点はFactory的に読めます。ただし、Jotai公式は `atom` をGoF Factory Methodパターンとして分類していません。これは生成責務をAPIへ集約する設計を理解するための教育的な類推です。GoFのFactory Methodが継承によって生成をsubclassへ委ねる構造と、関数のoverloadでconfigを作る `atom` は同一ではありません。

公式ドキュメントが、React render中に動的なatomを作る場合は参照を安定させるため `useMemo` または `useRef` が必要と注意している点も重要です。Factoryで作れば常に安全なのではなく、「いつ、何回生成するか」というライフサイクルは利用側に残ります。

## Redux ToolkitのcreateSliceにも生成APIを見る

Redux Toolkitの `createSlice` は、slice名、initial state、case reducerなどの設定からslice reducerとaction creatorをまとめて生成します。

```ts
import { createSlice } from "@reduxjs/toolkit";

const counterSlice = createSlice({
  name: "counter",
  initialState: { value: 0 },
  reducers: {
    increment(state) {
      state.value += 1;
    },
  },
});

export const { increment } = counterSlice.actions;
export const counterReducer = counterSlice.reducer;
```

設定から関連する複数の成果物を整合した名前で作る点に、FactoryやAbstract Factoryに似た生成責務を観察できます。しかしRedux Toolkit公式がGoFパターンとして分類しているわけではなく、返す成果物もRedux固有です。「Factoryという名前が付くか」ではなく、利用者からどの生成知識を引き取っているかを見る例です。

## より単純な代替案

不変条件がなく、値を1回作るだけならobject literalが最も明快です。constructorが検証と初期化を十分に担い、具象classも1つなら、直接 `new User(name)` と書く方が生成経路を追いやすいでしょう。引数が多いだけならoptions object、段階的な任意設定が多いならBuilderが候補です。

依存を組み立てる場所がapplication entry pointの1か所なら、専用Factoryを作らずcomposition rootへ明示的に並べる設計にも価値があります。配線を隠しすぎると、どの実装が選ばれたか追跡しにくくなります。DI containerも生成を自動化しますが、token登録やlifetimeという別の複雑さを持ち込むため、小規模な配線の第一候補ではありません。

## 失敗しやすい設計

- Factoryが生成だけでなく、取得・保存・業務判断まで担うと巨大なserviceになります。
- `process.env` や時刻を内部で直接読むと、同じ入力でも結果が変わりテストしにくくなります。
- 型キャストで外部入力を信用すると、不正な完成品を作れます。
- async初期化の途中で失敗したresourceを解放しないと、接続やhandleが漏れます。
- 毎回新規か共有かが曖昧だと、状態の隔離と性能の両方で予想外が起きます。
- Factoryの戻り値を巨大な具象class型にすると、利用側が内部実装へ結合します。必要なら小さなinterfaceを返します。
- 「テストしやすくするため」と、使われない上書きoptionを大量に公開すると契約がぼやけます。

Factory内部の分岐が増え続ける場合は、種類ごとの小さなFactoryへ分ける、Strategyで選択を注入する、関連する製品群ごとにAbstract Factoryを検討するなど、変化の軸を見直します。1つの万能 `createService(type, options)` にすべてを押し込めると、型の恩恵も失われます。

## 使うかどうかの判断基準

Factoryが向くのは、有効な完成品を作るために複数の規則がある、入力によって具象実装や既定値を選ぶ、同じ配線を複数箇所で再現している、生成が失敗し得る、テスト用の依存へ差し替えたい、といった場面です。呼び出し側が完成品の使い方だけへ集中できるなら、意味のある境界になっています。

反対に、単純な値、明快なconstructor、1か所だけの配線へ無理に導入すると間接層が増えます。導入前には「生成時に守る不変条件は何か」「誰が毎回・requestごと・processごとの生成を決めるか」「失敗と後始末をどう表すか」「Factoryの外へ漏らしたくない具体的知識は何か」を言葉にしてください。答えがなければ、まだリテラルや `new` で十分です。

## まとめ

Factoryの価値は、構文として `new` を包むことではなく、生成に必要な検証、既定値、依存選択、初期化、失敗処理を一貫した場所へ集めることです。JavaScriptでは小さな関数から始め、製品群や継承による拡張が本当に必要になったときだけ、GoFのFactory MethodやAbstract Factoryに近い構造を検討できます。

完成品が常に有効か、生成回数と共有範囲が明確か、途中失敗でresourceを解放できるかをテストしてください。JotaiやRedux Toolkitの生成APIは発想を学ぶ実例になりますが、公式のパターン分類と教育的な類推は分けて扱うことが、技術記事としての正確さにつながります。
