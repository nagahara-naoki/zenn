Adapterは、既存のインターフェースを、利用側が期待するインターフェースへ変換するパターンです。

フロントエンドでは、APIレスポンス、Web Storage、外部SDKなどをアプリ内部の型へ合わせる場面でよく使えます。

## 外部形式を画面へ漏らす問題

```ts
type UserResponse = {
  user_id: number;
  display_name: string;
  created_at: string;
};
```

この形式を画面で直接使うと、API都合のsnake_caseや日時文字列がアプリ全体へ広がります。

```ts
function UserProfile({ user }: { user: UserResponse }) {
  return (
    <p>
      {user.display_name} / {new Date(user.created_at).toLocaleDateString()}
    </p>
  );
}
```

API変更の影響が複数画面へ波及し、日時変換も重複します。

## Adapterで内部モデルへ変換する

```ts
type User = {
  id: number;
  displayName: string;
  createdAt: Date;
};

function adaptUser(response: UserResponse): User {
  const createdAt = new Date(response.created_at);

  if (Number.isNaN(createdAt.getTime())) {
    throw new Error("invalid created_at");
  }

  return {
    id: response.user_id,
    displayName: response.display_name,
    createdAt,
  };
}
```

画面は内部モデルだけを使います。

```tsx
function UserProfile({ user }: { user: User }) {
  return (
    <p>
      {user.displayName} / {user.createdAt.toLocaleDateString()}
    </p>
  );
}
```

外部仕様の変更をAdapterへ閉じ込め、内部では一貫した名前と型を使えます。

## TypeScriptの型だけでは検証できない

```ts
const response: UserResponse = await fetch("/api/user").then((value) =>
  value.json(),
);
```

型注釈は、通信で届いた値を実行時に検証しません。外部入力にはschema validatorや明示的なvalidationを組み合わせます。

```ts
const userResponse = UserResponseSchema.parse(await response.json());
const user = adaptUser(userResponse);
```

Adapterは「形を変える」、validatorは「入力が期待する形か確かめる」という別の責務です。必要なら境界の1つの処理として組み合わせます。

## RTK QueryのtransformResponse

RTK Queryの `transformResponse` は、base queryの戻り値をcacheへ保存する前に変換できます。

```ts
const api = createApi({
  baseQuery: fetchBaseQuery({ baseUrl: "/api" }),
  endpoints: (build) => ({
    getUser: build.query<User, number>({
      query: (id) => `users/${id}`,
      transformResponse: (response: UserResponse): User =>
        adaptUser(response),
    }),
  }),
});
```

コンポーネントが受け取る時点で内部の `User` に統一されるため、変換が各画面へ散らばりません。

これはAdapter的な配置です。ただし `transformResponse` 自体は汎用的なresponse変換フックであり、公式がGoF Adapterパターンとして分類しているわけではありません。

## atomWithStorageをAdapter的に読む

Jotaiの `atomWithStorage` は、Storage APIとatomの読み書きを接続します。

```ts
const darkModeAtom = atomWithStorage("darkMode", false);
```

利用側は `getItem`、`setItem`、storage eventを直接扱わず、atomとして状態を操作できます。

外部のstorage interfaceを状態管理のinterfaceへ適合させている点で、Adapter的に読めます。

## 変換方向を明示する

読み込みだけでなく保存もある場合は、関数名で方向を分けます。

```ts
type UpdateUserRequest = {
  display_name: string;
};

function toUpdateUserRequest(user: User): UpdateUserRequest {
  return {
    display_name: user.displayName,
  };
}
```

`adapt`、`fromResponse`、`toRequest` など、プロジェクトで命名を統一すると境界が見つけやすくなります。

## 使うべき場面

- 外部APIと内部モデルで命名・型が違う
- 外部SDKを自社の小さなinterfaceで包みたい
- 保存形式とドメイン型を分けたい
- 変更しにくい既存コード同士を接続したい

## 注意点

- Adapterへ業務ルールを詰め込みすぎない
- 不正入力を型キャストだけで通さない
- 変換のたびに情報を失っていないか確認する
- APIレスポンスと内部モデルを同じ名前の型にしない
- 日時、金額、IDなどの変換規則をテストする

## まとめ

Adapterは、異なるinterface同士の境界を明確にします。

- 外部形式をアプリ全体へ漏らさない
- 内部では用途に合った型と名前を使う
- runtime validationと役割を分ける
- 読み込み・書き込みの変換方向を明示する
