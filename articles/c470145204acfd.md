外部API、古いSDK、Web Storage、別チームのmoduleは、自分たちのアプリと異なる名前、型、失敗方法を持っています。その違いを利用側へ直接持ち込むと、`snake_case`、nullable、日時文字列、SDK固有エラーが画面や業務ロジックへ広がります。外部仕様の変更が、関係のないコードまで揺らす状態です。

Adapter（アダプター）は、既存のinterfaceを利用側が必要とするinterfaceへ変換する構造パターンです。本記事ではユーザーAPIを例に、実行時検証、読み込みと書き込みの変換、エラー、バージョン差、テストまで設計します。Adapterは単なる項目名の付け替えではありません。異なる契約同士の境界を明示し、変化をそこで受け止める役割があります。

## 外部の形をそのまま使う問題

APIが次のJSONを返すとします。外部仕様では名前が `snake_case`、日時が文字列、退会日時は `null` です。

```json
{
  "user_id": "u_123",
  "display_name": "Ada",
  "created_at": "2026-07-10T09:00:00.000Z",
  "deleted_at": null
}
```

レスポンス型をそのままアプリ全体で使うと、各利用側が外部の都合を知ることになります。

```ts
type UserResponse = {
  user_id: string;
  display_name: string;
  created_at: string;
  deleted_at: string | null;
};

function UserCard({ user }: { user: UserResponse }) {
  const createdAt = new Date(user.created_at);
  return `${user.display_name} / ${createdAt.toLocaleDateString("ja-JP")}`;
}
```

画面ごとに `new Date()` すれば、不正な日時の扱いがばらつきます。API v2で `display_name` がネストされたときは、多数のcomponentを修正します。さらに、外部レスポンスの型名を内部の `User` と呼ぶと、境界が見えなくなり「API都合なのか業務上必要な形なのか」を判断できません。

型注釈にも注意が必要です。`response.json()` の結果へ型を付けても、実行時のJSONは検証されません。

```ts
async function unsafeReadUser(response: Response): Promise<string> {
  // UserResponseだと保証したことにはならない
  const raw = (await response.json()) as UserResponse;
  return raw.display_name.toUpperCase();
}
```

サーバーがエラーHTMLや欠損JSONを返せば、その後の離れた場所で例外になります。変換の前に、入力が想定した外部契約を満たすか確かめる必要があります。

## Adapterを正確に定義する

GoFのAdapterは、あるclassのinterfaceをclientが期待する別のinterfaceへ変換し、本来は互換性のないclass同士を協調させます。典型的な登場人物は、利用側であるClient、利用側が望むTarget interface、既存のAdaptee、両者をつなぐAdapterです。

Webアプリではclassだけでなく、純粋な変換関数もAdapterとして有効です。外部DTOを受け取り内部modelを返す関数なら、Targetは戻り値の型、Adapteeは外部DTOの契約に相当します。状態や複数操作が不要なら、class wrapperを作る必要はありません。

Adapterが決めるのは形だけではありません。名前、単位、日時、欠損値、enum、エラー、同期・非同期、読み書きの方向を揃えます。ただし、割引計算や権限判定のような業務ルールまで詰め込むと、境界変換とドメイン判断が混ざります。

## 外部DTOと内部modelを分ける

外部仕様を表す型には `Api` や `Response` を付け、内部modelとは別名にします。内部ではアプリで扱いやすい `camelCase` と `Date` を使います。

```ts
type ApiUserV1 = Readonly<{
  user_id: string;
  display_name: string;
  created_at: string;
  deleted_at: string | null;
}>;

type User = Readonly<{
  id: string;
  displayName: string;
  createdAt: Date;
  deletedAt?: Date;
}>;
```

変換関数は新しいobjectを返し、入力を変更しません。日時は構文だけでなく、有効な時刻へ変換できることも確認します。

```ts
function parseDate(name: string, value: string): Date {
  const date = new Date(value);
  if (Number.isNaN(date.getTime())) {
    throw new Error(`${name} must be a valid date-time`);
  }
  return date;
}

function adaptApiUser(input: ApiUserV1): User {
  return {
    id: input.user_id,
    displayName: input.display_name,
    createdAt: parseDate("created_at", input.created_at),
    ...(input.deleted_at === null
      ? {}
      : { deletedAt: parseDate("deleted_at", input.deleted_at) }),
  };
}
```

`null` を内部でも維持する選択も正しい場合があります。ここでは「存在しない値」をoptional propertyへ統一しました。大切なのは、境界で意味を決め、利用側が外部仕様の `null` ルールを毎回解釈しないことです。

## 変換前に実行時検証を行う

Adapterは入力が正しい前提で変換し、validatorは入力が契約に合うか確かめます。役割は別です。手書きのtype guardでも実装できますが、項目が増えるとZod、Valibotなどのschema validatorを使うと、検証と型推論を揃えやすくなります。次は依存を増やさない最小例です。

```ts
function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === "object" && value !== null;
}

function parseApiUserV1(value: unknown): ApiUserV1 {
  if (
    !isRecord(value) ||
    typeof value.user_id !== "string" ||
    typeof value.display_name !== "string" ||
    typeof value.created_at !== "string" ||
    !(typeof value.deleted_at === "string" || value.deleted_at === null)
  ) {
    throw new Error("invalid ApiUserV1 response");
  }

  return {
    user_id: value.user_id,
    display_name: value.display_name,
    created_at: value.created_at,
    deleted_at: value.deleted_at,
  };
}
```

取得処理では「HTTP成功」「JSONの形」「内部modelへの変換」を順番に扱います。どこで失敗したか分かるよう、少なくともmessageへ段階を残します。大規模なアプリでは原因を保持するcustom errorを定義してもよいでしょう。

```ts
async function fetchUser(id: string, signal?: AbortSignal): Promise<User> {
  const response = await fetch(`/api/users/${encodeURIComponent(id)}`, {
    signal,
  });
  if (!response.ok) {
    throw new Error(`user request failed: HTTP ${response.status}`);
  }

  const dto = parseApiUserV1(await response.json());
  return adaptApiUser(dto);
}
```

この境界を通過した後、画面や業務処理は `User` だけを扱います。外部の日時表現を再びparseしたり、`user_id` と `id` を混在させたりしません。

## テストで変換の意味を固定する

Adapterは純粋関数にすると、外部I/Oなしで境界値をテストできます。単なるsnapshotだけでなく、日時と欠損値が意図した意味へ変わったかを明示的に確かめます。

```ts
import assert from "node:assert/strict";
import test from "node:test";

test("adapts an API user to the domain model", () => {
  const actual = adaptApiUser({
    user_id: "u_123",
    display_name: "Ada",
    created_at: "2026-07-10T09:00:00.000Z",
    deleted_at: null,
  });

  assert.equal(actual.id, "u_123");
  assert.equal(actual.displayName, "Ada");
  assert.equal(actual.createdAt.toISOString(), "2026-07-10T09:00:00.000Z");
  assert.equal(actual.deletedAt, undefined);
});
```

壊れた入力は、利用側で `Cannot read properties of undefined` になる前に境界で拒否します。

```ts
test("rejects a missing display name", () => {
  assert.throws(
    () =>
      parseApiUserV1({
        user_id: "u_123",
        created_at: "2026-07-10T09:00:00.000Z",
        deleted_at: null,
      }),
    /invalid ApiUserV1/,
  );
});

test("rejects an invalid date", () => {
  assert.throws(
    () =>
      adaptApiUser({
        user_id: "u_123",
        display_name: "Ada",
        created_at: "not-a-date",
        deleted_at: null,
      }),
    /valid date-time/,
  );
});
```

日時はtimezoneがない文字列を許すか、未知のenumをエラーにするか、余分なfieldを捨てるかなど、境界には判断事項があります。それぞれを契約としてテストすれば、外部API変更時に意図しない意味の変化へ気づけます。

## 書き込み方向も明示する

読み込みAdapterを逆向きに使い回すと、APIへ送ってはいけないfieldまで含めたり、`undefined` のserialize方法を誤ったりします。更新request専用のDTOと関数を定義します。

```ts
type UpdateUserInput = Readonly<{
  displayName: string;
}>;

type ApiUpdateUserRequest = Readonly<{
  display_name: string;
}>;

function toApiUpdateUserRequest(input: UpdateUserInput): ApiUpdateUserRequest {
  const displayName = input.displayName.trim();
  if (displayName.length === 0) {
    throw new Error("displayName must not be empty");
  }
  return { display_name: displayName };
}
```

`adaptApiUser`、`toApiUpdateUserRequest` のように方向を名前へ含めると、レビュー時に境界を追いやすくなります。`convert` のような曖昧な名前では、どちらが外部形か分かりません。

```ts
async function updateUser(
  id: string,
  input: UpdateUserInput,
): Promise<User> {
  const response = await fetch(`/api/users/${encodeURIComponent(id)}`, {
    method: "PATCH",
    headers: { "content-type": "application/json" },
    body: JSON.stringify(toApiUpdateUserRequest(input)),
  });
  if (!response.ok) throw new Error(`update failed: HTTP ${response.status}`);
  return adaptApiUser(parseApiUserV1(await response.json()));
}
```

入力のtrimは業務ルールにも見えます。API契約として前後空白を送らない方針ならrequest Adapterに置けますが、「表示名では空白をどう扱うか」というドメイン規則ならuse case側へ置くべきです。変換と業務判断の境界をチームで揃えます。

## APIバージョン差を局所化する

外部API v2で名前の形が変わっても、内部の `User` は維持できます。v1とv2を別のDTO・Adapterとして扱えば、移行期間中も差が明確です。

```ts
type ApiUserV2 = Readonly<{
  id: string;
  profile: { displayName: string };
  timestamps: { created: string; deleted?: string };
}>;

function adaptApiUserV2(input: ApiUserV2): User {
  return {
    id: input.id,
    displayName: input.profile.displayName,
    createdAt: parseDate("timestamps.created", input.timestamps.created),
    ...(input.timestamps.deleted === undefined
      ? {}
      : { deletedAt: parseDate("timestamps.deleted", input.timestamps.deleted) }),
  };
}
```

1つの関数へoptional fieldを大量に足して両versionを推測させると、どの組み合わせが有効なのか分からなくなります。version判定はHTTP headerやendpointなど信頼できる情報で行い、検証後に対応Adapterを選びます。曖昧なshape推測は、仕様違反を正常値として飲み込む危険があります。

## object Adapterが向く場面

複数のメソッドを持つ外部SDKを、小さな内部interfaceへ合わせるならclassやobject wrapperが適します。SDK固有の例外もここでアプリ共通のerrorへ変えられます。

```ts
interface Mailer {
  sendReceipt(input: { to: string; orderId: string }): Promise<void>;
}

class VendorMailerAdapter implements Mailer {
  constructor(private readonly sdk: VendorMailSdk) {}

  async sendReceipt(input: { to: string; orderId: string }): Promise<void> {
    try {
      await this.sdk.messages.create({
        recipient: input.to,
        template_id: "receipt",
        variables: { order_id: input.orderId },
      });
    } catch (cause) {
      throw new Error("receipt delivery failed", { cause });
    }
  }
}
```

利用側はvendor名、template parameter、SDK errorを知りません。SDKを変更しても `Mailer` を満たす別Adapterへ差し替えられます。ただし、内部interfaceを特定vendorの機能の写しにすると交換可能性は上がりません。アプリが実際に必要とする操作からTarget interfaceを設計します。

## RTK QueryのtransformResponseをAdapter的に読む

Redux Toolkit公式によると、RTK Queryのendpointに指定する `transformResponse` は、成功した `baseQuery` のdataがcacheへ入る前に加工し、その戻り値をcache dataとして使います。外部レスポンスをcomponentが使う形へ変換する境界として配置できます。

```ts
import { createApi, fetchBaseQuery } from "@reduxjs/toolkit/query/react";

const api = createApi({
  baseQuery: fetchBaseQuery({ baseUrl: "/api" }),
  endpoints: (build) => ({
    getUser: build.query<User, string>({
      query: (id) => `users/${id}`,
      transformResponse: (response: ApiUserV1) => adaptApiUser(response),
    }),
  }),
});
```

これによりcacheとcomponentは内部の `User` へ統一されます。現在の公式ドキュメントはruntime schemaによるresponse検証も案内しており、`transformResponse` を使う場合は `rawResponseSchema` で変換前、`responseSchema` で変換後を検証できます。型引数だけではruntime validationにならない点は、自作Adapterと同じです。

ただしRedux Toolkit公式は `transformResponse` をGoF Adapterとして分類していません。これは「外部形式を利用側の形式へ境界で変換する」という構造上の類似を学ぶ教育的な類推です。RTK Queryにはcache lifecycleなど固有の責務があり、古典的なobject Adapterと完全に同じではありません。

## JotaiのatomWithStorageをAdapter的に読む

Jotaiの `atomWithStorage` は、atomの読み書きとstorageの `getItem`、`setItem`、`removeItem` をつなぎます。custom storageを渡せば、localStorage以外の保存先にも合わせられます。

```ts
import { atomWithStorage, createJSONStorage } from "jotai/utils";

const storage = createJSONStorage(() => window.sessionStorage);
const themeAtom = atomWithStorage("theme", "light", storage);
```

公式ドキュメントはJSON parseが型安全ではなく、本番では検証が必要になり得ると明記しています。またSSRではbrowser storageが存在しないことや、初期値と保存値によるhydration mismatchにも注意が必要です。storage固有APIをatomのinterfaceへ合わせる点はAdapter的ですが、これもJotai公式によるGoF分類ではなく、本記事上の対応付けです。

## より単純な代替案とトレードオフ

外部と内部の形が同じで、変更可能性も低く、利用箇所が1つなら、別のAdapterを置かず直接使う方が明快です。項目を1つ取り出すだけなら `const name = response.display_name` で十分でしょう。名前だけを変える薄い関数を大量に作ると、定義へ移動する負担が増えます。

Adapterには境界が明確になる利点がある一方、DTOとmodelの型、検証、双方向関数、テストというコード量が増えます。変換でfieldを捨てると、後から必要になった情報を取得できません。日時へ変換するとserialize時に元の表記を完全には復元できない場合もあります。losslessな変換が必要か、アプリに必要な情報だけでよいかを決めます。

Facadeとの違いも押さえます。Adapterは互換性のないinterfaceを合わせるのが中心です。Facadeは複雑なsubsystemへ小さな入口を提供します。1つのwrapperが両方の役割を持つことはありますが、レビューでは「形を合わせるのか、操作をまとめるのか」を言葉にすると責務が膨らみにくくなります。

## 失敗しやすい設計

- `as ApiResponse` だけで外部値を信用し、検証したつもりになる。
- response DTOと内部modelへ同じ型名を使い、境界を見えなくする。
- 不正な日時や未知のenumを黙って既定値へ変え、障害を正常値に見せる。
- 読み込みと書き込みの変換方向を1つの曖昧な関数へ混ぜる。
- Adapterに認可や割引などの業務ルールまで集め、変更理由を増やす。
- vendor SDKの全APIを内部interfaceへ写し、結局vendorへ結合する。
- requestごとに同じ変換を画面で行い、仕様変更時の修正箇所を増やす。

エラーを変換するときは、診断に必要な `cause`、status、request IDを失わないようにします。利用者へvendor固有情報を見せないことと、運用ログから原因を追えないことは別です。また、機密情報をerror messageへ含めない配慮も必要です。

## 使うかどうかの判断基準

Adapterが向くのは、外部と内部で名前・型・単位・同期性・エラーが異なる、外部仕様の変更頻度が高い、複数箇所が同じ変換をしている、SDKを小さな内部契約の後ろへ置きたい、旧interfaceを保ちながら新実装へ移行したい場合です。

導入前に「Target interfaceはアプリの用途から設計されているか」「外部入力をどこで検証するか」「変換は情報を失うか」「読み書きの方向は明確か」「未知の値と失敗をどう表すか」を確認します。変換ルールがほとんどなく、利用箇所も限定的なら、直接利用する方が追跡しやすいこともあります。

## まとめ

Adapterは、外部仕様をアプリ全体へ浸透させず、境界で内部の契約へ合わせます。TypeScriptの型注釈だけに頼らず、未知の値を検証してから変換することが重要です。純粋な関数を基本にし、複数操作を持つSDKでは小さなobject Adapterを使うと、テストと交換が容易になります。

RTK Queryの `transformResponse` やJotaiのstorage utilityにはAdapter的な構造を観察できますが、それは公式のGoF分類ではありません。公式のAPI契約と、本記事での教育的な類推を分けながら読むことで、パターン名に引っ張られず「どの境界で、何を、どの意味へ変換するか」を設計できます。
