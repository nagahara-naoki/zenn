料金計算や配送方法のように、同じ目的へ複数の計算方法がある処理は、条件分岐が増えやすい場所です。最初は小さな `if` でも、規則が増えるにつれて、選択条件と計算内容が1つの関数へ混ざります。

Strategyパターンは、差し替えたい処理を同じ契約へ揃え、利用側から具体的な計算を分離します。クラスを増やすこと自体に意味はありません。「選ぶ処理」と「選ばれた後に実行する処理」を分けます。

コード例は、選択と計算の境界が見える範囲へ絞っています。実際の金額型や入力検証など、説明に直接関係しない定義は省略しています。

## 条件分岐の問題は長さより、変更理由の混在

会員ランクごとの割引を1つの関数へ書くと、次のようになります。

```ts
type Customer = {
  rank: "regular" | "silver" | "gold";
};

function calculatePrice(customer: Customer, subtotal: number): number {
  if (customer.rank === "regular") {
    return subtotal;
  }
  if (customer.rank === "silver") {
    return subtotal * 0.95;
  }
  if (customer.rank === "gold") {
    return subtotal * 0.9;
  }
  throw new Error(`Unknown rank: ${customer.rank}`);
}
```

3種類だけなら、これで十分です。条件分岐があるだけでStrategyへ変える必要はありません。

問題になるのは、割引ごとに有効期間、上限、対象商品、外部設定の参照などが加わったときです。新しい規則を足すたびに同じ関数を編集し、既存の規則まで再確認する必要が出ます。どのランクを使うかという選択と、各ランクの計算規則が密着しているためです。

```mermaid

    B --> C[共通の契約で実行]

    G[Gold] --> C
```

## まず関数を共通の型へ揃える

状態を持たない計算なら、クラスより関数Strategyの方が小さく書けます。

```ts
type PricingStrategy = (subtotal: number) => number;

const regularPricing: PricingStrategy = (subtotal) => subtotal;

const silverPricing: PricingStrategy = (subtotal) => subtotal * 0.95;

const goldPricing: PricingStrategy = (subtotal) =>
  Math.max(0, subtotal * 0.9 - 500);

const pricingByRank: Record<Customer["rank"], PricingStrategy> = {
  regular: regularPricing,
  silver: silverPricing,
  gold: goldPricing,
};

function calculatePrice(customer: Customer, subtotal: number): number {
  return pricingByRank[customer.rank](subtotal);
}
```

ここで分かれた責務は2つです。`pricingByRank` はランクから計算方法を選び、各関数は価格だけを計算します。goldの規則を変更しても、silverの関数へ触れる必要はありません。

ただし、分岐が消えたわけではありません。オブジェクトのキーによる選択へ形を変えただけです。Strategyの利点は、選択ロジックを1か所に集め、個別の規則を独立して読めるようにする点にあります。

## 共通契約には、意味まで含める

関数の引数と戻り値が同じでも、失敗方法や端数処理が違えば、安全には差し替えられません。

| 契約に含める項目 | 例 |
| --- | --- |
| 入力の単位 | 円か、最小通貨単位か |
| 戻り値の意味 | 割引額か、割引後価格か |
| 端数処理 | 切り捨て、四捨五入 |
| 許容範囲 | 0未満を許すか |
| 失敗方法 | 例外、Result、代替値 |

`PricingStrategy = (subtotal: number) => number` という型だけでは、これらを表せません。名前、型エイリアス、テスト、必要なら値オブジェクトを使って意味を固定します。

たとえばこの例では、すべてのStrategyが有限の非負値を返すと決めます。整数の円だけを許すなら、入力検証と端数処理も契約へ追加します。新しいStrategyを追加したときに同じ契約テストを通せば、利用側が個別の例外処理を増やさずに済みます。

## 依存や設定を持つならfactoryやクラスを使う

キャンペーン期間や割引上限など、Strategyが設定を持つ場合があります。無理にグローバル変数へ置かず、生成時に渡します。

```ts
function createCampaignPricing(options: {
  rate: number;
  maxDiscount: number;
  now: () => Date;
  endsAt: Date;
}): PricingStrategy {
  return (subtotal) => {
    if (options.now() >= options.endsAt) return subtotal;

    const discount = Math.min(
      subtotal * options.rate,
      options.maxDiscount,
    );
    return Math.floor(subtotal - discount);
  };
}
```

`now` を関数として渡したのは、テストで時刻を固定するためです。Strategyが必要とする依存がコード上に現れ、同じ計算を異なる設定で複数作れます。

状態と操作が増え、識別子や監査情報も必要になったらクラスが適する場合があります。Strategyが持つ状態と振る舞いの大きさを見て、関数とクラスを選びます。どちらを選んでもパターンの意図は保てます。

## 選択ロジックを利用側へ散らさない

Strategyを分けても、各画面やサービスが独自に `if (rank === ...)` と選び始めると、分岐の重複は残ります。

```ts
function selectPricingStrategy(
  customer: Customer,
  campaign: Campaign | undefined,
): PricingStrategy {
  if (campaign?.eligibleRanks.includes(customer.rank)) {
    return createCampaignPricing(campaign);
  }
  return pricingByRank[customer.rank];
}
```

利用側は選択結果を受け取り、同じ契約で実行します。選択条件が業務ルールなら、この関数自体もテスト対象です。

ここで注意したいのは、選択と実行を必ず別ファイルへ分けることではありません。小さな機能なら同じモジュール内でも構いません。読み手が「どこで種類を決め、どこで計算しているか」を区別できることが重要です。

## 非同期Strategyでは失敗の形を揃える

送料見積もりのように、外部APIを使うStrategyもあります。

```ts
type ShippingQuote = {
  provider: string;
  amount: number;
  estimatedDays: number;
};

interface ShippingStrategy {
  quote(input: ShippingInput, signal?: AbortSignal): Promise<ShippingQuote>;
}
```

すべての実装がPromiseを返し、キャンセルに `AbortSignal` を使い、同じエラー分類を返すと決めます。ある実装だけ `null` を返し、別の実装は例外を投げる状態では、利用側がStrategyごとの詳細を知る必要があり、差し替え可能とは言えません。

並列に複数社へ見積もりを依頼する場合は、最安値が必要なのか、最初の成功が必要なのか、全社の比較が必要なのかでPromiseのまとめ方も変わります。Strategyは個別アルゴリズムだけでなく、利用側とのエラー契約まで揃えて初めて機能します。

## テストは共通契約と個別規則に分ける

テストも2層にすると、何が壊れたか分かりやすくなります。

```ts
describe.each([
  ["regular", regularPricing],
  ["silver", silverPricing],
  ["gold", goldPricing],
] as const)("%s pricing", (_name, strategy) => {
  it("負の価格を返さない", () => {
    expect(strategy(0)).toBeGreaterThanOrEqual(0);
  });

  it("有限の数値を返す", () => {
    expect(Number.isFinite(strategy(10_000))).toBe(true);
  });
});
```

共通契約テストは、すべてのStrategyが守る最低条件を確認します。goldの500円追加割引のような固有ルールは、gold専用のテストへ分けます。これにより、新しい実装を追加するときの確認項目が明確になります。

## Strategyにするか、単純な分岐を残すか

| 単純な分岐が向く | Strategyが向く |
| --- | --- |
| 種類が2〜3個でほぼ増えない | 種類や規則が継続的に増える |
| 各分岐が1〜2行 | 各規則に独自の計算・依存がある |
| 選択条件と処理が同時に変わる | 選択条件と処理が別々に変わる |
| 個別テストの価値が低い | 実装ごとに契約を検証したい |

早すぎるStrategy化は、短い `if` を複数ファイルへ散らすだけになることがあります。変更理由が分かれてきた時点が、分離を検討する合図です。分岐の数だけで決めません。

## 失敗しやすい設計

Strategyを導入しても、次の状態では複雑さが減りません。

- Strategyごとに引数や戻り値の意味が違う。
- 利用側が具体的なStrategyの型を判定している。
- 選択ロジックが複数の画面やサービスへ散っている。
- 1つのStrategyが内部でさらに巨大な条件分岐を持つ。
- 変更予定のない2行の分岐までクラスへ分けている。

Strategyパターンは、増え続ける条件分岐を隠す魔法ではありません。同じ目的を持つ処理に共通の契約を与え、選択と実行を別々に変更できるようにする設計です。まず単純な関数とマップから始め、状態や依存が必要になったときにfactoryやクラスへ広げると、パターンのためのコードを増やさずに済みます。
