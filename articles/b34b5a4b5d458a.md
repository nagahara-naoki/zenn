Strategyは、同じ目的を持つ複数の処理を共通のinterfaceで表し、状況に応じて差し替えるパターンです。

目的はif文を消すことではありません。「何をするか」と「どの方法を選ぶか」を分離することです。

## 条件分岐が増え続ける例

```ts
type MemberType = "regular" | "premium" | "employee";

function calculatePrice(
  price: number,
  memberType: MemberType,
): number {
  if (memberType === "premium") {
    return price * 0.8;
  }

  if (memberType === "employee") {
    return price * 0.7;
  }

  return price;
}
```

条件が少なく、この関数だけで完結するなら問題ありません。

しかし、種類ごとに複雑な計算、外部設定、個別テストが必要になると、選択と計算を分ける価値が出ます。

## 関数をStrategyにする

```ts
type PricingStrategy = (price: number) => number;

const pricingStrategies: Record<MemberType, PricingStrategy> = {
  regular: (price) => price,
  premium: (price) => price * 0.8,
  employee: (price) => price * 0.7,
};

function calculatePrice(
  price: number,
  memberType: MemberType,
): number {
  return pricingStrategies[memberType](price);
}
```

JavaScriptでは、関数自体をStrategyとして扱えます。状態や複数メソッドが不要なら、classを作る必要はありません。

## classが向く場合

Strategyが依存や状態を持つ場合は、interfaceとclassで表せます。

```ts
interface ShippingStrategy {
  calculate(weight: number): number;
}

class DomesticShipping implements ShippingStrategy {
  calculate(weight: number): number {
    return 500 + weight * 100;
  }
}

class InternationalShipping implements ShippingStrategy {
  constructor(private readonly rate: number) {}

  calculate(weight: number): number {
    return 2_000 + weight * this.rate;
  }
}
```

利用側は具体実装ではなく、共通の操作だけを使います。

```ts
function checkout(
  weight: number,
  shipping: ShippingStrategy,
): number {
  return shipping.calculate(weight);
}
```

## 選択ロジックは消えない

Strategyへ分けても、どれを使うか決める処理は必要です。

```ts
function selectShipping(
  destination: "domestic" | "international",
): ShippingStrategy {
  return destination === "domestic"
    ? new DomesticShipping()
    : new InternationalShipping(300);
}
```

分岐を、業務処理の中からcompositionの場所へ移しました。

分岐が1か所で単純なら、元のif文の方が読みやすい場合もあります。

## NgRxのcreateReducerをStrategy的に読む

NgRxの `createReducer` と `on` は、action typeに対応するreducer関数を登録します。

```ts
const reducer = createReducer(
  initialState,
  on(increment, (state) => ({
    ...state,
    count: state.count + 1,
  })),
  on(reset, () => initialState),
);
```

現在のNgRx実装では、action typeとreducer関数の対応をMapへまとめ、受け取ったactionに合う関数を選びます。

```text
increment.type ──> increment用reducer
reset.type     ──> reset用reducer
```

actionに応じて処理戦略を選ぶ点はStrategy的に読めます。

NgRx公式がGoF Strategyパターンとして分類しているわけではありません。またreducerには状態遷移という固有の制約があるため、一般的なStrategyと完全に同一ではありません。

## switch文との比較

switchが常に悪いわけではありません。

```ts
switch (action.type) {
  case "increment":
    return increment(state);
  case "reset":
    return initialState;
  default:
    return state;
}
```

種類が少なく、処理が短く、追加頻度も低いなら十分に明快です。

Strategyが有効なのは、各処理を独立して差し替え・テスト・再利用したい場合です。

## 使うべき場面

- 同じ入力・出力を持つアルゴリズムが複数ある
- 運用設定や利用者ごとに処理を切り替える
- 各処理に個別の依存やテストがある
- 条件分岐から詳細処理を分離したい

## 注意点

- Strategyごとにinterfaceが少しずつ違わないか
- 選択処理が各所へ散らばっていないか
- 共有可能な状態をStrategyへ隠していないか
- 単純なifを過剰なclass群へ変えていないか

## まとめ

Strategyは分岐をなくすのではなく、変化する処理を交換可能な単位へします。

- 関数もStrategyとして使える
- 選択と実行を分離する
- 選択ロジックを適切な場所へ集める
- 単純な分岐には無理に導入しない
