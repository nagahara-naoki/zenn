JavaScriptやTypeScriptのプロジェクトで、ほぼ必ず目にする`node_modules`。

```text
my-app/
├─ src/
├─ package.json
├─ package-lock.json
└─ node_modules/
```

普段は意識せず使っていても、次のような疑問を持ったことはないでしょうか。

- 中には何が入っているのか
- なぜ数百MB、場合によっては数GBになるのか
- `package.json`にないパッケージまで入っているのはなぜか
- `import`したパッケージはどのように探されるのか
- エラーが出たときに削除してよいのか
- なぜGitへコミットしないのか

`node_modules`は、単なる「ライブラリ置き場」ではありません。

**プロジェクトが依存するパッケージを、Node.jsやビルドツールから利用できる形で配置したディレクトリ**です。

この記事では、`node_modules`の役割と仕組みを、実務で必要な範囲に絞って解説します。

## node_modulesとは

`node_modules`は、npmなどのパッケージマネージャーが、プロジェクトで使用するパッケージを配置するディレクトリです。

たとえば、次のコマンドを実行します。

```bash
npm install axios
```

すると、基本的には次のような変化が起こります。

```text
my-app/
├─ node_modules/
│  └─ axios/
├─ package.json
└─ package-lock.json
```

`package.json`には、プロジェクトが`axios`へ依存していることが記録されます。

```json
{
  "dependencies": {
    "axios": "^1.7.0"
  }
}
```

一方、実際に利用されるJavaScriptファイルや型定義などは、`node_modules`へ配置されます。

```ts
import axios from "axios";
```

このコードを処理するとき、Node.jsやVite、webpackなどのツールは、決められたルールに従って`axios`の実体を探します。

一般的なnpmプロジェクトでは、その探索先の中心になるのが`node_modules`です。

## package.jsonだけでは動かない

`package.json`には、必要なパッケージの名前と許可するバージョン範囲が記録されています。

```json
{
  "dependencies": {
    "axios": "^1.7.0",
    "zod": "^3.23.0"
  }
}
```

しかし、`package.json`自体に`axios`や`zod`のプログラムが含まれているわけではありません。

役割を分けると、次のようになります。

| 対象 | 主な役割 |
|---|---|
| `package.json` | 必要なパッケージと許可するバージョン範囲を宣言する |
| `package-lock.json` | 実際に解決した依存関係を記録する |
| `node_modules` | 解決されたパッケージの実体を配置する |

`package.json`が依存関係の**設計図**なら、`node_modules`は設計図をもとに組み立てられた**実体**です。

## node_modulesはどう作られるのか

プロジェクトのルートで次のコマンドを実行します。

```bash
npm install
```

npmは、大まかに次の処理を行います。

```text
1. package.jsonを読む
        ↓
2. package-lock.jsonを確認する
        ↓
3. 必要なパッケージとバージョンを決定する
        ↓
4. パッケージを取得する
        ↓
5. node_modulesへ配置する
        ↓
6. 必要なインストール処理を実行する
```

CI環境などで、Lockファイルどおりの状態を再現したい場合は、次のコマンドを使います。

```bash
npm ci
```

`npm ci`は既存の`node_modules`を削除し、`package-lock.json`をもとに依存関係全体をインストールします。

## 中には何が入っているのか

`node_modules`を開くと、多数のディレクトリやファイルが見つかります。

```text
node_modules/
├─ axios/
├─ zod/
├─ typescript/
├─ @angular/
├─ @types/
├─ .bin/
└─ .package-lock.json
```

主な内容を見ていきましょう。

## パッケージ本体

通常のパッケージは、パッケージ名と同じディレクトリに配置されます。

```text
node_modules/
└─ sample-package/
   ├─ package.json
   ├─ index.js
   ├─ dist/
   ├─ README.md
   └─ LICENSE
```

パッケージによって異なりますが、次のようなファイルが含まれます。

- JavaScriptファイル
- TypeScriptの型定義
- CommonJS用の成果物
- ES Modules用の成果物
- CSSや画像
- `package.json`
- ソースマップ
- ライセンスやREADME

パッケージ内の`package.json`には、読み込み先を決める情報が含まれることがあります。

```json
{
  "name": "sample-package",
  "main": "./dist/index.cjs",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "import": "./dist/index.js",
      "require": "./dist/index.cjs",
      "types": "./dist/index.d.ts"
    }
  }
}
```

Node.jsやビルドツールは、`main`や`exports`などを参照して、読み込むファイルを判断します。

## スコープ付きパッケージ

`@angular/core`や`@types/node`のように、`@`から始まるものはスコープ付きパッケージです。

```text
node_modules/
└─ @angular/
   ├─ core/
   ├─ common/
   └─ router/
```

`@angular`がスコープ名、`core`がパッケージ名です。

```text
@angular/core
└─ スコープ / パッケージ名
```

スコープを使うことで、組織やプロジェクト単位でパッケージをまとめられます。

## `.bin`ディレクトリ

`node_modules/.bin`には、パッケージが提供するCLIコマンドへのリンクが配置されます。

```text
node_modules/
└─ .bin/
   ├─ tsc
   ├─ eslint
   ├─ vite
   └─ prettier
```

たとえば、TypeScriptをインストールします。

```bash
npm install --save-dev typescript
```

TypeScriptパッケージは`tsc`というコマンドを提供しています。

`package.json`の`scripts`では、`.bin`までのパスを書かずに実行できます。

```json
{
  "scripts": {
    "typecheck": "tsc --noEmit"
  }
}
```

```bash
npm run typecheck
```

npmがスクリプトを実行するとき、`node_modules/.bin`を一時的にコマンドの探索先へ追加するためです。

次のように書く必要はありません。

```json
{
  "scripts": {
    "typecheck": "./node_modules/.bin/tsc --noEmit"
  }
}
```

## `.package-lock.json`

npm 7以降では、`node_modules`内に隠しLockファイルが作られることがあります。

```text
node_modules/
└─ .package-lock.json
```

これは、npmが`node_modules`全体を毎回読み直す負担を減らすために利用する内部的な情報です。

プロジェクトルートの`package-lock.json`とは別のファイルであり、基本的に開発者が直接編集するものではありません。

## package.jsonにないパッケージが入る理由

`package.json`に数個しか書いていないのに、`node_modules`には数百個のパッケージが入ることがあります。

理由は、インストールしたパッケージも、さらに別のパッケージへ依存しているからです。

たとえば、プロジェクトが`package-a`を使用するとします。

```text
my-app
└─ package-a
```

しかし、`package-a`は内部で`package-b`と`package-c`を使用しているかもしれません。

```text
my-app
└─ package-a
   ├─ package-b
   └─ package-c
```

さらに、`package-b`も別のパッケージに依存している可能性があります。

```text
my-app
└─ package-a
   ├─ package-b
   │  └─ package-d
   └─ package-c
```

自分で`package.json`へ追加したものを**直接依存**と呼びます。

```json
{
  "dependencies": {
    "package-a": "^1.0.0"
  }
}
```

`package-a`が内部で必要とする`package-b`などは、**推移的依存関係**または**間接依存**と呼ばれます。

| 種類 | 例 |
|---|---|
| 直接依存 | 自分のプロジェクト → `package-a` |
| 推移的依存 | `package-a` → `package-b` |

npmは、プロジェクトを動かすために必要な推移的依存関係も自動的にインストールします。

## 見覚えのないパッケージを調べる

なぜ特定のパッケージが入っているのかは、次のコマンドで確認できます。

```bash
npm explain パッケージ名
```

たとえば、`glob`が入っている理由を調べる場合は次のとおりです。

```bash
npm explain glob
```

依存ツリーは`npm ls`でも確認できます。

```bash
npm ls glob
```

表示例です。

```text
my-app
└─ build-tool
   └─ file-matcher
      └─ glob
```

`npm audit`で見覚えのないパッケージが表示された場合も、依存経路を確認することで、どの上位パッケージから入っているのか判断できます。

## なぜnode_modulesは巨大になるのか

`node_modules`が大きくなる主な理由は、次の5つです。

## 1. 推移的依存関係が多い

1つのツールを導入しただけでも、その内部で数十個以上のパッケージが利用されていることがあります。

特に次のようなツールは、多数の依存関係を持つ傾向があります。

- フレームワーク
- ビルドツール
- テストツール
- Linter
- Storybook
- E2Eテストツール

アプリケーション本体で使うライブラリだけでなく、開発環境を支えるツールも`node_modules`へ入ります。

## 2. 同じパッケージの複数バージョンが必要になる

異なるパッケージが、同じ依存パッケージの別バージョンを要求する場合があります。

```text
package-a
└─ shared-package@1

package-b
└─ shared-package@2
```

互換性がなければ、両方のバージョンを配置する必要があります。

概念的には、次のような構造になります。

```text
node_modules/
├─ shared-package/            # 2.x
├─ package-a/
└─ package-b/
   └─ node_modules/
      └─ shared-package/      # 1.x
```

このように、`node_modules`の中へさらに`node_modules`が作られることがあります。

## 3. 開発用ツールも含まれる

`devDependencies`に追加したパッケージも、通常の開発環境ではインストールされます。

```json
{
  "devDependencies": {
    "typescript": "^5.8.0",
    "eslint": "^9.0.0",
    "vitest": "^3.0.0"
  }
}
```

コンパイラー、テストランナー、Linterなどは、それぞれ多数の依存関係を持っています。

そのため、アプリケーションのコードが小さくても、開発環境全体では大きな容量になります。

## 4. 複数形式のファイルが含まれる

1つのパッケージに、複数環境向けのファイルが含まれることがあります。

```text
sample-package/
├─ dist/
│  ├─ index.js
│  ├─ index.cjs
│  ├─ index.d.ts
│  └─ index.js.map
├─ README.md
└─ LICENSE
```

たとえば、次のようなファイルです。

- ES Modules版
- CommonJS版
- TypeScript型定義
- ソースマップ
- 元のソースコード
- ドキュメント

実行時にすべて使うわけではなくても、配布パッケージに含まれていればディスクへ配置されます。

## 5. 大きなバイナリを含む場合がある

一部のパッケージは、JavaScript以外の大きなファイルを持っています。

- OSやCPU向けのネイティブバイナリ
- 画像処理ライブラリ
- コンパイラー
- ヘッドレスブラウザ
- WebAssemblyファイル

このような依存関係があると、`node_modules`の容量はさらに大きくなります。

## npmは依存関係をできるだけ共有する

すべての依存関係を各パッケージの内部へ個別に置くと、多くの重複が発生します。

npmは、互換性のあるパッケージを可能な範囲で上位の`node_modules`へ配置し、複数のパッケージから共有できるようにします。

一般に、このような配置は**hoisting**と呼ばれます。

`package-a`と`package-b`が同じ`shared-package`を必要としているとします。

```text
package-a ─┐
           ├─ shared-package@1.0.0
package-b ─┘
```

共有できる場合は、上位へ1つだけ配置できます。

```text
node_modules/
├─ package-a/
├─ package-b/
└─ shared-package/
```

必要なバージョンが異なり、共有できない場合は、一部が入れ子になります。

```text
node_modules/
├─ shared-package/            # 2.x
├─ package-a/
└─ package-b/
   └─ node_modules/
      └─ shared-package/      # 1.x
```

そのため、`node_modules`の構造は、`package.json`に書かれたパッケージを単純に並べただけではありません。

## importしたパッケージはどう探されるのか

次のCommonJSコードを考えます。

```js
const sample = require("sample-package");
```

相対パスが付いていないため、Node.jsは`sample-package`をパッケージ名として扱います。

CommonJSのモジュール解決では、現在のファイルに近い`node_modules`から順番に探索します。

実行中のファイルが次の場所にあるとします。

```text
/home/user/my-app/src/features/user.js
```

概念的には、次のような場所を上方向へ探します。

```text
/home/user/my-app/src/features/node_modules/sample-package
/home/user/my-app/src/node_modules/sample-package
/home/user/my-app/node_modules/sample-package
/home/user/node_modules/sample-package
/home/node_modules/sample-package
/node_modules/sample-package
```

近い場所で見つかったパッケージが利用されます。

この仕組みにより、次のような構成でも読み込めます。

```text
my-app/
├─ node_modules/
│  └─ sample-package/
└─ src/
   └─ features/
      └─ user.js
```

`user.js`と`node_modules`が同じディレクトリに存在しなくても、上位へたどることで見つけられます。

## 相対パスとの違い

次の2つは、探索方法が異なります。

```js
require("./sample-package");
require("sample-package");
```

### `./sample-package`

`./`から始まるため、現在のファイルからの相対パスとして探します。

### `sample-package`

相対パスではないため、パッケージとして`node_modules`などから探します。

ES Modulesでも、次の違いがあります。

```ts
import { value } from "./sample-package.js";
import { value } from "sample-package";
```

ただし、ES Modulesの正式な解決処理には`exports`なども関係し、CommonJSとは異なる部分があります。

## ブラウザが直接node_modulesを探すわけではない

React、Angular、Vueなどでも、次のようにパッケージを読み込みます。

```ts
import { z } from "zod";
```

しかし、通常のブラウザがプロジェクト内の`node_modules`を直接探索しているわけではありません。

一般的には、Viteやwebpack、Angular CLIなどがパッケージを解決します。

```text
ソースコード
import { z } from "zod";
        ↓
ビルドツールがnode_modulesから解決
        ↓
ブラウザで扱える形へ変換・結合
        ↓
ブラウザへ配信
```

本番環境では、必要なコードがJavaScriptファイルへまとめられたり、複数のチャンクへ分割されたりします。

```text
dist/
├─ index.html
├─ main-ABC123.js
└─ vendor-XYZ789.js
```

そのため、一般的なフロントエンドアプリでは、`node_modules`全体をそのままWebサーバーへ公開するわけではありません。

## なぜGitへコミットしないのか

通常、`node_modules`は`.gitignore`へ追加します。

```gitignore
node_modules/
```

主な理由は次の3つです。

## ファイル数と容量が大きい

`node_modules`には、数万以上のファイルが含まれることがあります。

Gitへ追加すると、次のような問題が起こります。

- リポジトリサイズが急増する
- cloneに時間がかかる
- 差分確認が難しくなる
- Gitの処理が重くなる
- 不要な変更が大量に記録される

## 再生成できる

通常は、次のファイルがあれば依存関係を再現できます。

```text
package.json
package-lock.json
```

新しい環境では次のコマンドを実行します。

```bash
npm ci
```

`node_modules`そのものではなく、依存関係を定義するファイルを共有する方が管理しやすくなります。

## 環境によって内容が変わることがある

一部のパッケージには、OSやCPUに応じたバイナリが含まれます。

```text
Windows x64
macOS arm64
Linux x64
```

Windowsで作った`node_modules`をMacやLinuxへそのまま持っていっても、正常に動かない場合があります。

環境ごとにインストールし直す方が安全です。

## node_modulesは削除してよいのか

基本的には、`package.json`と`package-lock.json`が残っていれば削除できます。

macOSやLinuxでは次のように削除できます。

```bash
rm -rf node_modules
npm install
```

WindowsのPowerShellでは次のとおりです。

```powershell
Remove-Item node_modules -Recurse -Force
npm install
```

Lockファイルどおりにクリーンな状態を作り直したい場合は、次のコマンドが便利です。

```bash
npm ci
```

`npm ci`は既存の`node_modules`を削除してから再インストールします。

## 削除すると直ることがある理由

`node_modules`を削除して再インストールすると、次のような状態をリセットできます。

- インストールが途中で失敗した
- 一部のファイルが欠けている
- 手動変更で内容が壊れている
- Lockファイルと実体がずれている
- ブランチ切り替えで依存関係が変わった
- Node.jsやOSの環境を変更した

つまり、依存関係の定義をもとに、パッケージの実体を組み立て直しています。

ただし、「エラーが出たら毎回削除する」という対応には注意が必要です。

根本原因が次の場所にある可能性もあります。

- `package.json`
- `package-lock.json`
- Node.jsやnpmのバージョン
- Peer Dependencies
- ビルドツールの設定
- 環境変数

再インストールで直っても、何がずれていたのかを確認することが大切です。

## package-lock.jsonも一緒に削除するべきか

`node_modules`と`package-lock.json`を同時に削除する方法を見かけることがあります。

```bash
rm -rf node_modules package-lock.json
npm install
```

しかし、この2つの削除は意味が異なります。

```text
node_modulesを削除
→ 配置されたパッケージの実体を作り直す

package-lock.jsonを削除
→ 依存関係の解決結果そのものを作り直す
```

`node_modules`だけを削除し、`npm ci`を実行すれば、Lockファイルに記録された依存関係を再現できます。

一方、`package-lock.json`も削除すると、`package.json`のバージョン範囲をもとに依存関係が再計算されます。

```json
{
  "dependencies": {
    "sample-package": "^1.2.3"
  }
}
```

以前は`1.3.0`が入っていても、再計算後は`1.9.0`が選ばれる可能性があります。

原因が分からないまま両方を削除すると、どのバージョン変更で問題が直ったのか分かりにくくなります。

まずはLockファイルを残したまま、次のコマンドを試す方が安全です。

```bash
npm ci
```

## node_modulesを直接編集してはいけない理由

`node_modules`内のコードを直接変更すると、その場では問題が直ることがあります。

```text
node_modules/sample-package/index.js
```

しかし、再インストールすると変更は失われます。

また、他の開発者やCI環境には修正が共有されません。

依存パッケージの変更が必要な場合は、次の方法を検討します。

- パッケージを更新する
- `overrides`で依存バージョンを調整する
- `patch-package`などでパッチを管理する
- Forkしたパッケージを利用する
- 本家へ修正を提案する

重要なのは、修正内容を**再現可能な形で管理すること**です。

## パッケージマネージャーによって構造は異なる

ここまではnpmを中心に説明しましたが、パッケージマネージャーによって配置方法は異なります。

### npm

通常の`node_modules`を作り、共有できる依存関係を可能な範囲で上位へ配置します。

### pnpm

パッケージを共有ストアへ保存し、リンクを使って`node_modules`を構成します。

見た目は`node_modules`でも、npmとは内部構造が異なります。

### Yarn

設定やバージョンによって、通常の`node_modules`を使う構成と、Plug'n'Playを使う構成があります。

Plug'n'Playでは、`node_modules`が作られない場合もあります。

本質的に必要なのは`node_modules`という名前のフォルダではなく、**実行環境やツールが依存パッケージを解決できる仕組み**です。

## よくある誤解

## 誤解1：直接追加したパッケージだけが入る

実際には、直接依存だけでなく推移的依存関係も入ります。

```text
自分のプロジェクト
└─ 直接依存
   └─ 推移的依存
      └─ さらにその依存
```

そのため、数個のパッケージを追加しただけでも、多数のディレクトリが作られます。

## 誤解2：importするとブラウザがnode_modulesを探す

一般的なフロントエンド開発では、ビルドツールが`node_modules`からパッケージを解決します。

ブラウザへ配信される段階では、必要なコードがビルド成果物へ変換されています。

## 誤解3：削除すると依存関係の定義も消える

依存関係の宣言は`package.json`、解決結果は`package-lock.json`にあります。

`node_modules`だけを削除しても、これらが残っていれば再インストールできます。

## 誤解4：package-lock.jsonも毎回削除した方がよい

Lockファイルを削除すると、依存関係のバージョンが再解決されます。

同じ状態を作り直すなら、まず`npm ci`を検討します。

## 誤解5：中を直接修正しても問題ない

直接修正した内容は再インストールで失われ、他の環境にも共有されません。

更新やパッチなど、再現可能な方法で管理する必要があります。

## 実務で覚えておきたいコマンド

### 依存関係をインストールする

```bash
npm install
```

### Lockファイルどおりに再構築する

```bash
npm ci
```

### パッケージが入っている理由を確認する

```bash
npm explain パッケージ名
```

### 依存ツリーを確認する

```bash
npm ls パッケージ名
```

### 更新可能なパッケージを確認する

```bash
npm outdated
```

### 不要なパッケージを削除する

```bash
npm prune
```

## 問題が起きたときの確認順

エラーが出たとき、最初から`node_modules`とLockファイルをすべて削除する必要はありません。

次の順番で確認すると、原因を追いやすくなります。

```text
1. エラーメッセージを確認する
        ↓
2. Node.jsとnpmのバージョンを確認する
        ↓
3. package.jsonとpackage-lock.jsonの差分を確認する
        ↓
4. npm lsで依存関係を確認する
        ↓
5. npm ciでnode_modulesを再構築する
        ↓
6. 必要な場合だけLockファイルの再生成を検討する
```

使用するコマンドの例です。

```bash
node --version
npm --version
git diff -- package.json package-lock.json
npm ls
npm ci
```

単に削除して直すだけでなく、どの状態が原因だったのかを確認できると、再発を防ぎやすくなります。

## まとめ

`node_modules`は、プロジェクトが依存するパッケージの実体を配置するディレクトリです。

```text
package.json
→ 必要な依存関係を宣言する

package-lock.json
→ 解決された依存関係を記録する

node_modules
→ パッケージの実体を配置する
```

`node_modules`が巨大になる主な理由は、次のとおりです。

- 推移的依存関係もインストールされる
- 複数バージョンが共存することがある
- 開発用ツールも含まれる
- 型定義や複数形式の成果物が含まれる
- 大きなバイナリを含む場合がある

また、基本的には再生成できるため、通常はGitへコミットしません。

不整合が疑われる場合は、Lockファイルを残したまま次のコマンドで再構築できます。

```bash
npm ci
```

ただし、`node_modules`を削除することと、`package-lock.json`を削除することは意味が異なります。

```text
node_modulesの削除
→ インストール済みの実体を作り直す

package-lock.jsonの削除
→ 依存関係の解決結果から作り直す
```

`node_modules`の仕組みを理解すると、依存関係のエラー、パッケージの重複、`npm audit`の結果、ビルドツールの挙動を追いやすくなります。

普段は直接触らないディレクトリですが、JavaScript開発の依存関係を支える重要な仕組みです。
