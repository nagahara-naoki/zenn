title: "完了待ちと到着順"

前章では、最新値を組み合わせる`combineLatest`と`withLatestFrom`を見ました。この章では、残りの合成方法を扱います。

具体的には、5つです。すべての完了を待って結果を集める`forkJoin`、到着順に1本へまとめる`merge`、順番に実行する`concat`、対応する順番の値を組にする`zip`、そして最初に反応したものを採用する`race`です。

数は多いですが、身構えなくて大丈夫です。どれも複数のObservableを組み合わせるという点は同じで、違いは「待ち方」と「まとめ方」だけです。Marble Diagramで動きを見比べながら、1つずつ整理していきましょう。

## forkJoinで完了を待つ

`forkJoin`は、複数のObservableがすべて`complete`するのを待ち、それぞれの「最後の値」を組にして流します。

```text
a$:      --1--2--3|
b$:      ----A------B|
             forkJoin([a$, b$])
出力:    ------------[3,B]|
```

`a$`の最後の値は`3`、`b$`の最後の値は`B`です。両方が完了した時点で、`[3, B]`を1回だけ流して、自身も完了します。途中の値（`a$`の1や2）は使われず、最後の値だけが結果になる、という点に注目してください。

これが役立つのは、複数のHTTPリクエストを同時に投げて、すべての結果がそろってから、まとめて処理したいときです。

```ts
import { forkJoin, from } from 'rxjs';

forkJoin({
  user: from(fetch('/api/user').then((r) => r.json())),
  tasks: from(fetch('/api/tasks').then((r) => r.json())),
}).subscribe(({ user, tasks }) => {
  console.log(user, tasks);
});
```

配列だけでなく、オブジェクトの形でも渡せます。結果も同じキーのオブジェクトで受け取れるので、「どの結果がどれか」がわかりやすくなります。ユーザー情報とタスク一覧を、両方そろってから画面に表示したい、といった場面にぴったりです。

## Promise.allとの比較

`forkJoin`の動きは、`Promise.all`によく似ています。`Promise.all`を知っていれば、その感覚でだいたい理解できます。どちらも、すべてがそろうのを待って、結果をまとめて返します。

| 観点 | `Promise.all` | `forkJoin` |
|---|---|---|
| 待つ対象 | すべてのPromiseの解決 | すべてのObservableの完了 |
| 返るもの | 解決値の配列 | 最後の値の配列（またはオブジェクト） |
| 1つが失敗すると | 全体が失敗 | 全体がエラー |

違いは、Observableが複数の値を流せることです。`forkJoin`は、そのうち「最後の値」だけを使います。ここは`Promise.all`にはない、Observableならではの注意点です。

## completeしないObservableの問題

`forkJoin`は完了を待つので、`complete`しないObservableを渡すと、結果が永遠に流れません。ここは、はまりやすい落とし穴です。

```ts
import { forkJoin, interval, of } from 'rxjs';

// intervalは完了しないので、forkJoinは何も流さない
forkJoin([interval(1000), of('done')]).subscribe((result) => {
  console.log(result); // 呼ばれない
});
```

`interval`のように終わらないストリームを渡すと、`forkJoin`は「まだ完了していない」と、いつまでも待ち続けます。`forkJoin`に渡すObservableは、必ず完了するものにしてください。もし終わらないストリームを渡したいなら、前章で見た`take`などで、あらかじめ完了させてから渡します。

## 一つでもエラーになった場合

渡したObservableのうち、1つでもエラーを流すと、`forkJoin`はその時点で、全体をエラーにします。ほかの結果は捨てられます。これも`Promise.all`と同じ挙動です。

もし、結果を個別に扱いたい（1つ失敗しても、成功した分は使いたい）なら、各Observableの内側で`catchError`を使い、エラーを「値」に変えておきます。

```ts
import { forkJoin, of, catchError } from 'rxjs';

forkJoin([
  riskyRequest$.pipe(catchError(() => of(null))), // 失敗をnullに変える
  safeRequest$,
]).subscribe(([risky, safe]) => {
  console.log(risky, safe); // riskyが失敗してもnullで受け取れる
});
```

`catchError`をObservableごとに置くと、1つの失敗が全体を巻き込むのを防げます。`catchError`の詳しい使い方は、「エラー処理・再試行・キャンセル」の章で扱います。

## mergeで到着順に流す

`merge`は、複数のObservableを1本にまとめ、値が届いた順に、そのまま流します。どのObservableの値も、届いたそばから流れます。

```text
a$:      --1-----3-----5-->
b$:      ----A-----B------>
             merge(a$, b$)
出力:    --1-A---3-B---5-->
```

`a$`と`b$`の値が、到着した順に混ざって流れています。完了を待つ`forkJoin`とは対照的に、`merge`は待たずに、来たものから流します。複数のイベント源をまとめて、1つの流れとして扱いたいときに使います。たとえば、複数のボタンのクリックを、1本にまとめる場合です。

## concatで順番に実行する

`concat`は、渡したObservableを、順番に実行します。最初のObservableが`complete`してから、次のObservableを購読します。

```text
a$:      --1--2|
b$:              --A--B|
             concat(a$, b$)
出力:    --1--2--A--B|
```

`a$`がすべて流れて完了してから、`b$`が始まっています。`merge`が「同時に流す」のに対し、`concat`は「前が終わるのを待ってから次へ進む」動きです。順番が重要な処理を、直列に並べたいときに向いています。1つ注意点があります。前のObservableが完了しないと次に進まないので、`concat`に渡すものも、完了するストリームにしてください。

## zipで対応する値を組み合わせる

`zip`は、それぞれのObservableの「同じ順番の値」どうしを組にします。1番目と1番目、2番目と2番目、という具合です。名前のとおり、ジッパー（ファスナー）のように、左右をかみ合わせるイメージです。

```text
a$:      --1-----3-----5-->
b$:      ----A------B------>
             zip(a$, b$)
出力:    ----[1,A]--[3,B]-->
```

`a$`の1番目`1`と、`b$`の1番目`A`が組になって、`[1, A]`が流れます。相手の同じ順番の値がまだ来ていなければ、来るまで待ちます。順番で対応づけたいデータがあるときに使いますが、片方が遅れると、そのぶん待ち続ける点には注意が必要です。

## raceで最初のObservableを採用する

`race`は、名前のとおり「競争」です。最初に値を流したObservableを採用し、残りは捨てるOperatorです。

```text
a$:      -------1--2-->
b$:      ---A--B------>
             race(a$, b$)
出力:    ---A--B------>   （先に流れたb$を採用）
```

`b$`のほうが先に値を流したので、`b$`が採用され、`a$`は無視されます。複数の取得元があって、最も早く応答したものだけを使いたい、といったときに向いています。

## 各結合方法の違いと選び方

ここまでの合成を、前章の`combineLatest`も含めて、表にまとめます。

| Operator | まとめ方 | 主な用途 |
|---|---|---|
| `combineLatest` | どれかが動くたび、全員の最新値 | 複数条件の組み合わせ |
| `forkJoin` | 全員の完了を待ち、最後の値 | 複数リクエストの結果集約 |
| `merge` | 到着順にそのまま流す | 複数イベント源を1本に |
| `concat` | 前が完了してから次へ | 順番が重要な直列処理 |
| `zip` | 同じ順番の値を組にする | 対応するデータの対応づけ |
| `race` | 最初に流したものを採用 | 最速の応答だけ使う |

選ぶときは、まず「待つのか、それとも流し続けるのか」を考えると、大きく2つに絞れます。全員の完了を待つなら`forkJoin`、待たずに流すなら`merge`や`concat`です。そのうえで、同時でよいか順番が要るか、対応づけが要るか、といった条件で、さらに絞り込みます。

## 完了を待つか、届いた値を流すかで合成方法を選ぶ

完了待ちと到着順を扱う合成方法を整理します。

- `forkJoin`は全員の完了を待ち、それぞれの最後の値を組にします。`Promise.all`に似ています。
- `forkJoin`は完了しないObservableだと結果が出ず、1つのエラーで全体が失敗します。
- `merge`は到着順にそのまま流し、`concat`は前が完了してから次へ進みます。
- `zip`は同じ順番の値を組にし、`race`は最初に流したObservableを採用します。
- 「待つのか流すのか」「同時か順番か」で、使う合成を選びます。

次章では、合成の中でも特に重要な、Higher-order Observableを扱います。Observableの中にObservableがある状態と、それをそのまま購読したときに起きるNested Subscribeの問題を見ます。
