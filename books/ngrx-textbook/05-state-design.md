title: "Stateを設計する"

ここからは、NgRxの中心である状態の設計と読み書きに入ります。

最初のテーマは、状態の設計です。NgRxを使い始めると、便利さのあまり、つい何でもStoreに入れたくなります。しかし、状態の持ち方を最初に誤ると、更新のたびに矛盾が生まれたり、前章までに見た二重管理が復活したりします。逆に、ここをきちんと設計できれば、あとのReducerやSelectorが自然に書けるようになります。

この章では、何を状態として持ち、何を持たないかを判断できるようにします。タスク管理アプリの状態を題材に、避けたい設計と、良い設計を見比べながら進めます。

## 状態を分類する

状態を設計する前に、扱うデータをいったん分類しておくと、方針が立てやすくなります。前章までにも触れたとおり、状態には大きく3種類あります。

| 種類 | 例 | 特徴 |
|---|---|---|
| サーバーのデータ | タスクの一覧 | 通信で取得・更新する |
| UIの状態 | 絞り込み条件、選択中のタスクID | ユーザー操作で変わる |
| 通信の状態 | 読み込み中か、エラーか | 通信の進行を表す |

なぜ分類するのかというと、種類によって扱い方の指針が変わるからです。サーバーのデータは、量が増えるので正規化を意識します。UIの状態は、できるだけ小さく保ちます。通信の状態は、あいまいにせず明示的に持ちます。分類しておけば、「この状態はどう持つべきか」を、種類から判断できます。

## いちばん大事な原則：派生値を状態に持たない

状態設計でもっとも大事な原則から始めます。派生値を状態に持たない、という原則です。派生値とは、ほかの状態から計算で求められる値のことです。

具体例で考えます。タスク管理アプリで「未完了タスクの件数」を表示したいとします。この件数は、タスクの一覧を見れば、数えれば求められます。つまり、一覧から計算できる派生値です。この件数を、わざわざ状態として別に持つと、どうなるでしょうか。

```ts
// 避けたい設計: 件数を状態に持つ
type TasksState = {
  tasks: Task[];
  incompleteCount: number; // tasksから計算できるのに、別に持っている
};
```

この設計だと、タスクを追加するたび、削除するたび、完了させるたびに、`incompleteCount`も忘れずに更新しなければなりません。1か所でも更新を忘れると、一覧と件数が食い違います。「タスクは3件あるのに、未完了は5件と表示される」といった、つじつまの合わない状態が生まれます。前章で見た二重管理と、まったく同じ問題です。

では、どうするか。派生値は状態に持たず、必要なときにSelectorで計算します。

```ts
// 良い設計: 件数はSelectorで計算する
type TasksState = {
  tasks: Task[];
};

// Selectorで未完了件数を求める（Selectorの章で詳しく扱う）
const selectIncompleteCount = createSelector(
  selectTasks,
  (tasks) => tasks.filter((task) => !task.completed).length,
);
```

こうすれば、`tasks`が変われば、件数は自動的に正しく計算し直されます。更新し忘れるということが、そもそも起こりません。「計算で求められるものは、状態に持たない」。この一言を、状態設計の背骨にしてください。

## 選択中の項目はIDで持つ

派生値と並んで、初学者がやりがちなのが、選択中の項目を丸ごと持つことです。

タスクの詳細画面で「いま選択されているタスク」を扱いたいとします。ここで、選択中のタスクのオブジェクトをそのまま状態に持つと、一覧の中の同じタスクと、内容が二重になります。

```ts
// 避けたい設計: 選択中のタスクを丸ごと持つ
type TasksState = {
  tasks: Task[];
  selectedTask: Task | null; // tasksの中の1つと、内容が重複する
};
```

一覧側のタスクを更新しても、この`selectedTask`のコピーは古いまま取り残されます。またしても二重管理です。

これを避けるには、選択中の項目は「IDだけ」を持ちます。実体は、そのIDを使って一覧から引きます。

```ts
// 良い設計: 選択中はIDで持ち、実体はSelectorで引く
type TasksState = {
  tasks: Task[];
  selectedTaskId: string | null;
};

const selectSelectedTask = createSelector(
  selectTasks,
  selectSelectedTaskId,
  (tasks, id) => tasks.find((task) => task.id === id) ?? null,
);
```

IDだけを持てば、一覧のタスクが更新されても、`selectSelectedTask`は常に最新のタスクを指します。実体は一覧に1つしかないので、ずれようがありません。「実体は1か所、参照はIDで」。これも覚えておくと役立つ指針です。

## 状態を正規化する

サーバーから取得するデータが増えてくると、正規化という考え方が効いてきます。正規化とは、データを入れ子にせず、IDをキー（見出し）にした平らな形で持つことです。

言葉だけだとイメージしにくいので、比べてみます。タスクを配列で持つと、特定のIDのタスクを取り出すたびに、配列を先頭から探すことになります。

```ts
// 配列で持つ: 特定のタスクを探すたびに走査が必要
type TasksState = {
  tasks: Task[];
};

// 正規化して持つ: IDから直接引ける
type TasksState = {
  entities: Record<string, Task>; // IDをキーにしたオブジェクト
  ids: string[]; //                並び順を保つためのID配列
};
```

正規化された形では、`entities['task-1']`のように、IDから直接タスクを取り出せます。件数の多い一覧ほど、この差は大きくなります。ほかにも、更新が1か所で済む、同じデータが重複しにくい、といった利点があります。

ただし、この`entities`と`ids`を手で管理するのは手間がかかります。そこで、NgRxには`@ngrx/entity`という、正規化を肩代わりしてくれる仕組みが用意されています。詳しくはEntityの章で扱うので、ここでは「コレクション（一覧データ）は正規化を検討する」とだけ押さえておいてください。

## 状態をフラットに保つ

状態は、深い入れ子を避けて、できるだけ平らに保ちます。なぜかというと、入れ子が深いと、更新のたびに外側の階層までまるごと作り直す必要が出て、コードが複雑になるからです。

```ts
// 深い入れ子: 更新のたびに各階層を作り直すことになる
type State = {
  tasks: {
    list: {
      items: Task[];
      meta: { total: number };
    };
  };
};
```

この`items`を1つ更新するだけでも、`list`も`tasks`も、外側をすべて新しく作り直さなければなりません。イミュータブルな更新では、変えた部分の外側も新しいオブジェクトにする必要があるからです。状態を浅くしておけば、更新するReducerも浅く、読みやすくなります。機能ごとに状態を区切り、それぞれを浅く保つのが基本です。

## 状態に持たないもの

最後に、そもそもStoreに入れないほうがよいものを整理します。

- **派生値**: ほかの状態から計算できるもの。Selectorに任せます。
- **DOMの参照やコンポーネントのインスタンス**: 保存や復元ができず、Storeにそぐいません。
- **一時的な入力途中の値**: フォームの編集中の文字など、そのコンポーネントだけで完結するものは、コンポーネントのSignalで持てば十分なことが多いです。

大切な考え方は、「すべてをStoreに入れる必要はない」ということです。アプリ全体で共有し、単方向フローで厳密に管理する価値があるものだけを、Storeに置きます。この線引きの判断は、状態管理手法の使い分けを扱う最終章で、あらためて深く考えます。

## タスク管理アプリの状態を設計する

ここまでの原則を使って、タスク管理アプリの状態を実際に設計します。

```ts
type Filter = 'all' | 'active' | 'completed';

type TasksState = {
  tasks: Task[]; //          サーバーのデータ（後の章で正規化する）
  filter: Filter; //         UIの状態: 絞り込み条件
  selectedTaskId: string | null; // UIの状態: 選択中はIDで持つ
  loading: boolean; //       通信の状態
  error: string | null; //   通信の状態
};
```

ここには、派生値が1つも入っていない点に注目してください。絞り込み後の一覧、未完了件数、選択中のタスクの実体は、どれもこの状態から計算できるので、持ちません。すべてSelectorで導きます。選択中はIDで持ち、状態全体はこれ以上分解できない最小限の形にとどめています。

この、無駄のない状態を土台にして、次章からActionとReducerを組み立てていきます。良い状態設計は、あとの工程すべてを楽にする投資です。

## まとめ

この章では、状態の設計を確認しました。

- 状態は、サーバーのデータ・UIの状態・通信の状態に分類できます。
- 派生値は状態に持たず、Selectorで計算します。これが二重管理を防ぐ最重要の原則です。
- 選択中の項目はIDで持ち、実体はSelectorで引きます。
- コレクションは正規化を検討します。`@ngrx/entity`が支援します。
- 状態はフラットに保ち、DOM参照や派生値は持ちません。
- タスク管理アプリの状態を、派生値を含まない最小限の形に設計しました。

次章では、この状態を更新するきっかけとなるActionを、イベントとして設計する方法を扱います。
