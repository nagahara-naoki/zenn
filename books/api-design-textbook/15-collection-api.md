---
title: "検索・絞り込み・並べ替えを設計する"
---

一覧APIは、データが少ないうちは簡単に見えます。件数が増え、検索条件と画面が増えると、曖昧なクエリ仕様が性能問題と互換性問題を引き起こします。

## クエリの役割を分ける

```http
GET /events?status=published&startsAt.gte=2026-09-01T00%3A00%3A00Z&sort=startsAt,-createdAt&limit=20
```

この例には四つの関心があります。

- フィルター: `status`、`startsAt.gte`
- 並べ替え: `sort`
- ページサイズ: `limit`
- ページ位置: 次章で扱う`cursor`

全文検索、返却フィールド、関連リソースの展開を加えるなら、`q`、`fields`、`include`のように別の名前空間を使います。一つのパラメーターへ複数の意味を持たせません。

## フィルターの演算子を限定する

`startsAt.gte`のように演算子を明示すると、境界を判断しやすくなります。

| 演算子 | 意味 |
|---|---|
| `eq` | 等しい |
| `gte` / `lte` | 以上 / 以下 |
| `in` | 候補のいずれか |
| `contains` | 部分一致 |

すべての項目へすべての演算子を開放しないでください。許可する組み合わせを列挙し、インデックスと最大実行時間を考慮します。クエリ文字列をSQLへ直接連結する実装は論外です。

複数値の表し方も統一します。

```text
status=published&status=scheduled
```

この本では、URLエンコードとの衝突が少なく、値にカンマを含められる反復形式を採用します。カンマ区切りを採る場合も、エスケープ規則を説明します。

## 並べ替えには必ず安定した末尾キーを置く

`sort=startsAt`だけでは、開始日時が同じ二件の順序が決まりません。ページを移動する間に順序が揺れると、重複や欠落が起きます。

```text
sort=startsAt,id
```

利用者が一つのキーしか指定しなくても、サーバーは一意な`id`を末尾へ補います。既定の並び順も必ず文書化します。「DBが返した順」は契約になりません。

## 検索とフィルターを区別する

フィルターは構造化された値の一致を調べます。検索は、タイトルや説明文を複数語で探し、関連度順に並べることがあります。

```http
GET /events?q=api+design&sort=-relevance
```

検索対象、単語分割、大文字小文字、言語、関連度の安定性を説明します。厳密な一致が必要な業務処理に全文検索を流用しません。

## fieldsとincludeは上限を設ける

```http
GET /events/evt_123?fields=id,title,startsAt&include=venue,organizer
```

`fields`は転送量を減らし、`include`は往復回数を減らせます。一方、任意の深い関連を展開できると、重いクエリを簡単に作れてしまいます。

```mermaid
flowchart LR
    Q["クエリ受信"] --> A["パラメーター許可リスト"]
    A --> C["組み合わせと上限を検証"]
    C --> P["実行計画を組み立てる"]
    P --> D["決められた時間・件数で取得"]
    D --> R["公開レスポンスへ変換"]
```

許可するフィールドと関連を列挙し、展開段数、件数、クエリ複雑度へ上限を設けます。権限のない項目は、`fields`に指定されても返しません。

## 複雑な検索は別リソースとして検討する

条件が長く、JSONで表した方が明瞭な場合、検索操作を`POST /event-searches`として扱えます。検索条件を保存するなら、検索自体がリソースになります。

2026年6月に公開された[RFC 10008](https://www.rfc-editor.org/rfc/rfc10008)は、内容を持つ安全で冪等な検索に`QUERY`メソッドを定義しました。

```http
QUERY /events HTTP/1.1
Content-Type: application/json

{
  "status": ["published", "scheduled"],
  "startsAt": {"gte": "2026-09-01T00:00:00Z"}
}
```

ただし、新しいメソッドを認識しないゲートウェイ、SDK、監視製品が残っています。採用前に通信経路全体を検証し、必要なら`POST`による検索も用意します。

## 件数取得の費用を隠さない

正確な`totalCount`は、大規模データや複雑な権限条件で高価です。毎回当然のように返さず、次の選択肢を検討します。

- 合計件数を返さず、次ページの有無だけを返す
- 概算値であることを明示する
- 明示指定されたときだけ計算する
- 集計用エンドポイントや非同期ジョブへ分ける

## 不正な条件を静かに直さない

未知のフィルター、許可しない並べ替え、上限を超える`limit`は、エラーとして返す方が利用者に親切です。`limit=100000`を無言で100へ丸めるなら、応答へ実際の値を示します。

一覧APIの品質は、パラメーター数では決まりません。結果が決定的で、費用が制御され、条件の意味を利用者が予測できることが重要です。
