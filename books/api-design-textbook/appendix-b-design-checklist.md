---
title: "付録B：API設計チェックリスト"
---

新規APIと変更レビューに使うチェックリストです。すべての項目に機械的にチェックを付けるのではなく、該当しない項目には理由を残してください。

## 目的と利用者

- [ ] APIが支える利用者の仕事を一文で説明できる
- [ ] 利用者、管理者、外部システムなどの主体を列挙した
- [ ] APIの範囲と、外部サービスの責任を分けた
- [ ] 成功だけでなく主要な失敗シナリオを書いた
- [ ] 応答時間、件数、鮮度、可用性の目標を数値化した

## リソースと状態

- [ ] DBテーブルではなく、業務上識別する対象からリソースを選んだ
- [ ] URIが安定した識別子を表し、処理手順を漏らしていない
- [ ] 親子関係のネストが深すぎない
- [ ] リソースごとの所有者とテナント境界を定義した
- [ ] 状態遷移図があり、許可・禁止する遷移を説明できる
- [ ] 取消や中止を物理削除と区別した
- [ ] 重要な業務操作を属性更新へ押し込んでいない

## HTTP

- [ ] メソッドの安全性と冪等性が操作の意味に合う
- [ ] 作成は`201`と`Location`、非同期受付は`202`と照会先を返す
- [ ] `204`応答へ本文を付けていない
- [ ] `401`と`403`を区別した
- [ ] 競合の`409`と条件不成立の`412`を区別した
- [ ] `Content-Type`と`Accept`の非対応を処理する
- [ ] キャッシュ、条件付き要求、再試行に必要なヘッダーを定めた

## 入力

- [ ] パス、クエリ、ヘッダー、ボディの役割が分かれている
- [ ] 作成用、更新用、レスポンス用スキーマを分けた
- [ ] 入力可能なフィールドを許可リストで定義した
- [ ] 未知フィールドの扱いを決めた
- [ ] 省略、`null`、空文字列、空配列の意味を決めた
- [ ] 文字列、配列、数値、ボディ全体へ上限を設けた
- [ ] 構文、スキーマ、業務ルール、現在状態を検証する
- [ ] 単位、日時、金額、IDの形式が明確である

## レスポンス

- [ ] 利用場面に必要な項目だけを返す
- [ ] DBモデルを直接シリアライズしていない
- [ ] 権限別に秘密項目を除外する
- [ ] 一覧要約と詳細表現の差を名前で示した
- [ ] 順序、`null`、省略、空配列の規則が一貫している
- [ ] 計算値の基準時刻と保証範囲を説明した
- [ ] 未知の応答フィールドを利用者が無視できる規則を共有した

## 一覧と大量データ

- [ ] 許可するフィルター、演算子、並べ替えを列挙した
- [ ] 既定順序が決定的で、一意な末尾キーがある
- [ ] ページサイズに既定値と上限がある
- [ ] offsetとcursorの選択理由がある
- [ ] カーソルは不透明で、検索条件と結び付いている
- [ ] 正確な総件数の計算費用を確認した
- [ ] 一括処理の原子性と部分失敗形式を定義した
- [ ] 長時間処理をジョブ化し、状態と期限を定義した

## エラー

- [ ] Problem Detailsなど共通形式を採用した
- [ ] HTTPステータスと問題タイプの対応表がある
- [ ] クライアントがメッセージ解析なしで分岐できる
- [ ] 検証エラーが入力位置と安定したコードを示す
- [ ] 再試行の可否と`Retry-After`を説明した
- [ ] スタックトレース、SQL、秘密情報を返さない
- [ ] 外部応答と内部ログをrequestIdで結べる

## 認証・認可

- [ ] 利用者に合う認証方式を選んだ
- [ ] トークンの署名、`iss`、`aud`、時刻、スコープを検証する
- [ ] IDトークンをAPI用アクセストークンとして使っていない
- [ ] トークンをURLやログへ含めない
- [ ] `subject × action × resource × context`で認可する
- [ ] IDを差し替えた他人・別テナントへのアクセスを拒否する
- [ ] 機能、オブジェクト、フィールドの各層で認可する
- [ ] 特権操作に追加認証と監査がある
- [ ] 鍵のローテーションと資格情報の失効手順がある

## セキュリティと悪用対策

- [ ] 資産、攻撃者、信頼境界を描いた
- [ ] CORSとCSRFを構成に応じて設定した
- [ ] リクエスト数だけでなく処理量と同時実行を制限した
- [ ] 予約買い占めなど正常機能の大量悪用を検討した
- [ ] URL入力にSSRF対策を行う
- [ ] 秘密情報、個人情報、監査ログの保持と閲覧権限を決めた
- [ ] 旧版、検証環境、管理APIを台帳で管理する
- [ ] 外部依存にタイムアウト、サイズ上限、回路遮断がある

## 信頼性

- [ ] タイムアウト後に処理済みか確認できる
- [ ] 非冪等な再試行に冪等性キーを用意した
- [ ] 同じキーと異なる入力を拒否する
- [ ] 同時初回要求を原子的に一件へ束ねる
- [ ] ETagと`If-Match`で更新競合を検出する
- [ ] DB制約とトランザクションで不変条件を守る
- [ ] 再試行に指数バックオフ、ジッター、上限、締切がある
- [ ] 副作用が生じる各境界で重複を扱う

## キャッシュと流量制御

- [ ] 公開・利用者別・保存禁止の表現を分類した
- [ ] `no-cache`と`no-store`を使い分けた
- [ ] ETag、`Vary`、無効化、許容鮮度を決めた
- [ ] 秘密情報が共有キャッシュへ入らない
- [ ] 制限単位がIPだけに依存していない
- [ ] 高価な操作を別の枠で制限した
- [ ] `429`と`Retry-After`を返す
- [ ] 過負荷時にキューを無限に伸ばさない

## 非同期処理とWebhook

- [ ] `202`の後に状態と失敗理由を照会できる
- [ ] イベントに一意なID、種類、版、発生時刻がある
- [ ] 重複、遅延、順不同を前提にしている
- [ ] 受信側がイベントIDで重複排除できる
- [ ] 生ボディ、時刻、IDへ署名し、リプレイを防ぐ
- [ ] 再送間隔、上限、DLQ、手動再送を設計した
- [ ] 受信URLの所有確認とSSRF対策がある
- [ ] 購読できるイベントとデータを認可する

## 互換性と廃止

- [ ] 利用者の観点で破壊的変更かを判断した
- [ ] 意味変更を単なるフィールド追加として扱っていない
- [ ] OpenAPI差分と過去版テストを自動化した
- [ ] 新旧を並行提供できる内部境界がある
- [ ] 移行ガイド、検証環境、連絡手段を用意した
- [ ] `Deprecation`と`Sunset`の日時を決めた
- [ ] 利用状況を観測し、停止条件を満たしてから廃止する

## 契約・テスト・運用

- [ ] OpenAPIと人向け説明が同じ意味を示す
- [ ] 正常、入力不正、認証、認可、競合、過負荷をテストする
- [ ] 代表利用者の契約テストがある
- [ ] p50、p95、p99と過負荷からの回復を測る
- [ ] ログ、メトリクス、トレースの役割が分かれている
- [ ] メトリクスラベルのカーディナリティが制御されている
- [ ] 利用者視点のSLI、SLO、エラーバジェットがある
- [ ] 段階リリース、ロールバック、ランブックがある
